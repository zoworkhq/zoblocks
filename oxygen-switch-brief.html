Switch

A switch is the only control in a design system that promises something it usually cannot keep: this is now true. In healthcare software that promise gets made over a hospital wifi network, about a fact that might never have been asked, by someone wearing gloves, on a record that may already be signed. This brief designs the control that keeps the promise, or admits plainly that it did not.

00

The reference grid, and what it leaves out

The starting point was a specimen sheet: four axes — large, checked, containing text, disabled — producing sixteen cells. Every cell is correct. The sheet is also a complete description of a switch in a settings screen for a photo app.

Hold it against a real clinical surface and the omissions are the whole product. Sixteen cells and not one of them can express:

  • the write is in flight and has not landed;
  • the write failed and the value you are looking at is not what the server holds;
  • nobody has ever answered this question;
  • you may look at this but not change it, and here is why;
  • turning this on is the dangerous direction.

Each of those is a state a clinician acts on. Each is currently rendered — across most healthcare products built on a general-purpose design system — as one of the sixteen cells that already exist, which is how a switch comes to make a claim nobody checked.

The thesis

A switch is a request to change something, not a change. Oxygen's Switch models the request, the outcome, and the gap between them — and never renders a state it cannot substantiate. Everything below follows from that one sentence.

This restates CONTENT.md §1 for an interactive control

The style guide's one idea — an interface that omits a fact it already has is making a claim — was written about displaying data. A switch makes the same error in the opposite direction: it displays a fact it does not yet have. An optimistic switch is a blank cell with a colour.

01

Eight ways a switch fails in a hospital

These are not hypotheticals dressed as requirements. Each one is a failure mode with a specific mechanism, and each maps to a design decision later in this brief.

Failure 01 · the optimistic lie

It flips, the write fails, it flips back, nobody notices

A ward tablet on saturated hospital wifi. A nurse toggles Contact precautions, sees green, walks away. The PUT times out. The switch reverts silently a second later, off-screen.

→ §04 The commit phase machine. Pending is a rendered state; a revert is announced assertively and holds a visible error until acknowledged.

Failure 02 · binary cannot hold absence

"Off" and "never asked" are the same pixel

Advance directive on file rendered as a switch. Off means no directive — or means the admitting clerk skipped the field. A clinician reading it at 03:00 cannot tell, and the difference decides whether somebody gets resuscitated.

→ §07 checked: boolean | "unknown" with a FHIR dataAbsentReason, reusing the taxonomy already in @oxygenui-design/fhir.

Failure 03 · implied immediacy

A switch inside a form with a Save button

Switches mean applied now. Put one in a form that commits on submit and you have built a control whose entire visual grammar lies about when it takes effect. Users navigate away believing it is done.

→ §14 commit="instant" | "deferred". Deferred renders a pending-change marker and is lint-flagged outside a form context.

Failure 04 · disabled says nothing

Greyed out, unfocusable, unexplained

In clinical software the honest reason is almost never "disabled". It is the encounter is signed, your role cannot change this, this is a historical record. disabled removes the control from the tab order, so a screen-reader user never learns it exists, let alone why it is unavailable.

→ §08 readOnly + lockedReason as the default; disabled documented as the last resort.

Failure 05 · on is always good

Brand green for "Override allergy checking"

Design systems paint the on-state in the brand's affirmative colour because in consumer software "on" means "you have the feature". Half the switches in a clinical system are suppressions: silence the alarm, bypass the interaction check, hide the flag.

→ §06 tone derives the on-state from the semantic status tokens, so a suppression reads amber or red at a glance.

Failure 06 · colour is the only signal

The luminance is nearly identical

Oxygen's own tokens make the point. Off-track --ox-border-strong (#64748b) and on-track --ox-accent (#067662) sit at relative luminance 0.171 and 0.138 — a contrast ratio between them of 1.17:1. Printed in monochrome, or rendered in forced colours, they are the same object.

→ §15 Thumb position, a thumb glyph, and a text state word are each independently sufficient. Colour is the fourth signal, never the first.

Failure 07 · the brush tap

A tablet carried through a ward

A 24px target beside a patient name, an instant irreversible commit, and an auditable event. Gloves reduce pointer precision; a tablet held against a body registers taps nobody made.

→ §05 confirm="hold" | "dialog" | "attest", and a hit area decoupled from the visual size so the target never shrinks with density.

Failure 08 · loading is disabled wearing a spinner

The in-flight state removes the control

The conventional treatment for an async toggle blocks interaction while the write is in flight. Focus is lost, the control cannot be cancelled, and a slow network converts a switch into a dead pixel for as long as the request takes.

→ §04 Pending stays focusable, keeps its accessible name, announces politely, and supports cancellation where the caller provides it.

02

The three-axis state model

Every switch in every design system has one axis: checked. A clinical switch has three, and they are genuinely independent — a control can be on, reverting, and read-only simultaneously, and each fact needs its own rendering.

Axis 1 · value

What the record says

type SwitchValue =
  boolean | "unknown";

true · false · "unknown". The third is entered from data, never by a user. Paired with absentReason from @oxygenui-design/fhir, so the word rendered is "Not asked" or "Declined" or "Restricted" — never the same grey shrug for all of them.

Axis 2 · phase

What the system is doing about it

type CommitPhase =
  | "idle"
  | "pending"
  | "committed"
  | "reverted"
  | "blocked"
  | "queued"    // §11
  | "stale";    // §11

Every one of these is a different recovery action, which is the test for whether a state deserves to exist. reverted: we tried, it failed, retry is reasonable. blocked: the system refused before trying, retry fails identically. queued: nothing has been sent yet and the user may cancel. stale: somebody else won, and the choice is theirs or yours.

Axis 3 · availability

Whether you may change it, and why not

readOnly?: boolean
lockedReason?: string
disabled?: boolean  // last resort

Read-only keeps the control in the tab order, keeps its accessible name, adds aria-readonly, and renders the reason as visible text. A screen-reader user learns the state and the constraint.

The phase machine

Written once, in a hook, and exported on its own — for the same reason useLoadingGate is exported from loader-core: an application will need this decision for something that is not an Oxygen Switch, and a second hand-rolled copy of it is a second set of bugs. 

//                    ┌──offline──▶ queued ──reconnect──┐
//                    │                └──cancel──▶ idle│
//                    │                                 ▼
// idle ──user acts──▶ pending ──resolve──▶ committed ──800ms──▶ idle
//   ▲                  │                                        ▲
//   │                  ├──reject────▶ reverted ──acknowledge───┤
//   │                  └──refuse────▶ blocked  ──acknowledge───┤
//   └─── keep / take ◀── stale ◀── someone else's write lands ──┘
//
// Invariants, asserted in tests:
//   · The rendered value in `pending` is the REQUESTED value, never the server's.
//   · Leaving `pending` for `reverted` animates back over ≥180ms. No snap.
//   · `reverted`, `blocked` and `stale` persist until acknowledged. They never
//     time out — a failure nobody saw is a failure.
//   · A second toggle while `pending` supersedes the first; only the last
//     request's outcome is applied. Out-of-order responses are dropped.
//   · `stale` NEVER auto-resolves. A record that silently adopts the last
//     writer is a record that loses the clinical reasoning of the first.
The last invariant is the one that bites

Toggle on, toggle off, and the two writes race. Almost every optimistic toggle in production resolves this by whichever response arrives last — which means a slow first request can overwrite a fast second one, and the switch ends up showing a value the user explicitly changed away from. Requests carry a monotonic sequence number; a response whose sequence is not the latest is discarded without touching state.

Three details in that grid worth naming

  1. The labelled track does not change width when it toggles. "Active" is six characters, "Inactive" is eight. Both words are laid into the same grid cell so the track is sized by the longer of the two, and the thumb travel is constant. A switch that resizes as it toggles reflows everything to its inline-end — in a table row, the whole row jumps.
  2. Read-only is not a dimmed switch. It is a dashed border and a filled thumb: a different object, not a weaker one. Dimming reads as "inactive", which is a value, not an availability.
  3. The on-thumb carries a check. Not decoration — it is the signal that survives greyscale, and the reason the row below is still readable.

04

Commit: the phase machine, live

The most important thing this component does. Toggle the switch below — the demo simulates a network with a configurable latency and failure rate, and logs exactly what a screen reader would hear.

network:
Bed 14 · Ada Lovelace · MRN 4471902 phase: idle
Contact precautions
Gown and gloves on entry. Visible on the bed board and the handover list.
Off
idle · pending · committed · reverted · blocked

Everything tagged SR is what goes into the live region. The polite/assertive split is deliberate: a success is polite, a failure interrupts.

The caller's side of the contract

All of the above comes from returning a promise. If onCommit resolves, the component commits; if it rejects, the component reverts, announces, and holds the error. There is no state to thread, no isLoading to declare, and no way to forget the failure path — which is the point. 

// The whole three-phase UX, including rollback and announcement.
<Switch
  label="Contact precautions"
  checked={precautions}
  tone="caution"
  onCommit={async (next) => {
    await api.setPrecautions({ encounter, contact: next });
    setPrecautions(next);          // only reached on success
  }}
  onAuditEvent={(e) => audit.record(e)}
/>

// Fine-grained control, when the caller owns the state machine.
<Switch
  checked={value}
  phase={phase}                    // "idle" | "pending" | "reverted" | …
  requested={requested}            // what to render while pending
  error={error}
  onChange={handleChange}          // antd-compatible; fires optimistically
/>
Why the phase belongs in the component and not the app

Because every application gets it slightly wrong, in the same four ways: no minimum pending duration so fast writes flash; no maximum so a hung request spins forever; a revert that snaps rather than animates, so nobody sees it; and no announcement at all. Those are four decisions that have one correct answer each, and the correct answer does not vary by product. That is the definition of something that belongs in the library.

05

Confirmation: hold, dialog, attest

Friction is a budget. CONTENT.md §4 puts it plainly: too little and mistakes happen; too much and clinicians route around the system, which is worse, because the work moves somewhere you cannot see. Three levels, chosen by consequence.

confirm="hold" — press and hold. Try it with the mouse, or focus it and hold Space.

Suspend fall-risk alarm
Silences the bed alarm for this patient until the end of the shift.
Hold to confirm.
Active

Hold has a WCAG problem, and it is not waved away

A press-and-hold is a timed input. SC 2.2.1 Timing Adjustable applies, and a user with a tremor or limited dexterity may be unable to sustain a 600 ms contact reliably. So hold is offered under three conditions, all enforced in code rather than documented as advice:

  1. Keyboard and assistive-technology activation never holds. Activating via Space/Enter without a sustained keydown, or via an AT click, opens the dialog path instead. The confirmation is equivalent, not degraded.
  2. The duration is a token. --ox-switch-hold-ms, default 600, settable to 0 by the host application to disable the hold entirely in favour of the dialog.
  3. Release before completion is a no-op with feedback — "Not changed. Hold until the ring completes." — not a silent nothing, which reads as a broken control.

This is the same shape of finding as Signature's WCAG 2.1.1 note about draw-only capture: the technique is genuinely good for the primary user and genuinely excluding for a minority, so it ships with a mandatory equivalent path rather than a warning in the docs.

confirm="hold"

Ward-floor friction

600 ms of sustained contact, single-handed, gloves-compatible, no second surface to hit. Right for actions that are consequential but routine and reversible: suspending an alarm, changing a diet flag.

confirm="dialog"

Named consequence

A modal that states what will happen, to whom, and what cannot be undone — with the patient named. Never "Are you sure?", which asks the reader to re-derive the thing they were unsure about. Right for anything that changes what other clinicians will see.

confirm="attest"

Typed reason, recorded

The toggle requires free text and writes it to the audit event. Right for overrides: bypassing an interaction check, suppressing a duplicate-therapy alert. The reason is the deliverable, not the friction.

An undo affordance is a complement, never a substitute

"Toggle instantly and show an Undo toast" was considered as a replacement for confirmation. It is rejected as a replacement for one reason: undo requires the user to notice. The failure mode this section exists to prevent is a tap nobody made, by someone who has already looked away. A toast addressed to an absent reader is a log entry with an animation.

06

Tone — when "on" is the dangerous state

Roughly half the switches in a clinical system are suppressions. Painting them in the brand's affirmative colour tells a clinician scanning a screen that a row of green means everything is fine, when one of those greens means an alarm is off.

Allergy interaction checking
tone="affirmative" — on is the safe direction, and the default.
Enabled
Suppress duplicate-therapy alerts
tone="caution" — on removes a safety net. Amber, with the word.
Suppressed
Bypass allergy check for this order
tone="critical" + confirm="attest" — on requires a typed reason, recorded.
Bypassed
Show archived encounters
tone="neutral" — a view preference with no clinical direction at all.
Shown

Four switches, all on. Only the second and third are situations anyone needs to know about — and the colour, the glyph and the state word all say so.

Tone is not severity, and it does not escalate

tone describes the direction of the on-state, fixed at design time by the person who knows what the toggle does. It is not derived from data and it never changes at runtime, so it cannot be used to make a switch shout — which is how CONTENT.md §3's interruption budget stays intact. A component that could escalate its own colour would be escalated for emphasis within a week.

07

The third state: unknown, and why you cannot toggle into it

The single most valuable thing this component does that a general-purpose switch cannot, and the one that reuses machinery Oxygen already has.

Advance directiveNot asked Interpreter neededDeclined to answer Substance use screenRestricted — not shown MRSA screenResult pending

Four switches in the same visual state, saying four clinically different things. The thumb glyph and the word both change; the colour does not.

It reuses the taxonomy that already exists

@oxygenui-design/fhir already ships resolveAbsentReason() and an eleven-member AbsentReason union collapsed to the groups a reader must treat differently — including unstated, which is Oxygen's own and means absent with no reason given. The Switch does not invent a parallel vocabulary; it renders that one. 

<Switch
  label="Advance directive on file"
  checked={"unknown"}
  absentReason={resolveAbsentReason(obs.dataAbsentReason)}
  onCommit={record}
/>
// renders: thumb centred, dashed track, word "Not asked"
// announces: "Advance directive on file, switch, mixed, not asked"

A user can leave unknown. A user can never enter it.

This is a hard rule, and the reason is worth stating plainly: allowing a third click position would let someone un-ask a question. "The patient told me, and now I have set it back to not-asked" is not a thing that can happen in a record; the correction for a wrong answer is a new answer with a provenance, not an erasure.

  • Activating an unknown switch commits true — the affirmative, because that is the answer someone is recording.
  • A shift-activation or the row's secondary control commits false. Both paths are keyboard-reachable and labelled.
  • There is no path back. Returning to unknown requires a data change from outside the component.

If a surface genuinely needs a three-way input — Yes / No / Not asked, all equally selectable — a switch is the wrong control. See §17.

What aria-checked="mixed" costs, honestly

mixed is valid on role="switch" in ARIA 1.2 but support is uneven — some screen-reader and browser pairings announce it as "partially pressed", and a few older ones fall back to "not pressed", which is exactly the wrong reading. Mitigation, tested rather than assumed: the state word is always in the accessible description, so the announcement carries "not asked" in words regardless of how mixed is verbalised. The screen-reader matrix in §15 lists this as a must-verify before stable, and if a pairing reads it as unchecked we fall back to role="group" with two buttons for that state.

08

Read-only, locked, and the death of disabled

disabled is the most over-used attribute in healthcare UI and almost always the wrong one. It removes the control from the tab order, which removes it from a screen-reader user's world, and it gives no reason to anyone.

SituationWhat most systems renderOxygen rendersAnnounced as
Encounter is signed disabled, dimmed, silent readOnly + lockedReason="Encounter signed 14:32 by Dr Okafor" "…switch, on, read only. Encounter signed 14:32 by Dr Okafor."
Role lacks permission disabled, or the row is hidden entirely readOnly + reason; the row stays visible "…switch, off, read only. Your role cannot change this."
Historical record disabled readOnly + "Historical — as recorded 3 Jun 2026" "…switch, on, read only. Historical — as recorded 3 June 2026."
Depends on another field that is off disabled readOnly + "Requires notifications to be on" "…switch, off, read only. Requires notifications to be on."
The form itself is submitting disabled disabled — genuinely correct here, and transient Not announced; the submit state owns the announcement
The rule, stated for review

disabled is correct only when the unavailability is transient and caused by something the user just did. Everything else — policy, permission, record state, dependency — is readOnly with a reason. A lint rule flags a disabled Switch that has a lockedReason, because that combination means someone reached for the wrong prop and knew the reason anyway.

SwitchField and SwitchList

A bare switch is rare in clinical software. What actually ships is a labelled row inside a titled group, and getting the group right — the summary, the shared commit strategy, the announcement when several change at once — is most of the work.

One panel, five rows, five different situations — and no row is rendered as an ordinary "off".

What SwitchList owns

  • The summary line. "2 of 5 in effect" — counted from real state, with unknown excluded from both numerator and denominator and stated separately. A count that silently treats unknown as off is the §07 failure at group scale.
  • One live region for the group, not one per row. Five rows each with their own aria-live produces five interleaved announcements when a group commit lands.
  • A shared commit strategy — commit="instant" per row, or a group-level Apply with a pending-changes count.
  • Provenance in the header — who last changed it and when, because in a shared record that is the first question anyone asks.

What it deliberately does not own

  • A master switch with an indeterminate state. "Some children on" and "not asked" are different facts, and a tri-state switch cannot hold both. A group header that toggles all children is a checkbox with indeterminate, and the docs say so.
  • Cascading dependencies. Turning off a parent does not silently turn off children — it renders them readOnly with "Requires X to be on" and leaves their recorded values intact. Silent cascade destroys data the user did not ask to destroy.
  • Reordering or filtering. A precautions list is a fixed clinical set; a control that hides rows hides the ones that are off, which is the set a clinician most needs to see.

All live. Click any of them. The pill, the chip, the row and the micro switch are all role="switch"; the segmented control is not — see below.

segmented changes the ARIA role, on purpose

Two labelled cells that both look pressable are a radio group, and calling them a switch would be a lie to a screen reader. So appearance="segmented" renders role="radiogroup" with two radios — same value, same commit machine, honest semantics.

This is the answer to §17's first "do not use a switch": when a product genuinely needs Yes and No to be equally visible choices, it does not need a different component, it needs a different appearance. The unknown cell renders and is never selectable — it disappears once answered, and there is no path back to it. §07's rule holds in every appearance.

Why micro is safe and chip is not a button

A 26×14 px switch sounds like an accessibility failure and is not, because the hit area is a separate pseudo-element sized from --ox-density-target — measured at 44×44 px in that table at standard density, and 32×32 px at clinical density. Both clear SC 2.5.8's 24 px with room. Shrinking the pill does not shrink the target, and that is exactly why the two were decoupled in §03.

The chip looks like a toggle button and keeps role="switch" because it still names a persistent state rather than an action. A filter that says "Isolation" is not a verb. If a chip ever means "do something", it is a button and it is not this component.

The rule that keeps this from becoming a costume box

An appearance ships only if it can name the surface it exists for — settings page, form field, toolbar, patient-facing preference, dense table. Five surfaces, five appearances. There is no appearance="modern", and a proposed sixth has to displace one of these or name a sixth surface.

11

Variations of meaning — the states nobody builds

The form variations are craft. These are the product. Each one is a situation that occurs constantly in a shared clinical record and is, as far as I can find, handled by no general-purpose design system at all.

1 · until — an "on" that is not forever

Almost no clinical on-state is permanent. NPO until after theatre. Precautions until the screen returns. An alarm suspended until the end of the shift. A switch with no expiry is how a patient stays nil-by-mouth for three days because the person who turned it on went home.

Nil by mouth
Set for theatre. Shows on the bed board, the diet list and the handover.
Not in effect

Toggle it — the demo expires after 10 seconds so you can watch the whole life cycle. In production the expiry is server truth; the component renders and announces it, and never decides it.

What the component owns

  • Renders the expiry beside the state — "In effect until 14:30", not buried in a tooltip.
  • Warns before it lapses, at a caller-set untilWarnMs, so it can be extended rather than silently dropped.
  • At expiry, calls onExpire and announces the change politely. It does not write.
  • Renders a lapsed on-state distinctly from a never-on state, until someone acknowledges it.

What it must never do

Decide that the value has changed. The component renders until from the server and fires onExpire; the application writes. A component that flips a clinical flag off because a client clock passed a timestamp is a component that turns off precautions on a workstation whose time is wrong — and ENGINEERING's rule against reading the wall clock exists for exactly this. now is supplied, always.

2 · stale — somebody else changed it while you were looking

The defining property of a clinical record is that it is shared. Two clinicians open the same patient; one changes a flag; the other is looking at a value that is now wrong and has no idea. Every product solves this with a page refresh, which throws away the second clinician's intent without telling them it existed.

Contact precautions
Gown and gloves on entry.
In effect
Both choices are offered, and neither is default

"Keep theirs" and "Change it back" are two buttons and no pre-selection, because a conflict in a clinical record is not a merge problem — it is two people who each had a reason. Auto-resolving to last-write-wins discards the reasoning of whoever typed first; auto-resolving to first-write-wins discards a change someone made deliberately and more recently. The only correct behaviour is to show both and ask, which is why stale is a phase rather than a silent re-render.

3 · queued — toggled with no network

DESIGN.md requires every product built on Oxygen to have a designed state for "offline / degraded connectivity". For a switch that state is specific and is not the same as pending: nothing has been sent, it may be sent much later, and the user can still change their mind.

Falls risk
Adds the bed sensor to the round list.
Not in effect

Toggle while offline, then reconnect. The queued value is rendered as queued — dashed, blue, with the word — never as committed.

4 · confirm="countersign" — the independent double-check

High-alert medications, restraint orders, blood products, paediatric dose overrides: a real and regulated workflow where a second qualified person must independently verify before the action stands. It is a switch whose commit requires a different human. And it is the one place this component composes with something Oxygen already ships.

Release restraint order

Requested S. Mehta, RN · 14:07

Why this is the strongest composition in the catalogue

The countersign is a signature capture — the component you have already built, with its meaning, its attestation, its typed and drawn paths, and its FHIR Provenance mapping. The Switch contributes the state machine; Signature contributes the evidence. 

<Switch
  label="Release restraint order"
  tone="critical"
  confirm="countersign"
  countersign={{
    role: "registered-nurse",
    notSameAs: currentUser.id,   // independence, enforced
    meaning: "verification",
  }}
  now={serverTime}
  onCommit={releaseOrder}
/>

notSameAs is the whole point of an independent double-check and the thing most implementations forget: without it, one person clicks twice. It is enforced in the component, not left to the caller's onCommit.

5 · impact, provenance, audience

Not on list

impact — the consequence, before the click

CONTENT.md §4 says to state what will happen, to whom, and what cannot be undone. Every design system puts that in a confirmation dialog, which is after the decision. A switch whose consequences reach other people should carry them where they inform the decision rather than interrupt it. When confirm is also set, the dialog reuses the same content — written once.

provenance — who, and when

In a shared record this is the first question anyone asks, and it is the difference between "the flag is off" and "someone turned it off twenty minutes ago". Rendered from data; the component never infers it.

audience — the same fact, two readers

Oxygen already keeps clinician-facing and patient-facing strings in separate @oxygenui/intl catalogs rather than as two tones of one. audience extends that from the words to the affordance: the patient-facing rendering gets a larger target, plainer language, the consequence phrased as it affects them, and no clinical shorthand at all.

One value, one audit trail, two readers. "Given" and "Share my records with my GP" are not translations of each other — they are different catalogs, which is why this is a prop and not a stylesheet.

12

Recipes — compositions that need no new API

The discipline that keeps §10 and §11 from turning into forty props: anything expressible by combining what already exists ships as a documented recipe, not as a feature. These four cover most of what a clinical product will actually reach for.

recipe · break-glass

Emergency access to a restricted record

tone="critical"
confirm="attest"
impact={["The patient is notified",
         "Your access is reviewed by IG"]}
stateLabels="allowed-blocked"

The distinguishing feature of break-glass is not the friction — it is that somebody else finds out. That belongs in impact, where the clinician reads it before deciding, not in a policy document.

recipe · NPO until theatre

A flag that expires with an event, not a clock

tone="caution"
until={theatreSlot.start}
untilWarnMs={30 * 60 * 1000}
onExpire={promptToExtendOrClear}
stateLabels="in-effect"

until takes a timestamp, so an event-driven expiry is the application resolving the event to a time and re-rendering. The component stays ignorant of theatre scheduling, which is correct — it would be wrong about it.

recipe · a whole bay

One toggle, four patients, four outcomes

<SwitchList
  subjects={bay3.patients}
  confirm="dialog"
  // per-subject phase; the group never
  // reports success until all resolve
/>

The failure mode this prevents: a bulk action that reports "done" when three of four succeeded. The group summary counts committed, pending, blocked and stale separately and never rounds them into one word.

recipe · as-of

What the flag was at 14:00 yesterday

readOnly
lockedReason={"Historical — as recorded " + asOf}
provenance={entry.recordedBy}

A timeline scrubber over a record is a genuinely useful clinical view and needs no new component: a read-only switch with a reason is already the honest rendering of "this is what it was, and you cannot change the past".

How the catalogue is tiered

v1 — the three axes, five appearances, tone, confirm="hold" | "dialog" | "attest", SwitchField, SwitchList. v1.1 — until, queued, stale, provenance: each is small, each is independently shippable, and each earns its own release note. v2 — countersign (it needs Signature as a dependency and a role model to check against), impact, audience, subject-batched SwitchList. Never — anything in the recipe list above, which is the whole point of writing it down.

Layer 2 — props, and layer 3 — slots

Layer 2 · configuration

Bounded choices with a clinical reason

The API

antd's Switch surface is preserved verbatim, so import { Switch } from "antd" can become from "@oxygenui-design/react" with no other diff. Everything Oxygen adds is additive and optional. 

// ── antd-compatible core ────────────────────────────────────────────
export interface SwitchProps {
  checked?: boolean | "unknown";   // widened; boolean is antd's shape
  defaultChecked?: boolean | "unknown";
  onChange?: (checked: boolean, event: React.SyntheticEvent) => void;
  disabled?: boolean;
  loading?: boolean;                     // mapped to phase="pending"; kept for drop-in
  size?: "micro" | "small" | "default" | "large"; // "micro" and "large" are ours
  checkedChildren?: React.ReactNode;      // implies appearance="labeled"
  unCheckedChildren?: React.ReactNode;
  autoFocus?: boolean;
  id?: string; className?: string; style?: React.CSSProperties;

  // ── value and absence ─────────────────────────────────────────────
  /** Why the value is "unknown". Renders the word; drives the glyph. */
  absentReason?: AbsentReason;         // from @oxygenui-design/fhir

  // ── commit ────────────────────────────────────────────────────────
  /**
   * Return a promise and the component owns the phase machine: pending
   * while it is in flight, committed on resolve, reverted on reject —
   * with the rollback animated and announced.
   */
  onCommit?: (next: boolean, ctx: CommitContext) => void | Promise<void>;
  phase?: CommitPhase;                 // controlled alternative to onCommit
  requested?: boolean;                 // what to render while pending
  error?: React.ReactNode;             // shown and announced on revert/block
  commit?: "instant" | "deferred";     // deferred marks an unsaved change
  minPendingMs?: number;               // default 220 — no flash on a fast write
  onSlow?: () => void;                  // fires at slowAfter, default 4000

  // ── availability ──────────────────────────────────────────────────
  readOnly?: boolean;
  lockedReason?: React.ReactNode;

  // ── meaning ───────────────────────────────────────────────────────
  tone?: "affirmative" | "neutral" | "caution" | "critical";
  stateLabels?: StateLabelPreset | { on: string; off: string; unknown?: string };
  showState?: boolean;                 // the word beside the control; default true
  audience?: "clinician" | "patient";  // §11 — picks the intl catalog AND the affordance

  // ── time-boxing (§11) ─────────────────────────────────────────────
  /** ISO 8601. Renders "in effect until …". The component NEVER writes on expiry. */
  until?: string;
  untilWarnMs?: number;                // warn this long before it lapses
  onExpire?: (at: string) => void;      // the application decides what happens

  // ── shared-record reality (§11) ───────────────────────────────────
  /** An external value that disagrees with `checked`. Puts the switch in `stale`. */
  serverValue?: boolean | "unknown";
  onResolveConflict?: (keep: "mine" | "theirs") => void;
  provenance?: { by: string; at: string; via?: string };
  /** false queues the commit instead of sending it. Renders `queued`, cancellable. */
  online?: boolean;

  // ── confirmation ──────────────────────────────────────────────────
  confirm?: "hold" | "dialog" | "attest" | "countersign" | false;
  confirmCopy?: { title: string; consequence: string; subject?: string };
  /** §11 — the consequence, rendered BEFORE the click. Reused by the dialog. */
  impact?: React.ReactNode[];
  /** `notSameAs` is what makes an independent double-check independent. */
  countersign?: { role: string; notSameAs: string; meaning?: SignatureMeaning };

  // ── layout and composition ────────────────────────────────────────
  label?: React.ReactNode;
  description?: React.ReactNode;
  labelPlacement?: "end" | "start";    // logical; flips under RTL
  /** §10 — five surfaces, five appearances. `segmented` renders a radiogroup. */
  appearance?: "switch" | "labeled" | "segmented" | "chip" | "row";
  slots?: SwitchSlots;

  // ── governance ────────────────────────────────────────────────────
  onAuditEvent?: (e: { type: string; at: string; from: SwitchValue;
                        to: SwitchValue; reason?: string }) => void;
  now?: string;                        // ISO 8601 from the server. Never reads the clock.
}

Two deliberate frictions in that surface

  • now is required when onAuditEvent is supplied. Enforced in the types. A component that reads Date.now() to stamp an audit event stamps the client's clock, which on a ward workstation is frequently wrong — and it makes the output impossible to visually regression-test. Signature already established this rule.
  • loading maps to phase="pending" and does not disable. The prop is kept for drop-in compatibility, but the behaviour is corrected: the control stays focusable and keeps its name. This is a deliberate, documented divergence from antd — the only one in the core surface.

Exported alongside it

  • useCommitPhase() — the phase machine on its own, for a control that is not this one. Same reasoning as useLoadingGate.
  • SwitchField, SwitchList — the row and the group.
  • STATE_LABEL_PRESETS — the vetted word pairs (§16).
  • isUnknown(), isCommitted() — guards, so callers do not compare against string literals.

Words: the state label problem

"On" and "Off" are correct for a light switch and wrong for almost everything in a clinical record. A precaution is in effect; a consent is given; an order is active; a flag is set. The word is not decoration — it is the signal that survives greyscale, forced colours, and a screen reader.

PresetOnOffUnknownUse for
"on-off"OnOffNot setDevice and display settings. The literal default.
"yes-no"YesNoNot askedRecorded answers to a question someone actually asked.
"active-inactive"ActiveInactiveNot startedOrders, care plans, protocols.
"in-effect"In effectNot in effectNot assessedPrecautions, restrictions, alerts.
"allowed-blocked"AllowedBlockedNot specifiedSharing, access, consent directives.
"given-declined"GivenDeclinedNot askedConsent. Note that "off" here is a positive act, not an absence.
"enabled-disabled"EnabledDisabledNot configuredSystem features. Never for a clinical fact.

Rules the presets encode

  • The unknown word is never a shrug. Each preset has its own, and absentReason overrides it with something more specific still.
  • "Declined" is not "off". In "given-declined", the off state is a recorded clinical act with a person behind it. Collapsing it into a default-off is CONTENT.md §1's third row.
  • Both catalogs, separately. Patient-facing and clinician-facing strings live in different @oxygenui/intl catalogs — not different tones of the same one. "In effect" is not the patient-facing word for anything.

Announcement templates

// idle → pending
"{label}: setting to {state}…"          // polite
// pending → committed
"{label}: {state}."                       // polite
// pending → reverted
"{label} was not changed. {error} Still {state}."
                                          // assertive
// blocked
"{label} cannot be changed. {reason}"     // assertive

"Still {state}" is the load-bearing clause. Without it the listener knows the write failed but not what the value now is, which is the question they were actually asking.

When not to use a Switch

The most useful page in the docs, and the one that keeps the component from being misapplied into the failure modes in §01.

✗ For a question with three real answers

"Does the patient have a latex allergy?" — Yes and No must both be visible as choices, and a pill shows only the one it is currently on. Reach for appearance="segmented", which renders the same value as a radiogroup with both answers on screen (§10). Oxygen's unknown state remains for displaying an absence that came from data, never for capturing one — in every appearance.

✗ Inside a form that commits on submit

A switch means applied now. If it is not applied now, use a checkbox — which carries no such promise — or set commit="deferred" and accept the pending-change marker. Lint flags a switch inside a Form without one of the two.

✗ As the only display of a safety state

A switch is a control, and controls live where you put them — off-screen, below the fold, on another tab. If a suppressed alarm must be knowable from anywhere in the application, the switch changes it and a persistent banner reports it. Two components, one fact.

✗ For mutually exclusive options

Two switches where only one may be on is a radio group that has been disassembled. Users will turn both on, and the code that prevents it will turn one off without saying so.

✗ For a group header

"Turn all precautions on" wants an indeterminate state meaning some. A switch's third state means not asked. Use a checkbox with indeterminate — a different control, because it is a different fact.

✓ Use it for

A single independent setting that takes effect immediately, has two states, is reversible or confirmable, and whose current value is worth seeing at a glance in a list of similar settings. That is a narrow brief, and holding to it is why the control stays trustworthy.

The antd decision

Signature was the first component with an antd dependency, and the note on that decision said plainly: before starting another antd-dependent component, revisit whether the registry channel survives. This is that component, and it is the one where the answer matters most, because a Switch is a primitive that every form built on Oxygen will contain.

Recommendation: match the API, own the implementation

Ship Switch with antd's prop names and behaviour, and no antd dependency. Four reasons, in order of weight.

  1. The extension is not expressible as a wrapper. antd's checked is boolean. Adding a third value means either shadowing the prop — at which point you are reimplementing the control and paying for a dependency you route around — or giving up the state that §07 argues is the component's main clinical contribution. The same is true of the phase machine, which needs to render a value that is neither the prop nor the server's.
  2. There is no expensive behaviour to inherit. Signature wrapped antd because Modal's focus trap and Tabs' ARIA were genuinely hard to rebuild well, and rebuilding them badly would have undermined a component whose whole argument is accessibility. A switch is a button with aria-checked and two key handlers. There is nothing here worth a peer dependency.
  3. A primitive spreads the dependency to everything. Wrap here and every form component that contains a Switch inherits the peer dep, which ends copy-source distribution for the entire form family — the channel ADR 0002 deliberately preserved, and the one the README leads with for a healthcare buyer who must read what renders a consent flag.
  4. The compatibility promise is cheap to keep. Matching the surface costs a props table and a test; taking the dependency costs a peer range, a version matrix, and a v5/v6 rename audit on every antd major.

What "follows Ant Design" then means here

  • Prop names and shapes — checked, defaultChecked, onChange(checked, event), disabled, loading, size, checkedChildren, unCheckedChildren, autoFocus.
  • The form-control contract — accepts id, value/onChange, and reads validation status from context, exactly as Signature does, so it drops into a Form.Item with a working <label htmlFor>.
  • Visual language — the pill, the travel, the in-track labels, the sizes. Recognisably an antd switch, in Oxygen's tokens.
  • An optional bridge — @oxygenui-design/react/antd-bridge reads theme.useToken() and writes the --ox-switch-* tokens, so an antd application gets Oxygen's behaviour in its own brand. antd is imported only by that subpath, so it stays out of the main graph.
This wants an ADR, not a paragraph

Proposed: ADR 0010 — antd-compatible, antd-free primitives. It draws the line explicitly: primitives match antd's API and take no dependency; compound clinical organisms may wrap antd where a genuinely expensive behaviour is being inherited, and each one names that behaviour. Signature satisfies the second clause. That is a rule a reviewer can apply to the next component without re-litigating this.

Three antd behaviours to measure before writing the compatibility table

Stated as things to verify, not as findings: (1) whether loading blocks interaction in v6 as it has historically — this brief's loading → pending mapping is a deliberate divergence and the docs must say so precisely; (2) whether an antd Switch with differently-sized checkedChildren and unCheckedChildren changes width as it toggles, which determines whether §03's fixed-width track is a fix or a difference; (3) the measured contrast of antd's default off-track against its own background — the conventional rgba(0,0,0,0.25) resolves near #bfbfbf on white, roughly 1.9:1 against SC 1.4.11's 3:1, but it must be measured against the consumer's ConfigProvider theme rather than asserted from the default. All three are one afternoon with antd v6 installed, and all three belong in the migration note.

Budgets and their consequences

  • Size. The react barrel is capped at 9 KB today and currently holds five loaders. The Switch primitive plus the phase machine lands around 4–5 KB gzipped; the barrel budget needs raising to ~14 KB in the same PR, with a per-component entry so the Switch is measured on its own rather than hidden in an aggregate.
  • Stylesheet. switch.css carries only keyframes and the forced-colours block, as loader.css does — everything else is tokens. Budget 3 KB.
  • No new runtime dependency, which is what makes P0's recommendation cheap: no ADR needed for the dependency policy, only for the architecture.

Lint rules to add, in packages/eslint-plugin

  • @oxygenui/switch-not-for-questions (warn) — a label ending in "?" or matching a known interrogative shape. Points at the radio group.
  • @oxygenui/switch-needs-commit-strategy (error) — a Switch inside a Form without commit set.
  • @oxygenui/no-disabled-with-reason (error) — disabled together with lockedReason: the author knew the reason and reached for the wrong prop.
  • @oxygenui/switch-audit-needs-now (error) — onAuditEvent without now. Also enforced in the types; the lint rule gives the better message.
  • Existing @oxygenui/no-absence-placeholder already covers a "—" in the state-word position.

The tests that carry the argument

Beyond the shared contract suite. Each of these exists because a specific claim in this brief is otherwise unverifiable — and per ENGINEERING §9, each asserts what a reader or a screen reader gets, not how it was built.

  • A rejected onCommit leaves the rendered value at the server's value, renders the error, and puts the failure into an assertive region containing the word "not changed".
  • Two toggles inside one pending window: the first response resolving after the second is discarded, and the final rendered value matches the second request.
  • A commit resolving in 40 ms still shows pending for minPendingMs, so the transition is perceptible rather than a flash.
  • Activating an unknown switch commits true; no sequence of user input reaches "unknown" from true or false.
  • Keyboard activation with confirm="hold" opens the dialog and never completes via a hold.
  • At data-ox-density="clinical" and size="small", the hit rectangle is still ≥24 px on both axes.
  • A readOnly switch is in the tab order and exposes its reason through the accessibility tree; a disabled one is not.
  • Every one of the eleven AbsentReason members renders a distinct word — a table-driven test, so a new member fails the build until it is given one.
  • Under prefers-reduced-motion, no element is left mid-transition: the revert still ends at the server's value with the error visible.

Rejected ideas, risks, open questions

Considered and rejected

rejected

A third click position for unknown

Lets a user un-ask a question. The correction for a wrong answer is a new answer with a provenance, never an erasure. §07.

rejected

Drag-to-toggle

SC 2.5.7 Dragging Movements requires a single-pointer alternative, and inside a scrollable list on touch a horizontal drag fights the scroll container. Click and hold cover the same ground without the conflict.

rejected

A scope prop — "this encounter" vs "the chart"

Genuinely important information, and it is prose. It belongs in description, where it can be phrased for the specific toggle, rather than in an enum that will be wrong for the fourth product that uses it.

rejected

Undo toast instead of confirmation

Undo requires the user to notice. The failure being prevented is a tap by someone who has already looked away. Kept as a complement for reversible instant commits; never as the substitute. §05.

rejected

Runtime-derived tone

A component that can escalate its own colour will be escalated for emphasis, and CONTENT.md §3's interruption budget is spent. Tone is fixed at design time by the person who knows what the toggle does. §06.

rejected

A master switch with an indeterminate state

"Some children on" and "not asked" are different facts and one control cannot hold both. The group header is a checkbox. §09.

rejected

A vertical switch

Proposed for narrow bedside columns. A vertical track reads as a slider, and a slider implies a range. There is no clinical surface that needs this badly enough to spend that ambiguity — chip and micro both solve the space problem without it.

deferred, not rejected

Voice and badge-scan confirmation

Both are real: sterile environments cannot touch a screen, and badge-scan is already the second factor in medication administration. Neither is a component concern — they are authentication transports. confirm="countersign" should accept a pluggable verifier so a badge scan can satisfy it without the Switch knowing what a badge is.

rejected

stale resolving itself

Last-write-wins discards the reasoning of whoever typed first; first-write-wins discards a more recent deliberate change. A conflict between two clinicians is not a merge problem, and a component that picks a winner is a component that loses clinical intent silently. §11.

The phase machine gets bypassed — teams use onChange and roll their own High Make the promise contract the documented default in every example and the meta.ts usage block. Consider a warn-level lint rule for onChange without commit, once there is real usage to learn from.
The antd compatibility claim drifts on the next antd major Medium A props-parity test table checked into the repo, plus a note in the release checklist to re-run the §18 measurements on each antd major. Cheaper than a peer dependency, and it fails loudly.
Hold-to-confirm is disliked in the field and quietly disabled everywhere Medium It is already a token (--ox-switch-hold-ms: 0), so disabling it is supported rather than a fork. If usage data says nobody keeps it, it is one prop value to deprecate.

Open questions — for you

1 · Does ADR 0010 land as proposed?

"Primitives are antd-compatible and antd-free; compound clinical organisms may wrap antd where they name the expensive behaviour they are inheriting." That rule decides the Switch and also every form primitive after it. If you would rather wrap antd here, the design above still holds but §07's third state and §04's phase machine both become substantially more expensive, and the registry channel closes for the form family.

2 · Is SwitchList in scope for the first release?

It is where switches actually live, and it is 2 days. Cutting it ships the primitive sooner and leaves every consumer to rebuild the group live region — which is the part they will get wrong.

3 · Which comes first, Switch or Checkbox?

§17 sends four situations to a checkbox and a radio group that do not exist yet. Shipping the Switch alone means shipping a docs page that points at nothing. A minimal Checkbox with indeterminate may be the more honest first primitive.

4 · Is there a real surface to validate against?

The precautions panel in §09 is invented from general clinical knowledge, not from a customer's screen. If zowork/formbuilder or an existing product has a real settings surface, the state-label presets and the absence taxonomy should be checked against it before P4 fixes them in an intl catalog.
