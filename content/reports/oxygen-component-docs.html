01
Where this lands

Executive summary

A component page has one job in a sales conversation: put the component on screen before the reader decides whether to keep reading. Today it takes 962 pixels of prose to get there, and on the heaviest page 1,187. That is the whole problem, and almost everything else on this list follows from it.

962pixels of prose before the first live component
42%of props have no description — 235 of 555
14/27components have no worked example at all
26,394pixels — the tallest component page

The four findings that matter

  1. The demo is buried, and it is the thing that sells. A client reacts to a working component in about two seconds. On every page today they meet a 160-word paragraph first — good prose, wrong place.
  2. The demo shows everything at once, so it shows nothing. Six results side by side, four tabs, and then eighteen state names as a flat list of strings. There is no path through it and no way to see the states that are named.
  3. The API table is unreadable and, on more than two fifths of props, empty. Descriptions are crammed into the name column. 235 of 555 props have no description — 63 on date-picker, 25 on switch, 21 of copilot's 24.
  4. None of it is generated. component-preview.tsx is 3,316 hand-written lines. Every new component makes the file longer and the pages less alike.
The proposal in one line Put a state browser at the top of every component page — one component on a calm stage, a rail of its states grouped by kind, and the reasoning and the code changing with the selection. It answers the demo problem, the eighteen-strings problem and the “what is this actually for” problem with one control, and §9 shows how to generate it from metadata that already exists.

The writing does not need replacing. It needs reshaping — and one thing added that no competitor could write: a sentence per state saying what that state means clinically. §8 shows the before and after.

02
Be honest about the reader

What actually happens on this page

Four people open a component page, and only one of them is going to read it. Designing for the reader who reads is how documentation gets long and unhelpful.

WhoTime hereWhat they doWhat kills it
The client
in a demo call		5–20 s Looks. Decides whether this feels like software built by people who have seen a hospital. Never scrolls past the first screen. A paragraph. Any paragraph.
The engineer2–10 min Copies the install line, scans the props, finds the one example closest to their case, leaves. A props table with no descriptions; no example for their case.
The clinical reviewer10–30 min Reads the states and asks whether each one is handled correctly. This is the person who approves or blocks adoption. States listed as bare strings with no clinical meaning attached.
The answer engineno JS Quotes one passage. Usually “when to use it”, or a state definition. Content that only exists after hydration.
The reordering this implies The current order — rationale, then preview, then variants, then usage — serves the reader who reads first and the reader who looks last. Invert it. The component goes at the top, because three of these four readers are looking rather than reading, and the fourth quotes a passage that works just as well below a demo as above one.

This is not an argument for less prose. The rationale on /components/result-value is the best writing on the site and it should stay in full. It should stay in full underneath the thing it is describing.

Why this shape and not a playground

A props playground — the Mantine model — lets a reader assemble any combination, most of which are not interesting and some of which are not reachable. A state browser is the inverse: it shows the combinations the team considers worth understanding, each one named, each one with a reason. For a clinical library that is the right trade, because the value is in knowing which states exist at all.

The URL carries the state

?state=restricted. A colleague opens exactly what you were looking at, and a support answer can link to a state rather than describe it.

02

The code is the selection

The panel shows the props that produce what is on screen — not a generic snippet. Copy gives you a working example of that state, not of the component in general.

03

The reasoning travels with it

One sentence saying why the state exists. This is the content a clinical reviewer is actually reading for, and it currently exists nowhere on the site.

Cost, honestly The control itself is small — radio inputs and sibling selectors, no JavaScript, as demonstrated above. The real cost is writing 312 state sentences, one per state across the catalogue. At the quality shown here that is perhaps three focused days, and it is the highest-value writing available to this product.

The rule: if a component's claim is about how it behaves inside something else, the demo has to contain the something else. ChartHeader's claim is that it stays legible above a scrolling record and collapses to a safety bar rather than to a name. Neither half of that is visible in isolation.

Drawing the host at reduced opacity keeps the eye on the component while making the context legible. An Isolated toggle returns the component alone for anyone who wants to inspect it — the two modes cost one boolean.

This is already half-built component-preview.tsx already contains HostChart, AppBehind and InstrumentStage wrappers doing exactly this for a handful of components. The work is not inventing the pattern — it is making it a declared property of the component rather than a decision taken per demo.

The fixed shape

Every prop description follows the same three slots, in the same order. That is what makes forty props scannable — a reader learns the shape once and then reads only the slot they need.

What it does
One sentence, bolded. Present on every prop without exception.
If you omit it
The actual behaviour. Present on every optional prop.
Why
Only where the default is surprising or the constraint is a safety decision. Absent more often than present, which is what keeps it worth reading.
One new column, worth its width For clinical components, a harm-if-wrong grade — the artefact a VP of engineering screenshots into an internal slide. Most of the input already exists in domain.safety; what it needs is a per-prop link.

And the 155 missing descriptions

These cannot be generated, and they should not be. But they can be required: a public prop with no doc comment should fail pnpm gen --strict the same way a component without a story already does. Turn the gate on with a grandfathered allowlist, and the list shrinks instead of growing.

The part that cannot be generated

The writing standard

The prose on this site is better than the prose on any competitor's. It is also, consistently, in the wrong shape — long where it should be layered, and absent exactly where it would be most valuable.

Three rules, each shown against real copy from the shipping site.

Rule 1 — lead with the claim, then enumerate

Nineteen of twenty-seven openings are over 120 words in one block. The fix is not to cut them; it is to lift the load-bearing sentence out and let the rest breathe underneath.

Why. This is the highest-value writing missing from the site. It is what a clinical reviewer reads to decide whether the component is safe, it is what an AI answer engine quotes, and no general-purpose library can write it.

The voice, which should not change

Short declaratives. Concrete clinical nouns. No hedging, no marketing verbs, and a willingness to say what the component refuses to do. “An annotated wrong number still gets read as a number.” — that sentence does more work than a paragraph of features, and it is already on the site.

Keep doing

Naming the hazard, not the feature

“The hazard is the reader's memory of it.” Every safety claim on this site is framed as the specific bad outcome it prevents. That is what a clinical reviewer is scanning for.

Stop doing

Stacking four hazards into one sentence

The rhythm is excellent and the density defeats it. One hazard per sentence; the list is already doing the accumulating.

A house rule worth writing down Nothing on a component page may claim a behaviour that no test asserts. The site already lives by this; making it explicit is what lets the accessibility section print a test name beside every claim, which is the single most credible thing a documentation page can do.
09
So it stays fixed

Generate it, don't write it

Everything above is undone within a year if the pages stay hand-written. The machinery to prevent that is already half-built.

What already exists packages/component-meta validates a schema with Zod. scripts/gen/ emits six artefacts and pnpm gen --check fails CI when they are stale. Props are already extracted from TypeScript rather than written by hand. Every state in the state browser above is already declared in *.meta.ts.

11
Do not touch

What I would not change

A list of things that are already right, because the fastest way to lose them is a redesign that does not know they were decided.

  • Anchored sections that never unmount. They look like tabs and behave like anchors, which keeps find-in-page, deep links and crawlers working. This is a deliberate decision recorded in the codebase and it is correct.
  • Props extracted from TypeScript. A hand-written prop table drifts silently and is then worse than none. The extraction is the reason the types and the docs cannot disagree.
  • Structured data serialised from the same metadata the page renders. A rich result describing a component page that says something else would be worse than no rich result — the code comment saying so should be preserved along with the behaviour.
  • The .instrument bezel around live demos. It reads as hardware, it is consistent across the site, and the state browser is designed to sit inside it.
  • The clinical fixtures. Okonkwo, Marsh, Boateng, Adeyemi — plausible, diverse, and over-representing the hard states. Every demo in this report reuses them rather than inventing new ones.
  • The voice. §8 reshapes it and adds to it. It does not rewrite it, and neither should anyone else.
