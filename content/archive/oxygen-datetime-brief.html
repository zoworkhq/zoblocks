01

What we are building, and why it cannot be a themed date picker

One value type, three engines, one component with fourteen variants. The bet is that healthcare temporal input is a different problem, not the same problem in a different colour.

A date picker is a solved problem. Every serious component library has one, several are excellent, and rebuilding one for a healthcare palette would be a waste of a quarter. The reason to build this is that the calendar is the least important part of healthcare temporal input, and every library that treats it as the centre gets the rest wrong.

Count the times a clinician touches a date in a working day. A therapist running eight sessions enters a date of birth at intake, a service date on every note, a start time and a duration on every session, a signature timestamp on every signed note, a follow-up date on most, and — perhaps twice a week — actually picks an appointment from a calendar. The calendar is the rare case. The common case is a person who already knows the value and needs the software to get out of the way.

Legacy EHR software fails this by making every temporal field the same field: a text input with a calendar button, a locale-ambiguous mask, and one validation state called “error”. The cost is not aesthetic. It is eight keystrokes turned into four clicks, a date of birth entered by scrolling back four hundred and eighty months, a session that silently moves its end time, and a retrospective note that is refused because the validator cannot tell “impossible” from “unusual”.

The thesis

Healthcare temporal input is four distinct jobs — recall, choose, construct, witness — and conflating them is why EHR date fields are bad. Each job wants a different primary control, a different keyboard model, a different validation posture and a different definition of done. A system organised around the four is simple at each point of use and still covers a twelve-week multidisciplinary treatment series.

What is different about this one

01
The calendar is a fallback, not the default
Only one of the four jobs wants a calendar as its primary control. The other three open with a keyboard-first field, and the grid is an escape hatch reached deliberately.
02
Three validation tiers, not one
Error blocks, conflict warns, advisory informs — with three different ARIA treatments. A retrospective session date is not an error and must not be announced as one.
03
The driver of a derived value is visible
Start, end and duration are three values with two degrees of freedom. Which one is held and which is computed is rendered on every edit, not inferred by the user from what moved.
04
Availability is data, never a fetch
ADR 0009 forbids network calls in component source. That constraint turns out to be the correct architecture anyway: the component owns optimistic state and reconciliation, the host owns the round-trip.
05
Precision is a type, not a flag
A birth date and a midnight timestamp are different kinds. Storing the first as the second is the single most common temporal defect in healthcare software, and it is unrepresentable here.
06
Nothing reads the wall clock
“Today”, “5 days ago” and “Use current time” all read an injected clock. Required by ENGINEERING.md §9; it is also what makes the whole surface deterministically testable.
Market position, checked

Terra UI, Cerner's React component library, was archived on 28 June 2024 along with the rest of the Cerner GitHub organisation — the only serious healthcare component library, gone. The FHIR-React packages are Material-era resource viewers. Behavioural health has no component library on page one of any search we ran. This component is the strongest available proof that the category is being occupied rather than competed for, because scheduling is the workflow every buyer already knows is broken in their current system.

02

The four temporal jobs

The spine of the whole system. Every one of the twenty-six scenarios below is one of these four, and knowing which one settles most design arguments before they start.

Recallthe user already knows the value
Date of birth, service date, admission date, medication administered time, incident time. The value exists in the world — on a wristband, in a person's memory, on a paper form — and the only job is to accept it in as few keystrokes as possible and reject what is impossible. Primary control: a segmented keyboard field. Calendar: a deliberate fallback, opened on the year pane. Done when: eight keystrokes have landed.
Choosethe system knows the options
Appointment slot, next available, provider availability, room booking. The user cannot know the answer; the system's knowledge of who is free is the entire product. Typing is nearly useless here. Primary control: a slot grid over a day strip. Keyboard: arrow navigation across a grid. Done when: an option is selected and still valid at save.
Constructthe user is building a structure
Session start + duration + end, recurrence rules, group series, treatment blocks. The value is not an instant but a small algebra with derived members, and the failure mode is a value that recomputes without saying so. Primary control: the driver, whichever it is. Every derived member is labelled derived. Done when: the plain-language summary reads correctly.
Witnessthe value is an assertion about the past
Now-stamping, signature time, note creation, retrospective documentation, countersignature. Convenience matters less than provenance: who asserted this, when, and against what clock. Primary control: a one-press stamp with a one-press undo. Never a confirm dialogue. Done when: the stored instant carries its zone.

What the split predicts

A framework earns its keep by making correct predictions before you have built anything. This one makes four, and all four contradict how mainstream date pickers behave:

PredictionMainstream behaviourWhy the split gets it right
A DOB field must not open a calendarCalendar button, opens on the current monthDOB is recall. The user knows the answer; a calendar is 480 months of navigation to enter something they could type in eight keystrokes.
“Use current time” needs undo, not confirmEither silently overwrites, or a modal confirmWitness. A confirm in front of a one-press action is trained through in a week; an undo after it is not, and it preserves the manually entered timestamp.
Changing the start time must not silently move the endEnd moves, or does not, with no signal either wayConstruct. The user asserted one of the three; which one survives an edit is information they need and currently have to discover by experiment.
A slot that was free 30 seconds ago may not be free nowOptimistic selection, generic error at saveChoose. The system's knowledge is the product, so its staleness is a first-class state, not an exception.
The corollary that matters commercially

Only the choose job needs availability, conflicts, holds or recurrence. Roughly four-fifths of temporal fields in an EHR are recall or witness, and those need less component, not more. A system that cannot render a fast, plain, boring date field is not a scheduling system with extra features — it is a scheduling system nobody will use for anything else.

04

Component architecture

Three headless engines, and one component with fourteen variants. Not eighteen components — the merge is the argument, and it goes further than antd parity alone would take it.

Layer 0Engines. No React, no DOM, no I/O. datetime.ts, availability.ts, recurrence.ts — shipped as one registry item, datetime-core.
Layer 1Parts. Eleven presentations in lib/datetime-parts.tsx, each a real component, separately rendered and separately tested.
Layer 2The front door. DatePicker — a variant union of fourteen and a dispatch, nothing else.

Why one component rather than eighteen

The first draft of this section proposed eighteen components across four layers, and the merges it argued were all sound as far as they went: antd parity collapses MonthPicker, YearPicker, DateTimePicker and the range variants into two entries, because antd expresses every one of them as picker plus showTime. Shipping them separately would break the parity promise on day one.

What that reasoning missed is that the same argument keeps going. A clinician does not shop for a “birth date field”. They reach for the date control, and it has to behave differently in fourteen places: a service date they already know, an appointment they have to be shown, a birth date that wants an age beside it, a session that is three numbers with two degrees of freedom, a course of treatment that is a rule rather than a date, and a signed timestamp that is a legal instrument.

The merge is the thesis, restated as packaging

Eighteen catalogue entries hide the thing that makes these a system — that every one of them shares a value space, a keyboard model and an accessibility contract — and they make a reader choose between components before they have understood the choice. §2's four jobs are an argument that this is one problem with four faces. Shipping it as eighteen products argues the opposite in the only place a buyer actually looks: the catalogue.

So the surface is <DatePicker variant="…" />, and variant is the front door. Tabs made the same call for the same reason: eleven skins and four semantic modes, one component, because the claim being made is about sameness.

What a dispatch has to be careful about

A variant prop is an invitation to write a component that is a switch statement standing in for design. The guard is structural: every behaviour lives in the part it belongs to, in lib/datetime-parts.tsx, and the front door is dispatch and re-export and nothing else. That is what stops it becoming the place fourteen variants grow fourteen different answers to what Escape does. The parts are exported by name as well, so a host that chose at design time writes <SessionTimeField> rather than passing a string.

The one parity conflict, and the recommendation

antd's picker value type is a Dayjs object; alternative libraries are supported through generatePicker<T>(config). Matching that literally would put a date library in the graph of every form component — precisely the outcome ADR 0010 exists to prevent, and a standing antd issue shows the ecosystem has not settled on Temporal either. Recommendation: match the API surface, not the value type, and ship a generatePicker-shaped adapter factory so a Dayjs codebase converts at the boundary. Divergences must be listed under limitations in component metadata; this is the first entry and the most consequential. See §20.

What the packaging costs, and what pays for it

A union of fourteen prop types means the type checker sees their intersection — three props — so the generated documentation had to learn to document each part in its own right rather than the dispatch alone. That is a real cost and it was paid once, in the generator. What it buys is a catalogue entry a reader can find, one page where the shared contract is visible, and a component that cannot drift into fourteen inconsistent keyboard models because there is only one of it.

05

The core date and time controls

Every figure below is live. Click into a field and type — the keyboard path is the one being demonstrated, and the mouse is the fallback.

The dot under today, and the diagonal on a closed day

Two rules from ENGINEERING.md §6 do real work in this grid. Colour never carries meaning alone, so today is a dot as well as a weight, and an unavailable day is struck as well as dimmed. And every cell's accessible name is the whole date plus its state — “Wednesday, August 26, 2026, 8 times available”, not “26”. A grid of bare numerals is navigable and useless.

The ambiguity the parser refuses to resolve

Typing 9 in a 12-hour locale is genuinely ambiguous, and the prototype's parser returns { h: 9, mi: 0, ambiguous: true } rather than guessing. A picker that quietly resolves it to 9 AM will, on some ward, turn a 9 PM discharge into a 9 AM one. The component keeps the meridiem segment unfilled and the value incomplete until the user says which.

06

Date of birth

The highest-volume temporal field in healthcare, and the one general-purpose pickers serve worst.

AGE

Rendered, not decorative

The age is the user's proof-read. A transposed year is invisible in 07/18/1968 and screaming in 58 years old. Under two years it reads in months, under four weeks in days — a paediatric chart that says “0 years old” for a four-month-old has discarded the only number that mattered.

UNKNOWN

Absence is stated, never punctuated

CONTENT.md is normative and lint-enforced: not —, not N/A. An unrecorded DOB renders “Not recorded” and carries a FHIR data-absent-reason, exactly as Switch carries its third value. The same argument as ADR 0010: a control that cannot distinguish “no” from “nobody asked” is lying.

ESTIMATED

A partial date is a real date

FHIR permits YYYY and YYYY-MM for Patient.birthDate. Homeless services, unaccompanied minors and forensic intake all produce them. Coercing “born around 1962” to 1 January 1962 invents a fact that will be read as precise for the rest of the record's life.

VALIDATION

Two rules, both hard

A future birth date is impossible and blocks. An impossible calendar date — 31 February, 30 February in a leap year — is unreachable by construction, because the segments are bounded and the day is checked against the month. The prototype's parser rejects it rather than clamping.

The two-digit year trap, stated rather than inferred

Typing six digits into a DOB field is common and the sliding window that interprets them is the sharpest edge in the component. 62 is 1962 for a patient and 2062 for nobody; 15 is 2015 for a paediatric patient and 1915 for a centenarian. The prototype uses a fixed pivot at 30 and the pivot is a prop, defaulted per-field rather than globally, because the correct answer differs between a paediatric intake and a geriatric one. Never inferred from the current year.

WCAG 2.2 SC 3.3.7 — Redundant Entry, and why it lands here

A Level A criterion added in WCAG 2.2: information previously entered must be auto-populated or available for selection. Intake flows ask for a date of birth two and three times — registration, insurance, consent. BirthDateField therefore accepts a suggested value that renders as a one-press fill rather than a pre-filled field, because silently pre-filling a legal attestation is a different defect.

07

Session, duration and the visible driver

Three values, two degrees of freedom, and the design problem that gives this component its name.

The rule, stated as a machine

type SessionState = {
  start: OxTime;              // the anchor, always asserted
  end: OxTime;                // derived when hold === "duration"
  endDayOffset: 0 | 1;        // crossing midnight is a value, not an error
  durationMin: number;        // derived when hold === "end"
  hold: class="c-s">"duration" | class="c-s">"end";   // what the user last asserted, and what survives
};

// Three transitions. There are no others.
setStart(s, t)      // keeps `hold`. Hold duration -> the session slides.
                    //               Hold end      -> the session stretches.
setEnd(s, t)        // hold becomes "end";      duration is recomputed
setDuration(s, n)   // hold becomes "duration"; end is recomputed
DEFAULT

Duration is held, end is derived

A clinician books “a 53-minute session”, not “9:00 to 9:53”. So moving the start slides the whole session by default, which is what a schedule shuffle means. Asserting an end explicitly flips it.

MIDNIGHT

An end at or before the start is a crossing

11:30 PM to 12:30 AM is a crisis-line shift, not a typo. Refusing it teaches staff to enter the wrong date to get past the validator — which is how you lose the real data. §7 figure 15.

BUFFER

Organisation-configured, not a field

The shaded tail on the tape is a 7-minute documentation buffer. It affects what the next slot can be and it is shown, but it is not a control, because nobody sets it per appointment.

BANDS

Data, not a judgement

The band readout is passed in by the host. The component never asserts a code — ADR 0009 prohibits a component deriving a clinical or coding recommendation. It renders the band the value falls in, and the org supplies the bands.

Why every behavioural-health schedule in the United States has a 53 on it

It is not an arbitrary number and it is not a rounding artefact. Under the AMA's CPT time rules, 90832 covers 16–37 minutes, 90834 covers 38–52, and 90837 — the higher-reimbursing individual psychotherapy code — requires 53 minutes or more. 53 is the cheapest safe clearance of that threshold. This is exactly the kind of fact a general-purpose duration picker has no reason to know and a healthcare one is negligent to ignore: it is why the preset list is organisation configuration rather than a tidy 15/30/45/60 ladder.

08

Availability, slots and conflicts

The only part of the system that needs to know anything about the world — and the part a component library must be most careful not to own.

The constraint that turned out to be the architecture

ADR 0009 forbids component source from calling fetch, opening a WebSocket, or emitting telemetry. That was written as a supply-chain rule, and it removes the option of a component that loads its own availability. It is also, independently, the correct design: availability is data with an age, and a component that fetches its own hides that age from the application that must reconcile it. The component owns presentation, optimistic state and recovery; the host owns the round-trip.

Slot lifecycle — the state machine the host drives

type SlotState =
  | { kind: class="c-s">"available" }
  | { kind: class="c-s">"held";      by: class="c-s">"me" | class="c-s">"other"; expiresAt: OxInstant }
  | { kind: class="c-s">"selecting" }                      // optimistic, local only
  | { kind: class="c-s">"confirming" }                     // host round-trip in flight
  | { kind: class="c-s">"booked" }
  | { kind: class="c-s">"rejected";  reason: string; alternatives: Slot[] };

// The server is authoritative and may always say no. `rejected` therefore
// carries alternatives, so the recovery path is a choice rather than an
// error message. A generic "that slot is no longer available" toast makes
// the user start the whole task again.

type AvailabilitySet = {
  asOf: OxInstant;         // rendered when stale, not hidden
  staleAfter?: number;     // seconds; the component dims and offers refresh
  slots: Slot[];
  exhausted: boolean;      // true empty vs "we stopped looking"
};
Buffers, and why they are not a field

A 7-minute post-session buffer, a 15-minute new-patient pre-buffer and a room turnover allowance all change which slots exist. They belong in the AvailabilitySet the host computes, not in the picker — the picker renders the resulting gap and names it if asked. Exposing buffer as a control on an appointment form gives every front-desk user the ability to break the clinic's own schedule policy one appointment at a time.

09

Recurrence

Behavioural health does not book appointments; it books courses of treatment. The unit is the series.

Standards in, standards out

The rule is emitted as a real RFC 5545 RRULE with a DTSTART;TZID=, so a series round-trips with iCalendar, with FHIR Timing, and with every downstream calendar the customer already runs. We implement a named subset and refuse the rest:

SupportedRefusedWhy the line is here
FREQ=DAILY|WEEKLY|MONTHLYYEARLY, HOURLY, MINUTELY, SECONDLYNo behavioural-health workflow produces them. An annual review is a task, not a series.
INTERVAL, COUNT, UNTIL—All three are in constant use: “every 2 weeks”, “for 12 sessions”, “through 30 November”.
BYDAY (weekday list)BYDAY with numeric prefixes beyond BYSETPOS“Tue and Thu” is the workhorse. “The 3rd-to-last Wednesday” is not a real request.
BYMONTHDAY, BYSETPOS (1st–4th, last)BYYEARDAY, BYWEEKNO, WKST edge semanticsMonthly injections and “first Monday” groups need the former. The latter change expansion in ways we cannot test honestly.
EXDATERDATE, nested RRULEFacility closures are exclusions. Ad-hoc additions are separate appointments, and modelling them as part of the rule makes the series unreadable.
A rule we cannot expand is a rule we must not pretend to

parseRRule returns a discriminated result: { ok: true, rule } or { ok: false, unsupported: string[] }. An imported series carrying BYYEARDAY renders as a read-only rule with its original string and the note that this application cannot edit it — never as a silently truncated rule that expands to the wrong dates. The failure mode we are avoiding is a twelve-week treatment plan quietly losing four sessions on import.

Conflict detection across a horizon is the hard part, and it is the host's

Checking twelve future Tuesdays against a clinician's calendar, a patient's other appointments, a room and a payer authorisation is a server query, not a client computation. The component's contract is narrow and testable: it expands the rule, hands the host a list of candidate intervals through onExpand, and renders whatever verdicts come back. It does not know what a conflict is.

10

Time zones and daylight saving

Mostly invisible, entirely load-bearing. The rule is that complexity appears only when the zones actually differ.

Three rules that prevent the classic defects

01
Store the instant and the IANA zone, never the offset
-04:00 is correct for half the year. A recurring appointment stored with an offset is wrong for roughly twenty-three weeks of every year, and the bug surfaces as “everything moved an hour” on a Monday morning in November.
02
Recurring series preserve wall clock, not instant
A weekly 3:00 PM therapy stays 3:00 PM across a transition. Consequently the UTC instant moves by an hour, and every reminder, telehealth link and cross-zone participant time must be re-derived from the rule rather than read from a stored instant computed in September.
03
Never hand-compute an offset
Zone arithmetic reads the platform's IANA database through Intl, or through Temporal where it exists. A hand-rolled offset table is wrong the first time a government changes its mind, which happens several times a year somewhere.
Disambiguation is a policy, and the policy differs by job

The same non-existent local time means different things to different fields. Scheduling should refuse 2:30 AM on 8 March and offer 3:30. Documentation must treat it as a hard error, because it could not have happened. The engine therefore takes disambiguation: "reject" | "earlier" | "later" | "compatible" — the same four names Temporal uses — and the composite sets it per job rather than the application setting it once and globally.

11

Documentation, witnessing and the “now” problem

The other four-fifths of temporal fields. Faster, plainer, and far stricter about provenance.

PAST

Retrospective entry is normal

Notes are written after sessions. “5 days ago” is context, not a warning, and it renders with no colour weight. Blocking it produces the worst outcome available: staff dating notes to today to get past the validator, which corrupts the record it was protecting.

FUTURE

Four different rules, none of them the component's

DOB: never. Session documentation: suspicious, warn. Discharge date: permitted, it may be planned. Appointment: expected. These are futurePolicy on the field, supplied per workflow — a generic date component that hardcodes any one of them is wrong three times out of four.

NOW

One clock, injected — as a prop

now is a prop on every variant that needs one. ENGINEERING.md §9 forbids reading the wall clock to decide what to render, so this is required rather than preferred, and it is what lets every figure in this report render identically next March. A ClockProvider and a useNow() hook were the first design and were dropped: a context is one hook call away from a component that re-renders on a tick, which is the determinism this rule exists to protect.

PROVENANCE

Who stamped it, and against which clock

A witnessed value carries the actor and the zone. The component surfaces both in read-only mode; it does not invent them, and it never writes them itself.

What a documentation field does not get

No availability, no conflicts, no recurrence, no holds, no timezone pair. A clinician entering a session timestamp should not load, see, or tab through the machinery required to schedule a twelve-week multidisciplinary series. That is the progressive-disclosure claim in §2 stated as a bundle boundary: DateField and ClinicalDateTime import temporal-core and nothing else.

13

Light and dark

Both themes are the same markup and the same tokens. If re-theming needed a component edit, it was never a system.

The contrast gate is a build step, not a review note

Every new colour pair is added to the contrast gate in the same pull request that introduces it — a pair the gate does not name is a pair that is not checked. This component introduces pairs on the selected day, the held slot, the derived badge and the range fill. All four are checked in both themes and in forced-colours, where selection falls back to Highlight/HighlightText with forced-color-adjust: none so it survives a user's own palette.

The held-slot countdown in §8. Internationalisation

Announcements: what is said, and how loudly

The month change. Arrowing from 31 August to 1 September changes the whole grid; a screen reader that announces only the new cell leaves the user in a month they did not know they entered. The grid's aria-label carries the month and the change is announced politely, once. The derived value. When duration recomputes because the user typed an end time, the change must be announced — silently updating a field the user is not focused on is invisible to a screen-reader user and is exactly the defect the visible Held badge exists to prevent for sighted users.

Technical architecture

Headless engines, reducer-driven components, and three constraints from the existing engineering standard that do more design work than any preference of ours.

The split

packages/
  temporal-core/        // values, parsing, formatting, zone maths. No React.
  availability-core/    // slot model, holds, conflict detection, buffers. No React.
  recurrence-core/      // RRULE subset: parse, expand, describe. No React.
  datetime/             // React. Hooks + unstyled behaviour + styled defaults.

// Each engine is pure, synchronous and serialisable in and out. That is what
// makes 4,000 timezone and DST assertions cheap to run and what lets the
// server compute the same availability the client renders.

// The React layer is two exports per component, never a `headless` fork:
useDatePicker(props)   -> { fieldProps, gridProps, getCellProps, state, actions }

// A second styled implementation of the same hook is a supported outcome.
// A second BEHAVIOUR is not — that is how two components come to disagree
// about what Escape does.
STATE

One reducer per component, no exceptions

Session, range and slot selection are all small state machines with illegal states that must be unrepresentable. A range mid-selection, a slot held by someone else, a duration derived from an end that crossed midnight — each is a legal variant, not a null plus a boolean.

SSR

The hydration bug this design cannot have

Server and client render different times, and that is the classic Next.js date defect. Here nothing reads the wall clock, so `now` arrives as a prop from the server and both renders agree by construction. Zones are IANA identifiers, never resolved from the browser during render.

SUSPENSE

Availability is a prop, so it suspends where the host puts it

The component has no data-fetching boundary to place. A server component can resolve the AvailabilitySet and pass it down; a client one can stream it. Neither changes the component.

PERF

Where the traps actually are

Not in rendering 42 cells. In re-deriving disabled predicates for every cell on every keystroke, and in expanding a recurrence rule inside render. Both are memoised on the engine side against integer day numbers, which is why dates are integers here rather than objects.

Security and telemetry — architectural, not a badge

The decision

Own the value types. Borrow the arithmetic. Depend on nothing. Values are plain, serialisable objects — no class, no Date, no wrapper. Civil-calendar arithmetic is integer day maths, which is exact and about forty lines. Zone conversion and formatting read the platform's own IANA database through Intl.DateTimeFormat, which is not reimplementing tzdb — it is querying the copy the operating system already updates. Where globalThis.Temporal exists, a native adapter replaces the Intl path transparently. Revisit trigger, named now: the first Safari stable release that ships Temporal. At that point the internal engine swaps and the public value types do not move — which is the entire reason for owning them.

Phasing — and what actually happened

All four waves are built. They were built in this order and the order held, so it is recorded rather than rewritten — but the packaging changed at the end, and the phasing is the place that shows why the change was cheap. Each wave added variants to a component that already existed rather than new entries to a catalogue, which is the practical argument for the merge in §4.

Wave 1
The recall path — the engine, field, time, calendar, picker, birth-date, readout
Needs no availability contract, no FHIR additions and no server. It is immediately useful to the clinical-note and assessment components already shipping, and it is the half of the system four-fifths of fields actually use.
Wave 2
The construct path — session, range, multiple
Still no server. This is the behavioural-health differentiator and the strongest single demo in the library.
Wave 3
The choose path — availability.ts, slots, scheduler, plus Slot/Schedule in packages/fhir
Was blocked on the availability contract settling, which was a product decision as much as an engineering one. It settled as data with an age: ADR 0009 forbids the network in component source, so there was never another shape available.
Wave 4
The series path — recurrence.ts, recurrence, series, group
Depended on wave 3's conflict contract. Highest effort, highest differentiation, smallest addressable set of buyers until the rest exists.
One thing the build got wrong, and it was a spec question

RFC 5545 applies COUNT to the RRULE and removes EXDATEs from the set it produces, in that order. A COUNT of 26 with three exclusions is 23 occurrences, not 26 ending three weeks later. The first implementation counted only kept dates toward COUNT — the kinder answer, and the wrong one, because it emitted COUNT=26 alongside those EXDATEs. Any conforming reader would have expanded a series ending three weeks earlier than the one on screen, and the screen is not the artefact the appointment reminders are generated from. Now conformant, with the tally naming all three numbers — dates in range, closures, sessions — so the difference is visible rather than resolved silently. If a programme wants twenty-six delivered sessions, that is a product decision, and it cannot keep exporting a bare COUNT.

The assumption with the largest downstream consequence

The whole system is organised on the claim that the four jobs are genuinely distinct and that recall and witness dominate by volume. If that is wrong — if the buyer's product is overwhelmingly a scheduling surface and documentation is somebody else's problem — then waves 1 and 2 are the wrong order, the primitive tier is over-invested and AppointmentScheduler should be built first with the primitives extracted from it afterwards. That is a product question about who the buyer is, and it is the same unresolved question as the behavioural-health bet in the healthcare-50 brief. It should be settled before wave 1, not during.

What is not in doubt

Three engines with no React and no I/O · plain serialisable value types with precision in the type · an injected clock · availability as data · three validation tiers · a visible driver on derived values · and a calendar that is a fallback rather than a default. Those six hold regardless of how the eight questions above are answered, and they are what makes this a system rather than a picker.
