A component page is not a page somebody writes. It is a projection of a schema. If a region of the page has no field behind it, that region is where inconsistency starts — so this standard defines the schema first and derives the page, the navigation, the search index, the internal links, the breadcrumbs, the structured data and the sitemap entry from it.

The component page mockup in §5 is rendered from a real instance of the proposed schema, not hand-drawn. Every region is annotated with the field that produced it. That is the argument of this document made executable.

01 · Executive summary

The consistency problem is an architecture problem, and half the architecture already exists here.

You have described the failure precisely: different components ending up with different layouts, documentation structures, previews and levels of detail. That does not happen because developers are careless. It happens because a documentation page is a blank file, and a blank file has no opinion.

The fix is not a style guide. A style guide is a document people are asked to remember, and at fifty components somebody stops remembering. The fix is to make the page a projection of structured data: the author supplies an implementation and a metadata object, and the system generates the page. Under that model inconsistency is not discouraged — it is unrepresentable, because there is no file in which to be inconsistent.

Half of this already exists in the repository

This is the most important thing in the document and it changes the size of the job. Oxygen already has defineComponentMeta(), a *.meta.ts per component, and a generator that emits six artefacts from it — the shadcn registry, the docs catalogue, TypeScript path mappings, the Tailwind source list, an agent manifest and the coverage gate. Props are already extracted from TypeScript rather than written by hand. pnpm gen --check already fails CI when anything derived is stale.

The one-sentence version

Adding a component should require an implementation, a metadata object and at least one realistic example. Everything else — page, navigation, breadcrumbs, related links, sitemap entry, metadata, structured data, search index, OG image — should be generated, and CI should refuse the component if the metadata is incomplete.

02 · Competitive research

What the best libraries do, what none of them do, and the category that was abandoned two years ago

I looked at what each of these actually does well rather than at what they claim. The useful finding is not in any single library — it is that the strengths are distributed and nobody has assembled them, and that the healthcare category specifically has been vacated.

LibraryWhat it genuinely does better than the restWhat it gets wrong, or does not attempt
shadcn/ui Copy-as-source distribution and the CLI. The install block is the first thing on the page and it works. Preview/Code as a two-state toggle rather than a tab bar is the right call — they are two views of one thing. No props playground at all. API tables are hand-maintained and visibly drift. No relationship graph. Search is name-only.

Synthesis · what to take

Four borrowings

Mantine's live props-to-code binding, made schema-driven so coverage is uniform. Radix's keyboard and ARIA tables, extended with a test id per claim. shadcn's install-first page order and CLI. Storybook's story-as-fixture, so a documented example is also a test input.

Synthesis · what nobody does

Three genuine gaps

A relationship graph. Nobody derives used in from imports, so nobody can show a primitive its own consumers. Domain documentation as data. Nobody conditions page sections on an industry field. An SEO contract. Nobody treats a unique primary keyword as a build-blocking constraint.

The category finding

Terra UI was archived on 28 June 2024

Cerner's Terra — the only serious healthcare React component library, and the top organic result for the category — was archived along with the whole Cerner GitHub organisation. The incumbent left and the search demand did not.

What actually ranks today, observed on the SERP

For healthcare React component library: an archived Terra, a repository literally named clinia-ui-legacy, a vendor-specific integration kit, and then agency content marketing (ReactJS for Healthcare Applications, Build a Low Cost Healthcare App). 03 · Information & URL architecture

Flat component URLs, nested hubs, and a redirect policy that treats a published URL as a promise

Component URLs are flat. Everything else nests.

The temptation is /components/behavioral-health/assessment-runner, because it looks organised. It is a mistake, for three reasons that all cost more than the tidiness is worth.

Categories change and URLs must not. Assessment Runner is plausibly Forms, Clinical or Behavioral Health, and the day somebody re-categorises it, a ranking URL 301s. Depth dilutes. A flat /components/* namespace concentrates authority on one directory. And a component has more than one parent — this one belongs to three categories, so any nesting picks a winner arbitrarily and creates two orphans or two duplicates.

PatternVerdictReasoning

Redirect policy

A published component URL is a promise

Once /components/x is public it is permanent. Renaming requires, in the same commit: a 301 from the old slug, an aliases entry so search still finds it, the old slug listed in redirects.json, and a changelog note. A rename without all four fails CI.

Deprecation never 404s. A deprecated component keeps its page, gains a banner naming the replacement, and is removed from the sitemap and from search — but stays reachable, because inbound links exist and breaking them is a self-inflicted ranking loss.

04 · Universal page anatomy

15 regions, in one order, every time

Order matters, and the research is unanimous on the first three: developers arrive wanting to know what it looks like, how to get it, and how to use it, in that sequence. Everything that follows is reference material, and reference material sorts by how often it is consulted.

Tabs, anchors or a hybrid?

Hybrid, and the choice is not cosmetic. Tabs that unmount their content — Preview/Code/API as real tabs — hide most of the page from Cmd-F, from the browser's own find, from deep links and from crawlers. Anchored sections in a single scrolling document keep everything addressable and indexable.

So: the section bar looks like tabs and behaves like anchors. Clicking scrolls and updates the URL hash; the active state is driven by an IntersectionObserver. The one genuine toggle is Preview ↔ Code, because those are two renderings of the same thing and only one can occupy the frame.

Three changes I made to your proposed order

When to use it moves above Usage. The question should I use this at all precedes how do I use it, and it is the section an AI answer engine quotes. Accessibility moves above Related, because it is reference material a developer returns to and Related is a departure point — departure points belong last. And Clinical becomes a distinct region rather than being scattered through the others, so a non-clinical component is visibly and structurally free of it.

The full fifteen-region table is the deliverable and lives in §19.

The rule that prevents fifty different pages

A region renders if and only if its schema field is populated, and it renders in the fixed order below. A component with no variants has no Variants section — it does not get an empty one, and it does not get to move Variants above States because the author preferred that. Order is not a parameter.

06 · Preview & playground

The preview is the product demo. It has to be honest about states, not just pretty in one.

Mantine's playground is the pattern to beat, and its weakness is instructive: the controls are declared per demo by hand, so some components have twelve knobs and some have none. Coverage is inconsistent for exactly the reason your components were inconsistent — it depends on the author.

The fix is that controls are schema, not markup. api.controls declares which props are knobbable, which widget each uses and what range it accepts. The playground is generated. A prop that should be knobbable and is not is a gap CI can see, because it can diff api.controls against the extracted prop list and warn on public props with no control.

Prop typeControlWhy, and the rule
booleanSwitchNever a checkbox. A switch reads as immediate effect, which is what this is.
union ≤ 4SegmentedAll options visible at once. Comparison is the point of a playground.
union > 4SelectWith the current value always rendered, never a bare placeholder.
number, boundedSlider + numeric readoutThe readout is required — a slider with no number cannot be reported in a bug.
stringText fieldSeeded from the fixture, never empty and never lorem ipsum.
token-valuedToken pickerSwatches from the actual token set, so an arbitrary hex is not even expressible.
data / resourceFixture selectorThe healthcare-specific one. Named fixtures — reyes-marcus, critical-potassium, part-2-segmented, empty-panel — so edge cases are one click, not a code edit.

Required in every playground

Nine affordances, non-negotiable

Reset · full-screen · theme toggle · density toggle · three breakpoint presets plus drag-resize · fixture selector · copy-state-as-props · deep-link-to-this-state · event log.

Deep link is the one people underrate: a support conversation becomes a URL that reproduces the exact configuration.

The healthcare requirement

Edge cases are first-class fixtures

Every clinical component ships fixtures for: normal, critical value, absent with a reason, restricted / Part 2 segmented, stale, and empty. These are the states the library exists for, so they are one click rather than something a reader has to imagine.

What the playground must not become

A configuration UI

If a component needs more than about nine controls to be understood, the component is too broad. The control count is a design signal and should be reviewed as one.

08 · API documentation

Extracted from TypeScript, never written by hand

Already solved here and worth protecting: props are extracted from TypeScript by scripts/gen/props.ts, and hand-writing a prop table is a lint error. A drifted table is worse than no table, because it is trusted.

Four additions this standard makes.

Filter, not search

An inline filter over prop name, type and description. At forty props, scrolling is the failure.

Expandable types

A complex union collapses to its name and expands in place. Never a wall, never a link away.

Version affordances

added 0.4.0 and deprecated 0.4.0 chips, generated from the type history rather than typed.

Deep-linkable rows

Every prop has an anchor, so a support answer can link to #prop-onItemRisk instead of describing where to scroll.

10 · Search, navigation & relationships

At 500 components, browsing dies and search becomes the product

At fifty components a sidebar works. At five hundred it is furniture. Search becomes the primary navigation, and search quality becomes a product feature rather than a utility.

Four ranked layers, in build order

Lexical — ship first Fuzzy over name, aliases, tags, category and prop names. A prebuilt index of roughly 40 kB for 500 components, shipped as a static asset. Answers patient card, PHQ-9, PulseStack. Zero infrastructure.
Capability — the differentiator Tags describe what a component does, not what it is called: virtualised, filterable, streaming, keyboard-first, offline-capable. This is what answers table with filtering, which name-only search cannot.
Workflow — the healthcare layer domain.workflows lets intake return the seven components that appear in an intake flow plus the pattern page that composes them. No competitor can answer this query.
Semantic — last, and only if measured Embeddings over description and rationale. Genuinely better for something for showing a patient's history over time. Also an inference cost and a latency risk. Gate it on measured lexical failure, not on enthusiasm.
Navigation architecture

Sidebar grouped by category with counts, but the command palette is the primary surface — ⌘K from anywhere, results with a thumbnail, and the install command copyable straight from a result without opening the page.

Persisted per user: recently viewed, favourites. Generated: new, updated, most-used. Filters for tier, status, framework, industry and capability, all reading closed vocabularies from the schema.

The relationship graph

Four edge types, and three of the four are derived. builtWith comes from imports; usedIn is its inverse; patterns comes from pattern membership. Only related is authored — and it is validated bidirectional, so a one-way relationship fails the build.

The same graph produces the internal-link structure in §16. It is one data structure serving navigation, discovery and SEO, which is why it must not be three hand-maintained lists.

14 · Consistency enforcement

How inconsistency is made structurally impossible rather than discouraged

You asked specifically how to prevent inconsistency technically rather than by asking people to remember. Six mechanisms, in descending order of how much they actually prevent.

1 · The strongest one

There is no page file to be inconsistent in

One template renders every component from metadata. An author cannot reorder sections, invent a heading or omit accessibility, because there is no file in which to do so. Everything else on this list is a backstop for what this cannot cover.

2 · Schema validation

Zod at author time, CI at merge time

defineComponentMeta() already validates on import, so a bad meta fails the typecheck before it fails a review. Extend the schema and the new fields are enforced the same day.

3 · Derived-artefact staleness

pnpm gen --check already does this

Regenerates everything and fails if the working tree differs. Nothing derived can drift, because drift is a red build. Seven new emitters inherit the guarantee for free.

4 · Closed vocabularies

Category, tag, workflow, framework, terminology

All enums. A new category requires a deliberate edit to the vocabulary file and a reviewer, which is the point — the alternative is forty near-duplicate free-text categories.

5 · Graph integrity

Relationships are validated, not trusted

related must be bidirectional. Every ref must resolve. usedIn is computed and a hand-written one is an error. A pattern claiming a component the component does not claim back fails.

6 · Visual regression

Seeded from api.states

The state list is not documentation — it is the VRT matrix. A state documented but never rendered has no snapshot, and no snapshot fails the gate. Documentation and tests cannot diverge because they are the same array.

Voice

Four rules

Second person for instructions, third for behaviour. Present tense — renders, not will render. Name the failure rather than praising the feature. British spelling in prose, US spelling in code and clinical terms of art (color, Behavioral Health) — inconsistent, and the alternative is renaming a category people search for.

Naming

Four names per component, one URL

Technical AssessmentRunner · Human Assessment Runner · Slug assessment-runner · Aliases the things people actually type. A creative internal name lives in aliases and marketing copy, never in the slug. Nobody searches PulseStack; they search recent patients.

Banned

Fails the content gate

Lorem ipsum · John Doe · Lorem Hospital · simply / just / easy · revolutionary · a description that restates the title · a prop description that restates the type · an example with fewer than three rows of data · any real patient name.

Terminology governance

This is the healthcare-specific half and it is not cosmetic. Patient, client, member, consumer and resident are not synonyms — they encode setting, funding and legal relationship, and using the wrong one signals to a behavioral-health buyer that you have not worked in their setting.

A <TerminologyProvider context="behavioral-health"> supplies the noun set, and the documentation exposes the same switch above every clinical example. Flip it and the demo data, the labels and the prose change together — Recent patients becomes Recent clients.

Two consequences. Every clinical component must take its person-noun from context rather than hard-coding it, which is a lint rule. And the switch is a genuine sales moment: a behavioral-health buyer sees their own vocabulary within five seconds of landing.

16 · SEO & discoverability architecture

An abandoned category with residual demand is the best SEO position there is

The competitive picture from §2 sets the strategy, and it is unusual: this is not a crowded keyword space to fight into. It is an abandoned category with residual demand. Terra UI was archived in June 2024; the FHIR React packages are Material-era resource viewers; and behavioral health has no component library ranking at all.

The correct posture is therefore topical authority over keyword volume — become the obviously-correct answer for a domain nobody is currently serving, rather than out-optimising anyone for a head term.

Read this before the plan is committed

The table below has no volume column, deliberately. I have no keyword tool on this machine and will not invent numbers that would then be used to prioritise. Intent and competition are SERP-observed and reliable; volume is not, and must be bought. Ahrefs or Semrush, one month, roughly $100–130, for the ~40 terms below plus competitor gap analysis against ui.shadcn.com, mui.com and the archived Terra domain. That is a wave-four prerequisite, not a nice-to-have.

Metadata generation

Title template: {title} — {primaryKeyword} | Oxygen UI, truncated at 60 with an editorial override that is logged. Description defaults to summary and is gated at 120–158 characters. Canonical is derived and asserted in CI, not assumed. OG images are rendered at build from the component's own preview.

The uniqueness constraint is the important one: two components may not claim the same primaryKeyword. That is keyword cannibalisation, and it fails the build.

Structured data — only where earned
SoftwareSourceCodeYesComponent pages. The page genuinely is documented source.
BreadcrumbListYesEvery page. Cheap, accurate, renders in results.
TechArticleYesPattern pages only — they are articles.
SoftwareApplicationNoThe library is not an application. Misuse risks a manual action.
FAQPageNoOnly if a page has genuine Q&A. Manufacturing questions for the rich result is exactly the abuse Google demoted.
Internal linking, generated

Every link comes from the relationship graph, so none goes stale. Component → related (6) → builtWith → usedIn → patterns → hub. Hubs link down to components; patterns link across. Every component must have at least three inbound internal links before it can reach Stable — an orphan page does not rank, and the gate makes that structural.

Programmatic SEO — the guardrail

A generated page may exist only if it has unique primary content, a distinct primary keyword and a reason a human would want it. Component × framework fails all three, so framework stays a tab. Component × pattern passes, because a pattern page has real composed content.

Rule: if a page's non-boilerplate content is under 300 words, it is noindex. Five hundred excellent pages, not five thousand thin ones.

AI answer engines are a different reader with the same fix

The instinct is to write for the model. Don't. The things that make a page quotable by an answer engine are the things that make it good: an explicit definition sentence, a stated use-when and avoid-when, real code, and a statement of what it does not do. Those are already required fields, so the AI posture is a by-product of the content standard rather than a separate workstream.

Three concrete additions: keep llms.txt current — it already exists here and is generated; make sure the definition sentence is the first sentence after the H1, not the fourth; and never hide primary content behind a tab that unmounts, which is the argument for anchors in §4.

Pages are static. The playground is the only client island and it hydrates lazily on intersection — a reader who never touches the controls never pays for them.

The expensive components

Grids, charts, WebGL and AI demos are dynamically imported and gated on intersection, with a skeleton matching the final layout so nothing shifts. Syntax highlighting is done at build time — shipping a highlighter to the browser to colour a static snippet is the most common doc-site performance mistake.

An ambient-capture demo requests no microphone permission until the reader presses record, and says so before it does.

Mobile is a different document

Sidebar → sheet behind the ⌘K button. Section bar → horizontally scrollable with the active item scrolled into view. Props panel → bottom sheet at two detents, so preview and controls are visible together. API table → definition cards, never a horizontally scrolling table. Code → collapsed to eight lines with an expand.

Preview resize handles disappear below 768 px; a drag handle on a touch device is a WCAG 2.5.7 problem and a usability one.

Motion, inherited

The four durations and two curves from phase two, unchanged. Doc-specific: tab underline slides (140 ms), preview crossfades on prop change (200 ms) rather than flashing, copy shows an inline checkmark for 1.4 s, and theme switches transition background-color and color only — transitioning everything is what makes a theme toggle feel cheap.

19 · The master template

The deliverable. Every component from here inherits this.

Fifteen regions, one order, every component. A region renders if and only if its field is populated, and the order is not a parameter. The two conditional regions are conditional on data — api.variants being non-empty, domain.industries containing a clinical value — not on an author's judgement, which is the whole point.

Against your proposed order I made three changes. When to use it moves above Usage, because the question should I use this at all precedes how and it is the section AI answer engines quote. Accessibility moves above Related, because it is reference material a developer returns to and Related is a departure point — departure points belong last. And Clinical is a distinct region rather than scattered through the others, so that a non-clinical component is visibly, structurally free of it.

20 · Implementation plan

Five waves, and the one that must come first

1
Wave one · the schema · ~2 weeks

Extend component-meta and validate it

Add the 24 new fields, the closed vocabularies, the graph validation and the length caps. Backfill the eleven shipping components. No visible change — and everything after this depends on it.

Done when: pnpm gen --check is green with the new schema and the eleven existing components pass validation.

2
Wave two · the template · ~3 weeks

One page, generated, replacing the current one

The fourteen regions, the section bar, the right rail. Migrate the eleven existing pages onto it and delete the bespoke ones. Ship the a11y panel and the API filter.

Done when: no component has a hand-written page file.

3
Wave three · playground & fixtures · ~3 weeks

The control runtime and the clinical fixture set

api.controls → generated controls, deep-linkable state, event log, fixture selector. Build the six mandatory clinical fixtures. This is the wave that makes the library feel alive.

4
Wave four · discovery · ~2 weeks

⌘K, the graph, and the SEO emitters

Lexical + capability search, the relationship graph, sitemap, JSON-LD, OG image generation, and the SEO quality gate. Buy keyword data before this wave — see §21.

5
Wave five · hubs & patterns · ~3 weeks

Where topical authority actually accumulates

/behavioral-health first, because it is the uncontested one. Then /healthcare, then the first four pattern pages. Editorial, not generated — these are the pages that earn links.

Sequencing logic

Waves one and two are unglamorous and everything else is blocked on them. The temptation is to build the playground first because it demos well. Resist it: a playground on a hand-written page is another bespoke surface, and you will rebuild it.

21 · Decisions

What I decided, what I am not certain about, and the seven things I need from you

What I decided without asking

DecisionReasoning
Extend the existing schema rather than design a new one You already have defineComponentMeta(), Zod validation and a six-artefact generator with a staleness gate. Twenty-three of the forty-seven fields exist. Replacing that would throw away working enforcement to gain nothing.
Flat component URLs, nested hubs Category nesting looks organised and breaks the day a component is re-categorised. Assessment Runner has three legitimate parents; any nesting picks one arbitrarily. Category lives in breadcrumbs and metadata.
Anchors that look like tabs, not real tabs Unmounting tabs hide content from find-in-page, deep links and crawlers. The only true toggle is Preview ↔ Code, because they cannot both occupy the frame.
No sandbox button A third-party sandbox cannot resolve our registry, tokens or fixtures, so it opens broken. Broken is worse than absent. Revisit when the playground can export a self-contained bundle.
Semantic search is gated on measurement Lexical plus capability tags answers the queries you listed. Embeddings add inference cost and latency for a gain nobody has measured. Ship the index, instrument the misses, then decide.
Terminology is a runtime context, not a doc convention If patient is hard-coded in components, the switch can never be more than a documentation toy. Making it a provider costs a lint rule now and turns into a real product feature.
No volume numbers in §16 I have no keyword tool here. A fabricated volume column would be used to prioritise, and would be worse than an honest gap.

Seven questions I need answered

Question 01 · blocks wave four

Will you buy one month of keyword data?

Ahrefs or Semrush, roughly $100–130, for the ~40 terms in §16 plus a gap analysis against shadcn, MUI and the archived Terra domain. Without it the SEO plan is directionally right and unprioritised. This is the cheapest unblock in the document.

Question 02 · blocks wave one

Is summary allowed to be the meta description?

It makes one sentence do four jobs, which is why it stays consistent — and it constrains it to 160 characters forever. The alternative is a separate seo.description that drifts. I recommend one field with an override, but it is a real trade and you own the voice.

Question 03

Client or patient as the behavioral-health default?

Therapy and counselling say client; psychiatry and inpatient say patient. The provider makes it configurable, but the default is what a first-time visitor sees and it signals which room we have worked in. My recommendation is client for behavioral-health, because the therapy market is larger and the psychiatry reader is not offended by it.

Question 04

Does the Pro tier hide code, or just gate the CLI?

Hiding the source kills the SEO value of the page and the trust value of the library. My strong recommendation: Pro pages show everything — preview, code, props, accessibility — and gate only the install. A Pro badge and one install-block state, no blur overlays, no teasers.

Question 05

Do pattern pages ship in wave five, or wait?

They are the strongest SEO asset and the most editorial work — each is a real composed example, not a generated page. Four good ones beat twelve thin ones. Confirm you have the writing capacity, or we push them and ship hubs only.

Question 06

Storybook: keep, replace, or run both?

Stories are excellent as test fixtures and weak as public documentation. My recommendation is stories stay as the internal test and VRT surface, and never become the public site — the public site is generated from metadata. Confirm, because it affects wave two.

Question 07 · the one I would argue about

Should the hubs come before the components?

The plan builds machinery first and hubs last. But /behavioral-health is the uncontested keyword and could be published in a week against the eleven components that already exist — earning authority while the machinery is built. The counter-argument is that a hub pointing at eleven components looks thin. I lean toward publishing the hub in wave two and growing it, but it is a judgement about what a visitor forgives.

The assumption with the largest downstream cost

This standard assumes documentation pages are generated and never hand-written. That is the source of every consistency guarantee here. It also means the first genuinely unusual component — one that needs a page region no other component needs — will feel like fighting the system. When that happens the correct response is to add a schema field, not to add a bespoke page. If that discipline is going to be overruled the first time it is inconvenient, the honest thing is to know that now, because half of this architecture is only worth building if it holds.
