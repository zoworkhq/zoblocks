The engine runs. The dashboard is a wireframe.

The architecture underneath the theme console is finished and tested — validation, versioning, tenant isolation, immutable delivery. The interface on top of it is scaffolding I wrote to exercise that architecture, and it shows. This is an honest account of the gap and a plan to close it in the design language oxygenui.design already has.

Section 01

What is actually wrong

Not "it needs polish". Four separate failures, three of them structural, and the screenshot is a fair sample rather than an unlucky one.

1.1 A navigation link that 404s

The left rail links to /frameworks. That route was never built. Anyone clicking the second item in the primary navigation gets Next's default not-found page. This is not a polish issue; it is a broken product.

1.2 Four screens are viewers pretending to be editors

The component customisation screen renders the word Override in an accent colour. It is a <span>. Nothing happens. Typography lists three fields as read-only text. Comparison shows a diff with no way to act on it. Measured by counting form controls in each page:

1.3 It does not look like a product

The screenshot shows the diagnosis precisely. A form on a flat ground, controls at default sizes, no card, no section rhythm, help text the same weight as labels, and a submit button floating with no footer to sit in. There is no visual hierarchy because there is no layout system — every screen is <h1>, a paragraph, then content, with Tailwind utilities applied ad hoc.

The specific mistake

I gave the console its own design — Inter, a low-chroma blue accent, a neutral grey scale — reasoning that a theme editor should stay visually quiet so it does not compete with the customer's colours. That reasoning is sound for the preview surface and wrong for everything around it. The result is a generic admin panel wearing none of Oxygen's identity, sitting one hop from a marketing site with 1,686 lines of considered design language. The quiet-preview principle survives; it belongs to one region of one screen, not the whole product.

1.4 What is genuinely finished underneath

Worth stating so the plan does not re-solve it. None of the following needs revisiting:

  • Validation — a customer's palette runs through the same gate the build uses; 78 contrast pairs across three themes.
  • Publish gating — a failing theme cannot be published by any role, tested against all four.
  • Tenant isolation — scoped queries that cannot express an unscoped read, proven at the API and the public stylesheet boundary.
  • Immutable delivery — version-pinned CSS with correct cache and nosniff headers, live and verified.
  • Versioning and audit — immutable versions, pointer rollback, append-only trail.

The work below is almost entirely interface. Where it touches the server it is to add a mutation the screens need — token overrides, typography, framework selection — never to change how any of the above behaves.

The honest summary

A customer can create a theme from a colour, look at it, and publish it. They cannot change a single token, choose a font, pick a framework, manage a colleague, download an export, or restore a version. It is a viewer with one write path, not a theme management product.

Section 03

The design system, inherited not invented

Everything below already exists in apps/docs/src/app/globals.css — 1,686 lines of it. The console's job is to adopt it, not to interpret it. This document is built in the same language so the argument is visible rather than described.

3.1 Palette

The --site-* set, lifted verbatim. A cool, faintly green off-white — a clean clinical surface, not warm cream — with a single teal accent and an always-dark instrument panel that keeps its colour in both themes.

Two rules that carry over unchanged

--site-trace is dark-panel only. The luminous teal has no contrast on paper, and using it there is the fastest way to make this look generic. The docs CSS says so in a comment; the console inherits the rule.

Red only ever means critical. Never a brand colour, never a destructive-button default, and never carrying meaning alone — every coloured thing also has a word or an icon.

3.2 Type

Instrument Sans for display and body, JetBrains Mono for tokens, hex values, ratios and file paths — both already loaded by the docs site through next/font. Inter is dropped: it is a fine interface face and it is not this product's face, and the two sites sitting one hop apart in different typefaces is most of why the console reads as a different company's software.

Tabular numerals are not decoration here. Every screen shows contrast ratios in a column, and two ratios that do not line up cannot be compared at a glance — which is the entire reason the number is on screen.

3.3 Surfaces and depth

Three levels, and the third is the signature. A page sits on paper. Content sits on a .surface card — white, hairline rule, a barely-there shadow. Anything that is rendering something — a live preview, a code block, a validation readout — sits in an .instrument: the always-dark panel with a 1.125rem radius and a deep, soft shadow. The instrument reads as the lit object on the page, and preserving that relationship is what stops the console flattening into a generic admin grid.

Surface · content

White, 1px rule, 0.875rem radius, 0 1px 2px -1px shadow. Forms, tables, lists.

Instrument · rendering

Always dark, both themes. 1.125rem radius, deep shadow. Previews, snippets, readouts.

3.4 Motion

One curve — cubic-bezier(0.16, 1, 0.3, 1), the docs site's --ease-out-expo — and a short list of uses. Hover lift on interactive cards at 420ms. Entry on first paint at 780ms, once, never on navigation. Everything else is instant. All of it inside prefers-reduced-motion.

3.5 The one thing the console adds

A neutral preview region. My original instinct was right in the wrong scope: where a customer's colours are being shown, the surrounding chrome must be achromatic, because an Oxygen-teal button beside a customer's teal makes their teal look wrong. That is a rule for the preview panel and the swatch grid — a defined region with its own reduced palette — and nowhere else.

Section 04

Component kit

Thirteen screens built from ad-hoc utilities is thirteen slightly different products. These are built once, in apps/console/src/components/ui/, before any screen is rewritten.

ComponentJobThe detail that matters
<PageHeader>Eyebrow, title, lede, actionsOne per screen, so every page has the same first 120px and the reader always knows where they are.
<Panel>A titled surface cardOptional tone="instrument" switches to the dark panel. One component, so the depth rule cannot drift.
<Field>Label, control, hint, errorBinds hint and error with aria-describedby and sets aria-invalid. Getting this wrong once is getting it wrong on every form.
<ColorField>Swatch, picker, hex inputThe hex input is the real control; the picker is the convenience. A picker alone is not keyboard-operable.
<ContrastBadge>Ratio, floor, verdictShows 5.82:1 against 4.5 and names the WCAG criterion. Never a bare tick.
<Ramp>Eleven steps, selectableEach step is a button with an accessible name of "step 600, #1D63C9" — operable and readable without sight.
<DataTable>Sortable, keyboard-navigable rowsA real <table> with <caption> and aria-sort. Cards on narrow screens.
<StatusChip>Published, draft, locked, failingAlways a word. Colour is reinforcement.
<Toolbar>Axis switches for the playgroundA labelled radio group per axis, not a row of unlabelled buttons.
<Preview>Neutral region rendering real componentsThe achromatic zone from §3.5. Renders the actual library, not a mock.
<Skeleton>Loading placeholderMatches the final layout so nothing shifts on arrival.
<EmptyState>Nothing here yetAlways offers the two real next actions. Never an illustration with no route out.
<Callout>Validation failure, noticeWhat happened · what it affects · what to do. Never "something went wrong".
<CopyButton>Copy a snippetConfirms in the button: Copy → Copied, reverting after two seconds.
Why this is Phase 1 and not a refactor afterwards

Every screen in Section 5 is specified in terms of these. Building the screens first and extracting components later produces thirteen sets of nearly-identical markup and a week of reconciliation — which is exactly how the current console ended up with a decorative <span> where a button belongs.

Section 06

Phases and tasks

Six phases, sequenced so the product is shippable at the end of each rather than only at the end of all six. Estimates assume one engineer and are relative, not commitments.

PhaseA3–4 days

Foundation — adopt the design system

Nothing user-visible ships alone here, and everything after it depends on it. Instrument Sans and JetBrains Mono via next/font, the --site-* palette, the type scale, the surface and instrument treatments, and the fourteen kit components from §4.

PhaseB2–3 days

Shell and the broken link

The three-group rail, the standard page header, and /frameworks — which currently 404s from the primary navigation and is the one thing here that is a live defect rather than a shortfall.

PhaseC5–6 days

The editors — make it a product

Token editor, brand and ramp, typography with real upload, component overrides. This is the phase where the console stops being a viewer.

PhaseD3–4 days

The tools

Playground, comparison with pickers and rendered previews, transfer with actual downloads, version history with restore.

PhaseE3–4 days

Organisation and states

Members, roles, approvals, settings — the data model exists and nothing renders it. Then the full state treatment across every screen.

PhaseF3–4 days

Proof

Console E2E, axe across every screen in three themes, VRT baselines, responsive verification. The console currently has no browser test of its own.

If the whole thing cannot be funded

A, B and C are the shippable minimum — roughly ten days. That gets a product that looks like Oxygen, has no broken navigation, and lets a customer actually change their design language. D and E are what make it feel finished; F is what keeps it that way. Stopping after B would leave a well-dressed viewer, which is the current problem with better typography.

Section 07

Definition of done

Checkable rather than aesthetic, because "looks like a SaaS product" is not something a build can verify and these are.

Visual
  • Instrument Sans and JetBrains Mono only — no Inter anywhere
  • Every colour resolves from a --site-* token
  • Every screen opens with <PageHeader>
  • Every primary action sits in a header or a panel footer, never loose in flow
  • At least one .instrument per screen that renders something
Functional
  • No navigation link 404s
  • All 13 mockup screens exist
  • No screen labelled with an action it cannot perform
  • A customer can change a token, a font, a component and a framework
  • Every export downloads
Accessible
  • axe clean on every screen × light, dark, high contrast
  • Every form control has a bound label and hint
  • Disabled controls use aria-disabled with a reachable reason
  • No state conveyed by colour alone
  • Full keyboard path through create → edit → publish
Proven
  • E2E covers the full lifecycle and the negative path
  • VRT baselines for eight screens, light and dark
  • No horizontal scroll at 320px on any screen
  • Coverage floor raised, never lowered
  • The whole CI gate green

What I would change about how this happened

The mockups in the original report were detailed and I treated them as illustration rather than specification — I built the data model against them and the interface against my own shorthand. The check that would have caught it is trivial and was never run: open every route the navigation links to. That would have found the 404 on day one, and finding it would have prompted the wider comparison.

Phase F exists so that check is automatic rather than remembered.
