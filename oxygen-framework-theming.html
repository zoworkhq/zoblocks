Section 00

Executive summary

The brief asks how to adopt Ant Design while staying open to Material UI, and how to let enterprise customers bring their own design language. The honest answer from reading the repository is that the hard architectural work is substantially done, and that the most likely way to get this wrong is to build the thing the brief's wording implies — a component-swapping adapter layer.

What the investigation found

Oxygen UI is a 23-package pnpm monorepo shipping healthcare components through two channels: shadcn copy-source and npm. Ant Design is already integrated, in three distinct and deliberate patterns, governed by an accepted architecture decision record. The theming layer is a W3C DTCG token pipeline with a build-time accessibility gate.

The finding that shapes everything else

Every Oxygen stylesheet already resolves its colours through an ordered fallback chain. This is not a stylistic tic — it is a working, zero-JavaScript, zero-dependency theme adapter, and it is the seam the rest of this report proposes to formalise.

1 · Our contract --ox-accent Set by the Oxygen token build, a customer brand, or the theme console.
2 · Host framework --ant-color-primary Set by the host's own ConfigProvider when cssVar is on. We never write it.
3 · Literal #059478 The component renders correctly with no token system present at all.

The real declaration, from packages/tabs/src/styles.css:47. There are 145 such fallbacks across four shipped stylesheets today.

Recommendation

Adopt a token-bridge architecture. Reject component swapping.

Keep Oxygen's components as the single implementation. Treat the --ox-<component>-* token surface as the published, framework-independent theming contract. Ship one small bridge per supported UI framework whose only job is to read that framework's resolved theme and write the Oxygen surface. Ant Design's bridge already exists and is tested; Material UI's is roughly 120 lines of the same shape.

Application code never changes when the framework changes, because application code never named the framework. Switching is mounting a different bridge — a runtime operation, safe under SSR, with no re-render of the component tree and no second implementation to keep in parity.

Why not the adapter layer the brief implies

A conventional pluggable-UI architecture defines an abstract <Button> and swaps antd's or MUI's implementation behind it. That approach is already settled against in this repository, on evidence, in ADR 0010, and the reasoning generalises:

  • The abstraction degrades to the intersection of both libraries. Oxygen's Switch has a third value — "unknown", carrying a FHIR dataAbsentReason — because a binary control cannot distinguish no from nobody asked. Neither antd's nor MUI's Switch can express it. An adapter that must satisfy both cannot ship the component's main clinical contribution.
  • It costs the copy-source channel. A component that wraps a framework cannot be copied into a customer's repository as readable source — it becomes a fork of that framework. ADR 0002 protects that channel deliberately, and healthcare procurement is precisely where "read every line before you trust it" earns its keep.
  • It multiplies the accessibility surface. Two rendering paths mean two focus models, two ARIA trees, and two sets of axe results, per component, forever.

1.4 The styling architecture

There is no CSS-in-JS anywhere. Styling is plain CSS custom properties, with Tailwind v4 used only in the documentation site. This is the property that makes framework-plural theming tractable at all, and it should be treated as load-bearing rather than incidental.

Three token tiers

Tier 1 · Primitive

--ox-ref-brand-600

The raw palette. Referenced by semantic tokens only. A customer brand replaces this tier wholesale and nothing else.

Tier 2 · Semantic

--ox-status-critical

84 keys per theme. What a value means. Components reference these. @oxygenui/no-primitive-token makes reaching past them a lint error.

Tier 3 · Component

--ox-badge-critical-bg

169 tokens across 12 component groups. The published override point — and, this report argues, the framework-independent theming contract.

Three axes

Brand × theme × density, all applied through HTML attributes and resolved entirely in CSS. No JavaScript, no flash of unstyled content, correct under SSR and React Server Components. Verified at scripts/gen/tokens/emit.ts:42,159,194.

The fallback chain

Component stylesheets do not read semantic tokens directly. They declare a component token whose value walks a chain, and this is where the framework integration actually lives:

packages/tabs/src/styles.css:31,47,55

Read left to right: use Oxygen's token if the host set one; otherwise use Ant Design's if the host is an antd application with CSS variables enabled; otherwise use a literal that is known to pass the contrast gate. A component styled this way is correct in an Oxygen app, correct in an antd app, and correct in a plain HTML page — with no configuration and no JavaScript.

1.5 How Ant Design is integrated today

ADR 0010 — "Primitives are antd-compatible and antd-free" (content/decisions/0010-antd-compatible-primitives.md, accepted 16 August 2026) governs this, and it draws a line that the rest of this report builds on rather than revisits:

ADR 0010 · the decision

Primitives match Ant Design's public API exactly and take no dependency on it. Compound clinical organisms may wrap antd, and each one must name the expensive behaviour it is inheriting.

In practice this has produced three patterns. They are worth naming separately because the brief's requirements land on them differently.

PatternWhat it meansExamplesCopy-source?
A · Compatible primitive Oxygen implements the component. Its prop names, shapes and defaults match antd's, so migration is changing an import. Divergences are permitted only where antd's behaviour is a defect, and each must be listed in the component's limitations. Switch, Timeline, Accordion Yes
B · Wrapping organism The component wraps antd because it inherits genuinely expensive behaviour — Modal's focus trap, Upload's file handling. antd is a peer dependency. signature, copilot No — npm only
C · Optional bridge A separate entry point that reads the host framework's resolved theme and writes Oxygen's component tokens. antd is imported only by this subpath, so it never enters the main module graph. @oxygenui-design/tabs/antd Yes — the bridge is not copied

Pattern C is the one that generalises, and it already exists in working, tested form. It is 96 lines:

packages/tabs/src/antd.ts — abridged
import { theme } from "antd";

export function useAntdTabsTokens(): AntdTabsTokens {
  const { token } = theme.useToken();
  return React.useMemo(() => ({
    "--ox-tabs-accent":     token.colorPrimary,
    "--ox-tabs-fg":         token.colorTextSecondary,
    "--ox-tabs-critical":   token.colorError,
    "--ox-tabs-min-h":      `${token.controlHeight}px`,
    // Concentric radii: the inner corner is the outer corner minus
    // the inset, which is why a thumb that simply reuses the track
    // radius looks subtly wrong at every size.
    "--ox-tabs-track-radius": `${radius + pad}px`,
    "--ox-tabs-thumb-radius": `${radius}px`,
    …
  }), [token]);
}

Its own comment states the design rule precisely: "Only the tokens whose meaning genuinely matches are mapped. Anything without an honest counterpart is left alone so the stylesheet's own fallback chain wins." That sentence is the correct specification for every future bridge, including Material UI's, and Section 4 formalises it as the partial mapping rule.

1.6 Component structure

Every component is a directory with a fixed layout, and one file in it — *.meta.ts — is the source of truth from which shared artifacts are generated. Sixteen components carry metadata today (13 with registry source, 3 package-only).

Props are never written twice: they are extracted from the TypeScript types by scripts/gen/props.ts, so a prop table cannot drift from the implementation. pnpm gen --check fails CI if any generated artifact is stale. This is the mechanism that makes adding a framework bridge cheap — the catalog, the registry JSON, the docs, and the coverage gate all update themselves.

1.10 Assumptions

These are stated so they can be corrected. Each would change parts of the recommendation if wrong.

  1. React remains the only rendering target for framework-coupled components. The elements and loaders packages serve Vue, Angular and Svelte as custom elements, but antd and MUI are React libraries. A Vue host gets Oxygen's elements and its tokens, never an antd bridge. Assumption
  2. "Framework switching" means the host application's framework, not ours. Section 02

Architecture investigation

Seven approaches, each evaluated against the same ten criteria and against this repository specifically rather than in the abstract. The order below is roughly from most coupled to least, and the recommendation is a named combination of three of them — because the real question is not which single approach wins, but where each one is allowed to apply.

2.1 The criteria

"Suitability for enterprise customers" is doing a lot of work in the brief, so it is worth decomposing. For a healthcare buyer it means four specific things, all of which appear in procurement: the source can be read and audited; the accessibility claims are testable; the upgrade path is stated; and the customer's own brand can be applied without forking. Those are the lenses used below.

2.2 Option A — Direct Ant Design integration

Architecture. Take antd as a hard dependency. Oxygen components are compositions of antd components, themed through ConfigProvider. Customer branding is antd's theme.token object.

Benefits
  • Fastest to a first release; the least code we own.
  • antd's accessibility, i18n and RTL come free.
  • One theming system, thoroughly documented, that customers may already know.
Drawbacks
  • Ends the copy-source channel outright — ADR 0002's central product promise.
  • Forecloses the Switch third value and the commit phase machine, which antd's boolean cannot express.
  • Total vendor lock-in; a Material UI customer is unservable.
  • antd's bundle enters every consumer, including copy-source ones.

2.3 Option B — Wrapper / adapter layer

Architecture. Define an Oxygen component interface. Implement it once per framework. A registry maps component names to implementations, selected by provider or build flag. 

// the shape this option implies
interface UIAdapter {
  Button: React.ComponentType<OxButtonProps>;
  Switch: React.ComponentType<OxSwitchProps>;
  Modal:  React.ComponentType<OxModalProps>;
  …
}
const antd: UIAdapter = { … };
const mui:  UIAdapter = { … };
Benefits
  • The literal reading of the brief; easy to explain to stakeholders.
  • Each framework renders in its own idiom, so a host application looks native.
  • Adding a framework is additive — no existing implementation changes.
Drawbacks
  • The interface collapses to the intersection of every framework. This is the fatal one, and it is concrete here, not theoretical.
  • N implementations × M components, each needing its own a11y tests and VRT baselines.
  • Guaranteed silent divergence — the repository already maintains parity tests between just two channels of one component and treats it as a standing hazard.
  • Copy-source becomes impossible for anything routed through the adapter.
The concrete failure, from this repository

Oxygen's Switch accepts value: boolean | "unknown", where "unknown" carries a FHIR dataAbsentReason distinguishing not asked from asked and declined from not applicable. It also runs a seven-phase commit machine so that a write in flight is visible and still operable, and a failed write animates back and interrupts rather than snapping silently.

antd's checked is boolean. MUI's is boolean. An adapter interface satisfiable by both cannot carry either feature — so the abstraction would delete the component's clinical contribution in order to be portable. ADR 0010 reached this conclusion for antd alone; adding MUI strengthens it.

2.4 Option C — Framework-agnostic design-system layer

Architecture. Behaviour, state machines and ARIA contracts live in dependency-free core packages. Rendering is Oxygen's own. No UI framework is involved at any layer.

This is what the repository already does, in five *-core packages, and it is the reason the rest of the plan is affordable. tabs-core owns the keyboard model, role selection, overflow strategy and URL adapters in 10 modules with zero dependencies; identity-core owns Jaro–Winkler and Metaphone patient matching; signature-core owns the capture engine and the 21 CFR 11 outcome taxonomy.

Benefits
  • Accessibility is solved once, in the layer that has no rendering opinion.
  • Zero framework coupling; consumable from a server, a test, or a non-React app.
  • Capability ceiling is ours, not the intersection of vendors'.
  • Preserves copy-source: the source is genuinely ours to give away.
Drawbacks
  • We own every keyboard interaction and focus trap outright — ADR 0010 names this cost explicitly.
  • Components look like Oxygen, not like the host, unless something bridges the visual language. Option D is that something.
  • Slower per component than wrapping a mature library.

2.5 Option D — Design-token bridging Recommended

Architecture. The component-tier token surface — --ox-<component>-*, 169 tokens today — is published as a versioned contract. Components read only that surface. Anything may write it: the Oxygen token build, a customer brand, the theme console, or a bridge that reads a host UI framework's resolved theme and translates it.

Writer Oxygen build DTCG source → CSS. The default.
Writer Customer brand [data-ox-brand], validated and contrast-gated.
Writer bridge-antd theme.useToken() → the surface.
Writer bridge-mui useTheme() → the same surface.

Every writer produces the same kind of output — CSS custom property declarations — so they compose by ordinary cascade rules rather than by negotiation. A customer running an antd host with their own brand gets the bridge for structure and their brand for colour, and neither knows the other exists.

Benefits
  • Application code never names a framework, so switching costs nothing at the call site.

2.6 Option E — Compile-time framework selection

Architecture. The framework is chosen at build time via package exports conditions, a bundler alias, or an environment flag; dead branches are eliminated.

This is not a rival to Option D so much as a delivery mechanism for it. Under the recommended architecture, compile-time selection is what already happens: importing @oxygenui-design/bridge-antd pulls the antd bridge and nothing else, and a consumer who imports no bridge ships no bridge. The interesting question is only whether to add automatic selection on top — a conditional export that resolves to whichever framework is installed.

Benefits
  • Zero runtime cost for unselected frameworks; perfect tree-shaking.
  • Type-safe — the consumer sees exactly one API.
Drawbacks
  • Automatic resolution is fragile: a monorepo with antd in one app and MUI in another has no single right answer.
  • Cannot serve an application that renders both, which is the realistic state of a large migration.
  • Switching requires a deploy — the brief explicitly asks about runtime.

Verdict Adopt the explicit form, reject the magic form. Bridges are separate subpath exports the consumer imports by name. No auto-detection, no build flags, no conditional exports keyed on installed packages.

2.7 Option F — Runtime framework selection

Architecture. A provider holds the active framework; components dispatch through it and can change framework without a reload.

Under Option B this is expensive and dangerous — swapping implementations unmounts and remounts every component, losing focus, scroll position, form state and any in-flight commit. Under Option D it is nearly free, because nothing dispatches: changing the bridge changes which CSS custom properties are written to a wrapper element. The component tree does not re-render, DOM identity is preserved, and focus survives.

What "runtime switching" costs under each option
UnderMechanismCost of a switch
Option B — adapterSwap component implementationsFull unmount/remount. Focus, scroll and form state lost. Both bundles resident.
Option D — bridgeChange which tokens a wrapper writesA style recalculation. No remount, no state loss.

Verdict Adopt, in the Option D sense. Runtime switching of the theme source is supported and cheap. Runtime switching of the component implementation is not offered, and Section 8 states that limitation plainly rather than implying otherwise.

2.8 Option G — Micro-frontends / isolated libraries

Architecture. Each framework's components ship as an independently deployed bundle, composed at runtime via Module Federation or custom elements with Shadow DOM.

Benefits
  • True isolation — no CSS or version conflicts between frameworks.
  • Independent deployment per framework.
  • The elements and loaders packages already prove the custom-element half works, verified across six frameworks in three browser engines.
Drawbacks
  • Shadow DOM breaks cross-boundary aria-labelledby and aria-controls, and complicates label association and form participation — all load-bearing in clinical forms.
  • Multiple React copies is a well-known hazard class.
  • Enormous operational complexity for a component library.
  • Theming across a shadow boundary needs custom properties anyway — so it depends on Option D regardless.

Verdict Rejected for UI-framework plurality, retained for what it already does well: reaching Vue, Angular and Svelte hosts through custom elements, where there is no React to share.

2.10 Recommendation

The recommended architecture

C + D as the architecture, B by exception, E and F as delivery.

Framework-agnostic cores (C) continue to own behaviour, keyboard models and ARIA contracts. Token bridging (D) is the framework integration layer: one small module per UI framework, writing a published token surface that components already read. Wrapping (B) remains available for compound organisms under ADR 0010's existing rule, with the justification written down per component. Bridges are imported explicitly (E) and may be changed at runtime (F) because changing one only changes which custom properties are written.

The name for this in the codebase should be the theme bridge, not the "adapter" — because calling it an adapter invites the next engineer to put components behind it, which is the failure mode this whole section is arguing against.

Why this one

  1. It is the smallest change that satisfies the brief. Three of the four layers exist; one bridge exists and is tested. The work is generalisation and enforcement, not construction.
  2. It does not trade away the product. Every alternative that makes components portable does so by reducing them to what all frameworks share. In clinical software the differentiating features — the third switch value, the commit machine, the absence taxonomy — are precisely what does not survive that reduction.
  3. It keeps both distribution channels. Copy-source and npm both continue to work, because the framework coupling lives outside the component.
  4. It is consistent with the decisions already made. No ADR needs superseding. One new ADR is needed to name the token surface as a public contract.
  5. It fails gracefully. If a bridge is missing, absent or wrong, the CSS fallback chain renders correct, accessible, contrast-gated defaults. No other option degrades this well.

What we give up by choosing it

Stated plainly, because it will come up in a customer conversation: an Oxygen component in a Material UI application will match that application's colour, radius, typography, spacing and motion — and will still not be a Material UI component. Its DOM structure, its ripple behaviour, and its elevation model are Oxygen's. For a customer whose requirement is "pixel-identical to our MUI components", the answer is that they should use their MUI components and take Oxygen's *-core packages for the clinical behaviour underneath. That is a real, supported path, and Section 4 documents it.

3.4 Styling and CSS considerations

Three rules, of which the first two are already practised and the third is new.

Rule 1 · Chain, don't branch

Never :where(.ant-…) selectors or framework-detection classes. Resolve through var() fallbacks so precedence is the cascade's job.

Rule 2 · Terminate in a literal

Every chain ends in a value that passes the contrast gate, so a component with no token system present is still accessible.

Rule 3 · Declare the surface new

Every component declares its --ox-<name>-* tokens in a single :where() block at the top of its stylesheet — the generated surface manifest reads from there.

Specificity. Component tokens are declared inside :where() so a consumer's own stylesheet always wins without needing !important. This is already the shape in packages/tabs/src/styles.css and should be a lint rule.

Cascade layers. Antd v6 emits into its own layer when configured to. Oxygen currently uses none. Recommendation: emit component styles into @layer oxygen so a host can order Oxygen relative to antd and its own overrides explicitly rather than by import order. This is a small change with a large effect on integration complaints.

That is the one thing a clinical design system does not delegate." A host framework is not entitled to more than a customer brand is.

Recommendation: bridges map chrome — colour, radius, typography, spacing, motion, surfaces, borders. Clinical status tokens are never bridged, and the token-surface manifest marks them bridgeable: false so the rule is enforced by the generator rather than remembered.

3.6 The partial-mapping rule

tabs/antd.ts states it in a comment; it should be the written specification for every bridge:

Map a token only where the meaning genuinely matches. Where it does not, write nothing — the stylesheet's own fallback chain then wins, which is the correct outcome. A bridge that fills every slot by approximation produces a component that is uniformly slightly wrong, which is harder to diagnose than one that is partly unthemed.

Derived values are computed, not copied. The existing bridge demonstrates this: it does not map antd's radius onto both the track and the thumb, it recomputes the concentric relationship (track = radius + pad, thumb = radius) because a thumb that reuses the track's radius "looks subtly wrong at every size". Bridges carry geometry knowledge; they are not lookup tables.

3.9 Accessibility

The bridge is where a host framework's theme can quietly break an accessibility guarantee we have otherwise proved, so it needs its own gate.

  • Contrast validation at the bridge boundary. A host's colorPrimary can be any hex. In development, the bridge runs the same contrast check the token build runs and warns when a mapped pair falls below its floor. Stripped in production by the NODE_ENV guard, consistent with the deprecation-warning pattern already in use.
  • Hit targets have a floor, not a mapping. controlHeight maps to --ox-density-target via max(44px, …). A host that wants 24px controls does not get to shrink a clinical control below WCAG 2.5.5.

  • Forced-colors mode ignores both. Under forced-colors: active the system palette overrides everything, which is correct and already handled in the token layer.
  • axe runs per story × theme × density, and the matrix gains a bridge dimension — see Section 9.

4.3 The bridge interface

Deliberately small. A bridge is a pure function from a framework's resolved theme to a set of custom properties, plus enough metadata for the generator and the tests to reason about it.

packages/bridge-core/src/contract.ts
/**
 * A bridge translates one UI framework's resolved theme into Oxygen's
 * component token surface. It renders nothing and owns no state.
 *
 * The partial-mapping rule is enforced by the type: every value is
 * optional, and omitting one is the correct way to say "this framework
 * has no honest counterpart". A bridge that fills every slot by
 * approximation makes a component uniformly slightly wrong, which is
 * harder to diagnose than one that is partly unthemed.
 */
export interface BridgeDefinition<HostTheme> {
  /** Stable id — the `data-ox-bridge` value and the npm suffix. */
  readonly id: "antd" | "mui" | (string & {});

  /** Peer range this bridge is written against. Asserted in CI. */
  readonly supports: string;

  /**
   * The mapping. Returns only the tokens with an honest counterpart.
   * Never returns a token whose surface entry is `bridgeable: false` —
   * clinical status colours are the reason that flag exists.
   */
  map(theme: HostTheme): Partial<TokenSurface>;

  /** Tokens this framework cannot express, for the docs table. */
  readonly unmapped: readonly (keyof TokenSurface)[];
}

/** Generated from every component's stylesheet. Never hand-written. */
export interface TokenSurfaceEntry {
  readonly name:       string;   // "--ox-tabs-accent"
  readonly component:  string;   // "tabs"
  readonly semantic:   string;   // "--ox-accent" — what it falls back to
  readonly kind: "color" | "dimension" | "duration" | "font" | "shadow";
  /** false for clinical status. A bridge writing one fails the build. */
  readonly bridgeable: boolean;
  /** Semver of the surface this entry entered. Removing it is breaking. */
  readonly since:      string;
}

4.6 Fallback behaviour

Four degradation levels, in order. The important property is that every one of them renders a correct, accessible component — the differences are only how closely it matches the host's visual language.

L1
Bridge mounted, token mapped
The component takes the host's exact value. Closest visual match.
L2
Bridge mounted, token deliberately unmapped
Falls to the Oxygen semantic — which is the intended outcome for clinical status, not a shortfall.
L3
No bridge, host exposes CSS variables
The var(--ox-*, var(--ant-*, …)) chain resolves against the host's own variables. Zero JavaScript.
L4
Nothing present at all
Literal defaults, all of which passed the contrast gate at build time. A component dropped into a bare HTML page is still accessible.
One constraint to state honestly

CSS var() fallbacks are ordered, not conditional. A chain reading var(--ox-x, var(--ant-x, var(--mui-x, literal))) does not detect which framework is present — it takes the first variable that resolves. In an application running both antd and MUI, the earlier stop always wins regardless of which framework owns the subtree. For mixed-framework applications the JavaScript bridge is required, not optional, because only it is scoped to a subtree. This is why the recommendation keeps both mechanisms rather than choosing one.

5.2 What is restricted, and why

The one refusal that needs management sign-off

Clinical status — critical, high, low, normal, unknown — and the identity flags deceased, restricted, provisional are not customer-configurable. This is already the rule for build-time brands, and the brands README states the argument in one sentence: "Letting a brand override semantic tokens would let it redefine what critical means. That is the one thing a clinical design system does not delegate."

What the restriction actually protects is not the hue. It is the relationships: a validated contrast floor against the matching background, and more than 60° of hue separation between high and low so that the direction of an abnormal result survives colour-vision deficiency and monochrome printing. A customer who sets both to shades of their corporate blue has not rebranded a component — they have removed a clinical signal, in a way that renders correctly and passes every other test. Section 10 lists this as a decision requiring approval, because a large customer will eventually ask.

Also fixed, for narrower reasons: focus-ring visibility (colour is configurable, suppression is not), minimum hit target, the requirement that every status carries an icon and a text label alongside colour, and prefers-reduced-motion honouring. Each is a WCAG obligation or a stated product invariant, and each fails silently if delegated.

Published versions are immutable. Editing a published theme creates a draft; publishing the draft writes a new version and moves a pointer. That makes rollback a pointer move rather than a restore, and it makes "which theme was live when this screenshot was taken" answerable — which matters in a regulated environment.

5.5 Validation

The single most important implementation constraint in this report

There must be exactly one validator. Today the rules live in scripts/gen/tokens/validate.ts, reachable only from a build script. If the console reimplements them, there are two definitions of "accessible clinical colour" that will diverge — and the divergence will be discovered by a customer whose theme passed in the browser and failed in CI, or worse, passed in both and was wrong. Phase 1 extracts it to @oxygenui-design/tokens/validate: pure functions, no filesystem, no process, so the identical module runs in the generator, in a server action, and in the browser for live preview.

Three points of enforcement, one implementation:

Live · in the editor

Debounced on every keystroke. A failing pair marks the field and shows the measured ratio against its floor. The user cannot reach a bad state unknowingly.

Gate · on publish

Server-side, authoritative. Client validation is a courtesy; this is the boundary. A theme failing any check cannot be published — the button is disabled and says why.

Guard · on serve

The delivery service re-checks validation.validatorVersion. A theme validated by an older validator is re-validated before it is served, so tightening a rule cannot leave old themes live.

The checks are the ones that already exist, applied to customer input:

  • Key space — a theme may only override keys the base palette defines. A typo is an error, not a silently ignored line.
  • Status contrast — every status foreground against its background, 4.5:1, or 7:1 in high contrast.
  • Text and interface contrast — SC 1.4.3 for text at 4.5:1, SC 1.4.11 for interface components at 3:1. The existing validator already separates these correctly.
  • Hue separation — status.high and status.low more than 60° apart.
  • Reference resolution — no dangling {ref.…}.
  • Tier discipline — a component token may not reference a primitive.
  • All three themes — light, dark and high contrast are each re-validated. A brand that passes in light and fails in dark does not publish.

5.7 Application and delivery

Three delivery modes, because customers sit in different places on the trade-off between control and convenience.

ModeHowAppliesBest for
1 · Build-time exists Theme exported as a brand JSON, committed, compiled by pnpm gen Next deploy Regulated customers who require every visual change to pass their own release process.
2 · Runtime stylesheet proposed <link> to /t/{org}/{slug}@{version}.css, immutable and long-cached Next page load The default. Version-pinned, CDN-cacheable, no JavaScript.
3 · Runtime provider proposed <OxygenTheme tokens={…}> writes inline custom properties Immediately Multi-tenant applications rendering two customers' branding on one page, and the console's own preview.

Modes 2 and 3 compose with bridges by ordinary cascade rules: the bridge writes on a wrapper element, the brand writes on a container or :root, and the more specific one wins. No coordination code is required, which is the main practical benefit of having chosen custom properties over a JavaScript theme object.

Runtime or deploy?

Runtime, with a build-time escape hatch. Requiring a deploy for a colour change is the thing enterprise customers complain about, and mode 1 already exists for those who want it. The version pin in the URL is what makes runtime delivery safe: a customer's application references a specific immutable version, so a theme edit cannot change a running application until someone moves the pointer.

5.8 Versioning, export and import

  • Monotonic integers, not semver. A theme is data, and "is this newer" is the only ordering question anyone asks of it.
  • Every publish writes a version with a diff against its predecessor, the publishing user, and the validator version.
  • Rollback is a pointer move to any prior version, and is itself a new version so the audit trail stays append-only.
  • Export to DTCG JSON (the portable form), a CSS custom-property block (drop-in for any stack), a Tailwind v4 @theme block, an antd ConfigProvider token object, and an MUI createTheme object. The last two are what let a customer apply their Oxygen brand to their own components — a genuinely useful export, and the same mapping tables the bridges use, run backwards.
  • Import from DTCG JSON, Tokens Studio, a Figma Variables export, or an existing antd/MUI theme object. Import is lossy in one direction and the UI must say so: an antd theme has no clinical status, so those tokens keep Oxygen's validated values.
A known constraint on DTCG round-tripping

The current token source is DTCG-shaped but not DTCG-compliant: dimension, duration and shadow use raw CSS strings where the specification requires structured objects, and the loader coerces with String($value). Colour and font family round-trip; the rest would be mangled by Tokens Studio or Style Dictionary v4. Import/export beyond colour requires fixing this first, which is why it is scheduled in Phase 4 rather than promised in the MVP.

5.9 Fonts, icons and assets

Fonts. Two supported paths: reference a URL the customer already hosts, or upload a file we store and serve. Uploads are validated as real font files by magic number rather than extension, capped at 2 MB per face, served from an isolated asset origin with Content-Type pinned and X-Content-Type-Options: nosniff, and recorded with a SHA-256 so the served bytes are verifiable. The console previews the actual face — a font that lacks tabular numerals is a real problem for a flowsheet and is invisible until you look at aligned digits.

Icons. A customer may select a supported icon set or supply SVGs for a defined slot list. They may not change which icon carries which clinical meaning: the pairing of icon to status is part of the never-colour-alone guarantee, and remapping it breaks the redundant encoding that makes the system usable without colour. Uploaded SVGs are sanitised — no <script>, no external references, no event handlers — consistent with the reasoning already applied to signature ink, where a stored SVG rendered through innerHTML was identified as an XSS vector because the value round-trips through a database.

5.10 Preventing inaccessible combinations

Four layers, in the order a user encounters them.

LayerBehaviour
1 · SteerThe colour picker shows the live contrast ratio against the surfaces the token will actually sit on, and marks the region of the picker that would fail. Prevention beats correction.
2 · WarnA failing pair marks the field immediately, states the measured ratio and the required floor, and names the WCAG criterion. The message says which pair and by how much — not "invalid colour".
3 · RepairOffer the nearest passing colour, holding hue and adjusting lightness. Customers reliably accept a shade they did not choose; they do not reliably accept a rejection.
4 · BlockPublish is disabled with the failing pairs listed. There is no override, no "publish anyway", and no admin bypass — an accessibility floor with an exception is a default.

Beyond contrast, the simulation views cover what ratios cannot: the greyscale and colour-vision-deficiency previews are where a customer discovers that their two chosen abnormal-direction colours are the same colour to eight percent of their clinicians.

5.11 Customer-specific overrides

Four scopes, resolved by specificity — deliberately mirroring the token tiers so there is one mental model rather than two:

Widest Oxygen default The shipped token build. Always present.
Organisation [data-ox-brand] The customer's published theme.
Application container scope One product within the organisation.
Narrowest inline style A single component instance. Escape hatch.

All four are ordinary CSS specificity, so no resolution code exists to be wrong. The instance-level escape hatch is deliberate: the alternative to an override point is a customer editing a copied component file, which permanently severs their upgrade path — the exact failure the component token tier was introduced to prevent.

Section 08

Limitations and risks

Every item below has a mitigation, and a few have none worth the cost — those are marked accepted and stated so they can be quoted to a customer rather than discovered by one.

8.1 Differences between UI frameworks

Limitation. antd and MUI disagree on elevation (3 tokens vs a 25-step scale), typography (sizes vs full variants), density (one componentSize vs per-component size plus a spacing() function), and motion (tokens vs a transitions.create() function). A single mapping cannot be faithful to both.

Mitigation. The partial-mapping rule: map only honest counterparts, sample where a scale is finer than ours, and declare the rest in unmapped so it appears in the docs table. A customer sees the difference before they file it.

8.2 Components that cannot be abstracted

Limitation. The wrapping organisms — signature and copilot — genuinely depend on antd's Modal, Form and Upload. They will not work in an MUI-only application without an MUI implementation, which would be a second implementation with all the divergence cost Section 2.3 describes.

Mitigation. Their cores already carry the value: signature-core owns the capture engine, the ink model and the 21 CFR 11 outcome taxonomy with no dependencies. An MUI customer takes the core and supplies their own shell — a supported path that must be documented, with the core's API treated as public rather than internal. Longer term, re-implementing the overlay layer on Oxygen's own primitives would remove the constraint; that is a real project, not a bridge.

8.3 Runtime switching constraints

Limitation. Switching the theme source at runtime is cheap. Switching the component implementation is not offered at all. Anyone reading "runtime framework switching" as the latter will be disappointed.

Mitigation. Say so in the documentation, in those words. The capability that is actually wanted — the same application code running under either framework, changeable without touching call sites — is delivered.

8.4 CSS var() fallbacks are ordered, not conditional

Limitation. A chain cannot detect which framework is present; it takes the first variable that resolves. In an application running both antd and MUI, the earlier stop wins everywhere regardless of which framework owns a given subtree.

Mitigation. The JavaScript bridge is scoped to a subtree and is therefore required, not optional, in mixed applications. Documented as a hard rule, and the docs must not imply the CSS-only path is universally sufficient.

8.7 antd version skew — the silent failure

The highest-priority risk in this section

Peer ranges accept ">=5.20.0 || >=6.0.0". A bridge written against v6 token names reads undefined on a v5 host. Because undefined in a CSS custom property means "fall through", the result is a component quietly wearing Oxygen's defaults instead of the customer's brand — no error, no console warning, no failing test. The customer sees an unbranded component and concludes the theming does not work.

Mitigation. Bridges declare a single major. A development-only check warns when the resolved theme is missing tokens the bridge expects. CI runs the bridge suite against every supported major. And the existing parity-test discipline — reading antd's shipped .d.ts and holding our surface against it — extends to the bridge's token names, so a rename fails our build rather than a customer's.

8.8 Token incompatibilities

Limitation. Some Oxygen semantics have no counterpart in any framework: status.high and status.low encode the direction of an abnormal result; the identity flags deceased, restricted and provisional are clinical concepts; the three-profile density axis is finer than either framework's sizing.

Mitigation. These are exactly the tokens marked bridgeable: false. The incompatibility is not a gap to be closed — it is the boundary of what a general-purpose UI framework knows about, and the architecture is built to respect it.

8.14 Testing complexity

Limitation. The matrix multiplies: components × themes × densities × bridges × viewports. Naively that is thousands of visual regression baselines, which is how VRT becomes noise a team learns to ignore.

Mitigation. Test the mapping, not the rendering. A bridge is verified by asserting which token lands where — cheap, fast, and it catches transposition, which screenshots do not. VRT covers a representative slice (one component per family × 3 themes × 2 bridges) rather than the full cross product. Section 9 sizes this.

8.15 Vendor lock-in

Limitation, inverted. The recommended architecture has notably low lock-in: no component depends on a framework, dropping a bridge is deleting a package, and customers can leave with a DTCG export.

The residual risk is lock-in to us — a customer whose brand lives in our console. Mitigation: export in five formats including two that theme the customer's own components, and keep the build-time path so a customer can commit their brand into their own repository and stop depending on our service entirely. Being easy to leave is a reasonable thing to sell to a healthcare buyer.

8.17 Accepted limitations

No mitigation is proposed for these. They are stated so they can be quoted.

  • An Oxygen component will never be a Material UI component. It will match colour, radius, type, spacing and motion, and it will keep Oxygen's DOM structure, its elevation model, and no ripple.
  • Clinical status colours are not customer-configurable. Subject to the decision in §10, but if the recommendation stands, this is a permanent product boundary and a sales objection to be answered rather than engineered around.
  • Framework-specific behaviours are not reproduced. antd's wave, MUI's TouchRipple, and each framework's exact focus-ring rendering stay theirs.
  • Wrapping organisms need their framework. Signature needs antd. The core is the portable part.

The repository already runs 132 test files across unit, parity, accessibility, visual regression and cross-framework E2E. This section adds what the bridge and theme layers need, and — more importantly — says what not to test, because the failure mode of a matrix this shape is a suite too slow and too flaky to be read.

9.4 Accessibility

  • axe per story × 3 themes × 3 densities × 3 bridge states — the density and theme axes exist today; the bridge axis is new, and the third theme is currently missing.
  • Forced-colors mode in all three engines, as now.
  • Keyboard traversal unchanged by any bridge — a bridge that alters focus order is broken by definition, since it should touch only custom properties.
  • Reduced-motion honoured with a bridge mounted.
  • 200% zoom and 320px reflow.
  • Contrast re-verified for every published customer theme, in CI for built-in brands and at publish time for customer ones.

9.5 Theme validation

  • Every built-in brand re-validated on every build — already implemented; northwind is the fixture.
  • Property-based testing over generated palettes: any theme the validator accepts must satisfy every floor. This is worth doing because the validator is the security boundary of the whole theming feature.
  • Adversarial themes as fixtures: all-white, all-black, monochrome, one hue, near-identical high and low. Each must be refused with a message naming the failure.
  • A migration test that a theme validated by an older validator is re-checked before serving.

9.6 Cross-framework compatibility

The test that holds the architecture

One application source, rendered under three configurations — antd bridge, MUI bridge, no bridge — asserting that the accessibility tree is identical in all three: same roles, same accessible names, same states, same focus order. Only computed styles may differ. If this test fails, framework coupling has leaked into a component, which is the one regression the whole design exists to prevent. It extends the existing e2e/frameworks.spec.ts pattern, which already drives six framework hosts through a single contract.

9.8 Quality gates in CI

The catalog-level gate already in place — pnpm gen --strict asserting that every stable component has a story, a test, zero axe violations and a VRT baseline — extends with three assertions:

  1. Every component token declaration terminates in a literal fallback.
  2. Every clinical token is bridgeable: false, and no bridge writes one.
  3. Every bridge has a mapping test, a partial-mapping test, and a size budget.

This keeps the standard holding without a human reviewing every component, which is the stated reason the gate exists.

Section 10

Final recommendation

In one paragraph

Adopt token bridging as the framework integration architecture. Keep one implementation of every component, built on the framework-free cores that already exist. Publish the --ox-<component>-* token surface as a versioned contract, and ship one small bridge per supported UI framework that translates that framework's theme onto it. Ant Design's bridge already exists and passes tests; Material UI's is the same shape and is the thing that will prove whether the contract is right. Build the customer theme console on the existing brand pipeline, with the existing validator extracted so there is exactly one definition of an accessible clinical palette. Reject the component-swapping adapter layer, because the abstraction it requires would delete the clinical features that are the product.

Roughly 12–15 weeks to an MVP where a customer configures their brand in a browser and sees Oxygen components render in it under either framework.

10.2 Recommended Ant Design strategy

Keep ADR 0010 exactly as written, and complete it. Primitives match antd's API and take no dependency — that is what makes "change the import" a real migration story and what keeps the copy-source channel alive for the form family. Organisms may wrap, with the inherited behaviour named in metadata rather than in prose. The bridge becomes a first-class package rather than a subpath of one component.

Three corrections are needed before any of this is built on: normalise the four antd dependency declarations, fix the identity documentation, and narrow bridge peer ranges to a single major so version skew fails loudly instead of producing a quietly unbranded component.

10.3 Recommended theme model

Three tiers, three axes, DTCG source — unchanged, because it is already better than most commercial design systems have. Add: customer themes as first-class documents sharing the brand file format; immutable versions with pointer-based rollback; runtime delivery as version-pinned immutable CSS with the build-time path retained; and one validator, extracted, running at all three enforcement points.

Customers configure colour, typography, spacing, radius, shadow, icons, and the component tier. They do not configure clinical status, and the reason is written down where a customer can read it.

A closing note on framing

The brief asks how to "adopt a UI framework". The most useful correction this investigation can offer is that Oxygen should not adopt one. It should be compatible with several — API-compatible where that makes migration a one-line change, visually compatible where a token bridge can carry a host's design language, and honest about the difference. That is a stronger position commercially than adoption would be, and it is very nearly where the codebase already stands.
