Platform engineering · Assessment

The pipeline is thorough, slow, and green about one thing it never does

A review of Oxygen UI's CI/CD system and local build workflow, against the actual workflow files and real run telemetry. The quality gates here are unusually strong. The problems are that one deployment job has never run, roughly 40% of every build is duplicated work, and the local pre-push check is missing four of the gates CI enforces.

17 August 2026 zoworkhq/oxygenui main @ a2eb9ad Evidence: run 32013169805, job 95323329767

Executive summary

This is a well-governed repository. The gate set is broader than most teams ship — generated-artifact drift, an executable architecture rule, bundle budgets, a WCAG audit across sixteen pages in two themes, cross-framework smoke tests in three browser engines, and a synthetic-data scan. Almost every workflow step carries a comment explaining the incident that produced it. That is rare and worth preserving.

The findings below are therefore not about missing rigour. They are about three things: one gate that silently does nothing, an execution model that has outgrown its single job, and a local workflow that has drifted from CI in exactly the places that produced this week's red builds.

The finding that matters most

The Deploy hq (production) job has never deployed anything, and reports success every time. Five of its six steps are gated on steps.gate.outputs.skip == 'false', but no step in the job declares id: gate. The expression evaluates against an empty string, every gated step is skipped, and a job whose steps all skip is a job that passes. The repository variable it checks for, VERCEL_PROJECT_ID_HQ, is set — so this is not a deliberate skip. hq has not been deployed by this pipeline at all.

What the numbers say

The most recent full run took 17m53s in a single job. Of that, 435s (41%) is spent running the test suites twice — once as Test, once as Coverage thresholds — and roughly 630s is spent on work Turbo could cache but currently cannot, because no Turbo cache is carried between runs.

A conservative rework — deduplicate the suites, cache the Turbo graph and the Playwright browsers, and split the job so independent gates run concurrently — should put PR feedback at 6–8 minutes wall clock without removing or weakening a single check.

F1 · The hq deployment has never run

Critical Deploy job green, deploys nothing confirmed

deploy-hq opens with a step named Check the project exists that writes skip=true|false to $GITHUB_OUTPUT. Every subsequent step is guarded by if: steps.gate.outputs.skip == 'false'. No step in the job declares id: gate.

An unresolvable step reference yields an empty string, so the guard is always '' == 'false' — false. Checkout, setup, deploy and the post-deploy verification are all skipped. GitHub reports a job whose steps all skipped as successful.

Evidence — job 95323329767, a run marked green on main

job conclusion: success
  success  Set up job
  success  Check the project exists
  skipped   Run actions/checkout@v7
  skipped   Run pnpm/action-setup@v4
  skipped   Run actions/setup-node@v7
  skipped   Deploy
  skipped   Verify hq is serving hq
  success  Complete job

The variable the gate looks for is present — gh api repos/zoworkhq/oxygenui/actions/variables returns VERCEL_PROJECT_ID_HQ — so this is not the intentional self-skip the comment describes. It is an unintentional total skip that would persist even after the project was created, which is precisely the case the author was trying to handle.

Root cause
A step id was never added when the guard was written. Nothing validates step references: GitHub does not warn on an unresolvable steps.* lookup, and the failure mode of the mistake is silence.
Impact
hq production receives no deployments from CI. Worse than an outage, the pipeline asserts the opposite — a green Deploy hq (production) next to a real docs deploy is actively misleading, and the post-deploy assertion (Verify hq is serving hq) is skipped with it, so nothing notices.
Fix
Add id: gate to the check step. Then make the skip visible: a skipped deployment should not look identical to a successful one. 
- name: Check the project exists
  id: gate
  env:
    PROJECT_ID: ${{ vars.VERCEL_PROJECT_ID_HQ }}
  run: |
    if [ -z "${PROJECT_ID:-}" ]; then
      echo "skip=true" >> "$GITHUB_OUTPUT"
      echo "::warning::VERCEL_PROJECT_ID_HQ unset — hq was NOT deployed."
    else
      echo "skip=false" >> "$GITHUB_OUTPUT"
    fi
Alternative
Move the condition to the job level (if: vars.VERCEL_PROJECT_ID_HQ != ''). GitHub then reports the job as skipped rather than successful, which is honest by construction and removes the per-step guards entirely. This is the stronger option; the only cost is losing the explanatory summary line.
Prevention
Add actionlint to the lint gate. It detects unresolvable steps.* references statically and would have caught this the day it was written.
Effort · Priority
15 minutes · do first. No dependencies.

F2 · Publishing is blocked on a repository setting

High Version PR refused confirmed

release.yml declares permissions: pull-requests: write. That is necessary and not sufficient: the repository switch Settings → Actions → General → Workflow permissions → "Allow GitHub Actions to create and approve pull requests" overrides it. While it is off, changeset version runs correctly and the final API call fails: 

All files have been updated. Review them and commit at your leisure
creating pull request
Error: HttpError: GitHub Actions is not permitted to create or approve pull requests.

Nineteen packages are versioned and waiting. Five consecutive release runs have failed on this call.

Impact
No npm release since the switch was last off. Nothing is half-published — merging the Version PR is what publishes, and it was never opened — so this is a stalled release train, not a corrupted one.
Fix
Tick the switch. It is scoped to this repository and stores no credential. A RELEASE_PAT secret is the alternative for organisations that keep the switch off by policy; the workflow already prefers it when present.
Status
Partially mitigated. The workflow now falls back to pushing changeset-release/main and emitting a one-click "open the PR" link, so the release is no longer fully blocked — but the switch remains the correct fix.
Effort · Priority
1 minute · do first. Requires repository admin.

F3 · No build cache between runs

High Turbo recomputes everything, every run confirmed

turbo.json declares correct outputs for build, test and test:coverage, so the task graph is cacheable. But ci.yml caches only the pnpm store (via setup-node) and the mongod binary. The two occurrences of the string "turbo" in the workflow are both inside comments. No .turbo directory is persisted and no remote cache is configured.

Every run therefore recomputes typecheck (123s), test (227s), coverage (208s) and build (74s) from cold, including for a pull request that changed one markdown file.

Impact
Roughly 630s per run of avoidable compute, on every push and every PR. This is the single largest lever available.
Fix — preferred
Turbo remote caching. Self-hosted options exist, or Vercel's — the account is already in use for deployment. Set TURBO_TOKEN and TURBO_TEAM and the cache is shared across runs, branches and developer machines, which also speeds up local pnpm verify.
Fix — no new dependency
actions/cache on .turbo, keyed on the lockfile and the commit with a restore-key prefix: 
- uses: actions/cache@v4
  with:
    path: .turbo
    key: turbo-${{ runner.os }}-${{ hashFiles('pnpm-lock.yaml') }}-${{ github.sha }}
    restore-keys: |
      turbo-${{ runner.os }}-${{ hashFiles('pnpm-lock.yaml') }}-
      turbo-${{ runner.os }}-
Turbo hashes task inputs itself, so a restored cache cannot produce a stale result — a changed input is a changed hash is a miss. This is safe for pull requests from forks because GitHub scopes caches by branch and forks cannot write to the base branch's cache.
Cache-poisoning note
Do not key a Turbo cache on the branch name alone. Key on lockfile content plus commit SHA with prefix restore-keys, so a poisoned or partial entry can never be a content-address match for different inputs.
Effort · Priority
2 hours · immediately after F1. No dependencies.

F4 · The test suites run twice

High 435s spent, ~208s of it duplicated confirmed

Test runs turbo run test && pnpm test:registry (227s). Coverage thresholds then runs turbo run test:coverage && vitest run --coverage (208s), executing substantially the same suites again with instrumentation.

The obvious fix — delete the Test step — is wrong, and the workflow comment already says so. Eight packages define test without test:coverage: 

component-meta   elements   eslint-plugin   fhir
intl             loaders    react           hq

Dropping Test would silently stop running all eight.

Root cause
Coverage was added per-package as each package earned a threshold, rather than as a workspace-wide convention. The gap was papered over by running both commands.
Fix
Add test:coverage to the eight packages that lack it — for packages without a threshold it can simply alias vitest run --coverage with no thresholds block. Then delete the Test step. Verify the suite count is unchanged before and after; that is the acceptance criterion.
Alternative
Keep both steps but let Turbo cache absorb the second (F3). Cheaper to implement, though it leaves two sources of truth for "did the tests run".
Impact
−208s per run, and one unambiguous answer to whether tests passed.
Effort · Priority
3 hours · near-term. Best done after F3 so the saving is measurable in isolation.

F5 · Local verification is missing four CI gates

High The parity gap that produced this week's red builds confirmed

scripts/verify.sh is a genuinely good idea — one command that mirrors CI, wired into pre-push via husky. Its header even says "If you add a step to ci.yml, add it here too." But it has drifted:

Gate CI verify verify --fast (pre-push)
generated artifacts, lint, format, typecheck, deps yes yes yes
tests, coverage, build, bundle budgets yes yes no
pnpm audit yes no no
synthetic-data (PHI) scan yes no no
accessibility audit yes no no
browser e2e (3 engines) yes no no

The e2e gap is not hypothetical. Three separate CI failures this week were reproducible only under a full parallel browser run, and each cost a push-wait-read cycle of roughly fifteen minutes to observe. The bundle-budget gap produced a fourth, and has since been closed.

Root cause
Nothing enforces the parity the script's own header asks for. The two lists are maintained by hand in different files.
Fix — mechanical parity
Make the gate list data, not duplication. Define the gates once (a small JSON or the package.json scripts themselves), have verify.sh iterate it, and have CI call pnpm verify rather than restating each step. A test can then assert that every CI step name maps to a known gate.
Fix — tiered local workflow
See the local development section: a three-tier model that keeps pre-push under a minute while making the full CI-equivalent one command.
Effort · Priority
3 hours · near-term. Highest developer-experience return of any item here.

F6 · Actions are pinned to mutable tags

High Supply chain confirmed

All nine third-party action references use a tag:

9 × actions/checkout@v7        7 × pnpm/action-setup@v4
7 × actions/setup-node@v7      2 × actions/upload-artifact@v7
2 × github/codeql-action/*@v3  1 × changesets/action@v2
1 × actions/cache@v4

A tag is mutable. The repository has already been bitten by this and documented it — release.yml carries a comment explaining that changesets/action renamed four inputs inside the v2 tag, breaking every push to main, and concluding: "pinning a major is not the protection it looks like. A digest pin would have held."

Impact
A compromised or merely careless upstream release executes with contents: write and, in the release workflow, with id-token: write and the npm token in scope. This is the highest-severity security exposure in the pipeline.
Fix
Pin every action to a full commit SHA with the human-readable version in a trailing comment, and let Dependabot (F14) propose digest bumps: 
- uses: actions/checkout@08c6903cd8c0fde910a37f88322edcfb5dd907a8 # v7.0.0
Trade-off
Digest pins do not auto-receive upstream security patches. That is the point — they arrive as a reviewable PR instead. Pair with Dependabot so the review actually happens.
Effort · Priority
1 hour · near-term, and higher if this repository ever handles customer data.

F7–F12 · Structural and operational

Medium F7 · One job does everything confirmed

verify runs eleven gates sequentially under one 25-minute budget. A lint error is reported seventeen minutes into the run, after the tests and the build have already been paid for. A single slow gate pushes the whole job toward its timeout — which is exactly what happened at 15m16s before the budget was raised.

Fix. Split into static (gen · lint · format · typecheck · deps · audit — under 3 min), unit (tests + coverage), and browser (build · a11y · e2e), running concurrently. Fast feedback arrives in about three minutes instead of seventeen. The cost is per-job install overhead (~20s each), which the pnpm store cache already makes cheap. Effort: 4 h.

Medium F8 · Playwright browsers re-downloaded every run confirmed

playwright install --with-deps chromium firefox webkit costs 71s on every run and is not cached. Cache ~/.cache/ms-playwright keyed on the Playwright version from the lockfile; keep --with-deps as a separate, cheap step since OS packages are not cacheable. Saving: ~60s. Effort: 20 min.

Medium F9 · Node version pinned twice confirmed

.nvmrc says 22; seven workflow steps hardcode node-version: 22. They agree today. Replace all seven with node-version-file: .nvmrc so they cannot disagree tomorrow — a CI/local Node mismatch produces exactly the "works locally" class of failure this review is about. Effort: 15 min.

Medium F10 · Deploy rebuilds what verify already built confirmed

verify runs pnpm build (74s). Each deploy job then runs vercel build, compiling the app again — three occurrences across the three deploy jobs. Beyond the duplicated minutes, the artifact that ships is not the artifact that was tested, only one built from the same commit. Uploading the build output from verify and having deploys consume it would make the tested artifact and the shipped artifact identical.

Trade-off. Vercel's --prebuilt flow expects .vercel/output, produced by vercel build rather than next build, so this is not a drop-in swap. Treat as a deliberate piece of work, not a quick win. Effort: 3 h.

Medium F11 · Visual regression never runs in CI confirmed

e2e:ci excludes the @vrt tag because the committed baselines are darwin and font rasterisation differs on linux. The reasoning is documented and correct as far as it goes — but the consequence is that 24 visual baselines are enforced only on whichever developer remembers to run them. The workflow comment already contains the remedy: generate linux baselines once inside mcr.microsoft.com/playwright:v1.56.0-jammy and commit them. Doing so also removes the darwin/linux split that makes local VRT results non-transferable. Effort: 4 h.

Medium F12 · Branch protection unconfirmed inferred

GET /repos/zoworkhq/oxygenui/branches/main/protection returns 404. That is ambiguous: GitHub returns 404 both when no protection exists and when the caller lacks admin scope, and the token used here has neither. Assumption: required status checks may not be enforced, in which case a red CI run does not prevent a merge and every gate in this report is advisory. Verify by opening Settings → Branches and confirming that Typecheck, test, build and Synthetic data check are required. Effort: 15 min.

F13–F15 · Observability and hygiene

Low Three smaller items

  • F13 · No flake detection. Playwright retries once in CI, so an intermittent test can pass on retry and leave no signal anyone reads. Three genuinely flaky behaviours were found and fixed this week only because someone was watching. Have CI surface retried-but-passed tests in the job summary, and post failures on main to a channel someone owns.
  • F14 · No dependency automation. No dependabot.yml and no Renovate config. pnpm audit --audit-level=high reports vulnerabilities but nothing proposes the upgrade. This pairs with F6: digest pinning without automated bumps produces stale actions.
  • F15 · Comment contradicts behaviour. ci.yml line 117 describes failing on "a critical advisory"; line 119 runs --audit-level=high. The behaviour is stricter than the comment, so this is documentation drift rather than a gap — but in a file this heavily commented, the comments are load-bearing.

What not to do

Do not shard the browser suite across matrix jobs yet. At 232s it is not the bottleneck, and the three engines share a webServer whose startup would be paid three times over. Revisit if it passes ~400s.

Reliability

Three flaky behaviours were diagnosed this week, and all three had the same shape: a test interacting with the page after a fixed timeout rather than after a condition. They failed only under three-engine parallel load, and each wore a different disguise — a click landing on a neighbouring element, a measurement read back stale, an element that had not appeared yet.

The durable lesson is worth encoding as a review rule: a fixed waitForTimeout before an assertion is a defect. It asserts the speed of the machine as much as the behaviour of the code, and when the machine is slower the failure is indistinguishable from the bug the test exists to catch. Prefer expect(...).toPass(), auto-retrying assertions, or an explicit signal from the component such as a data-* attribute set when it has settled.

Local development and validation

What exists, and it is good

Husky is wired with three hooks: pre-commit runs lint-staged, commit-msg runs commitlint, and pre-push runs pnpm verify --fast. The verify.sh script prints a gate list with a suggested fix command per failure. This is better than most repositories have.

The gap

--fast covers generated artifacts, lint, format, typecheck and dependency rules — everything cheap. It excludes tests, build, bundle budgets, and everything browser-based. So the checks most likely to fail in CI are the ones a developer cannot conveniently run, and the feedback loop for them is a fifteen-minute push-and-wait.

Recommended: three tiers, one command each

Tier Command Budget Covers When
Staged lint-staged < 5s Format and lint the touched files pre-commit (already)
Fast pnpm verify --fast < 60s + types, generated drift, deps, audit, PHI scan pre-push (already)
Full pnpm verify --ci ~6 min warm Everything CI runs, including a11y and e2e Before opening a PR; on request

The two additions to --fast are nearly free: pnpm audit took 1s in CI and the PHI scan is a pair of greps. Both currently exist only in CI, and both can fail a build for reasons a developer would rather learn in one second than in fifteen minutes.

The new --ci tier is the important one. It should run the a11y audit and e2e:ci, and it becomes practical precisely because of F3: with a warm Turbo cache, the build and test portions are near-instant on an unchanged tree, so the marginal cost is the browser suite alone.

Environment validation

There is a real trap in the current setup, discovered while working in this repository: running next build in apps/docs without first building the workspace packages fails with nine unresolved modules, because next.config.ts aliases two packages to their dist. That is a build-only failure invisible to typecheck and tests. It has been fixed in vercel.json, but the class remains: add a preflight that checks Node matches .nvmrc, pnpm is the expected major, and required dist directories exist — run from verify.sh and from predev.

Parity, enforced rather than intended

The single highest-leverage change in this section is to stop maintaining the gate list twice. Have CI invoke pnpm verify, and reduce the workflow to environment setup plus that one call. Then local and CI cannot drift, because they are the same list — and the four gates in F5 could never have gone missing.

Assumptions, open questions and risks

Assumptions stated, and how to check them

  • Branch protection may not be enforced. The API returned 404, which is ambiguous between "no protection" and "insufficient scope". Verify in Settings → Branches. If unprotected, every finding here is advisory and F12 becomes the highest priority item in the document.
  • hq has been deployed by some other means. The pipeline has never done it, but a manual vercel --prod may have. Check the Vercel dashboard's deployment history and its source before assuming production is stale.
  • Turbo remote caching is available on the current plan. Not verified. If not, the actions/cache fallback in F3 delivers most of the benefit within CI, losing only the CI↔local sharing.
  • The 17m53s run is representative. It is one measurement on a cold cache with all gates executing. Take a median over ten runs before and after Phase 1.

Open questions

  • Is the workflow-permissions switch off deliberately? If it is organisational policy, the RELEASE_PAT path should be adopted properly rather than left as a fallback.
  • Should apps/hq gate deployment on its own tests rather than the whole monorepo's? It currently waits for the docs e2e suite, which cannot fail for a reason that affects hq.
  • Is the darwin-only VRT baseline a deliberate long-term choice, or an unpaid debt? It determines whether F11 is worth 4 hours.

Risks of acting

  • F1 will deploy hq for the first time. Whatever is on main goes to production. Review it, and have a rollback deployment identified, before merging.
  • Caching can mask a real failure if keyed wrongly. Key on lockfile content plus commit SHA with prefix restore-keys, never on branch name alone. Turbo's own input hashing is the safety net; do not defeat it with a hand-rolled key.
  • Job splitting changes required check names. Update branch protection in the same change, or merges block on checks that no longer exist.

Risks of not acting

The ordering here is deliberate. F1 means a production system is not receiving deployments while the pipeline reports that it is — that is a correctness problem, not a performance one, and it is the only finding in this document that could already have caused harm. Everything else costs time and patience.
