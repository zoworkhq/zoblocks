The two components in the reference design are not two sizes of the same idea — one of them is a safety control, and it should be built like one.

01

What the reference design gets right, and the fourteen things it does not say

Three things in the reference are already correct and should survive unchanged into the build.

  • The hues are decorative and disjoint from status. None of the eight ring colours is the red, amber or green that means something clinically. That is the most common mistake in healthcare avatars and the design does not make it — the repo already encoded the same call as --ox-swatch-*.
  • Identity and status are visually separated. The status pill sits outside the name, not inside it.
  • The demographic line is secondary weight. Name is the loudest thing in the banner, which is right — it is the field a human actually matches on.

Then there is what the artboards cannot express, because an artboard renders one state and every one of these is about a state that was not drawn.

The thesis of this document

The avatar is a primitive worth about a day of work. The banner is a patient-safety control worth three weeks, and it is the most defensible thing this library could ship — because no general-purpose UI kit will ever build it, and every health-tech buyer has been burned by its absence.

02

Twenty-four artboards is a data structure problem

The reference sheet is a Cartesian product: 3 sizes × patientId? × patientInfo? × inactive? = 24 banner cells, plus 2 kinds × 8 hues × 3 sizes = 48 avatar cells. Seventy-two artboards for two components.

That is not a lot of design. It is a lot of design because the API is booleans, and booleans multiply. The four facts §1 says are hiding inside "Inactive" are four more flags. Sensitivity is a fifth. Disclosure level is a sixth.

// Where the boolean API ends up
3 × 2 × 2 × 2                         = 24   ← the reference sheet
3 × 2 × 2 × 2 × 2 × 2 × 2 × 2 × 2  = 384  ← the same design, honestly enumerated,
                                          each needing its own VRT baseline

The fix is not fewer states. The states are real; a record really can be a merged, restricted, deceased test patient. The fix is that none of them should be a prop. Every one of those flags is already in the resource, and the component's job is to read it, not to be told.

fields is not a visibility list — it is a priority order. The component measures its container and drops from the tail. That collapses three sizes into one component with a container query, and the small size never needs a designer to decide what disappears: the ordering already said. Demo in §8.9.

The collision arithmetic nobody runs

Swatch collisions live birthday problem, 6 buckets
Patients on screen 6 Swatches

Real FNV-1a hashing over real synthetic record ids. Colliding avatars are outlined and joined. Drag the slider: with six swatches, a collision is more likely than not from four patients onward, and certain at seven by the pigeonhole principle.

The consequence, stated plainly

On a ward round list of eight, two patients will share a colour every single time. Clinicians will start saying "the teal one", because humans reach for the fastest available discriminator. Colour therefore cannot be permitted to be the fastest available discriminator. It has to be visibly weaker than the initials it sits behind, and the component has to actively strengthen something else when a collision is detected. That is the escalation ladder in §8.6, and it is the most novel thing in this brief.

Hash the record, never the name

The obvious implementation is hash(displayName) % 6. It is wrong, and it is wrong in a way that is invisible in a Figma file and obvious in production:

  • A patient marries and changes surname. Their colour changes. Staff who had learned the record visually now have a stranger.
  • A trans patient updates their name. Same failure, with a worse meaning attached to it.
  • The banner shows the chosen name and the worklist shows the legal name. Same patient, two colours, on two screens at once.

Hash the stable resource key — Patient.id, or an identityKey the application supplies when it has something better. The colour then survives every rename, and the "same person looks the same everywhere" property that makes the swatch worth having at all actually holds.

The hash must also be deterministic across server and client. Anything seeded, anything reaching for Math.random or a module-load counter, produces a colour flip on hydration — a patient's avatar visibly changing hue half a second after the page paints, which is precisely the signal we are trying not to send.

// identity-core/src/swatch.ts — the whole thing
export function identitySwatch(key: string, buckets = 6): number {
  let h = 0x811c9dc5;                          // FNV offset basis
  for (const b of new TextEncoder().encode(key)) {  // bytes, not code units
    h ^= b;
    h = Math.imul(h, 0x01000193) >>> 0;          // FNV prime, unsigned
  }
  return h % buckets;
}

Math.imul rather than * because 32-bit multiplication overflows a double and silently loses the low bits — the classic way a hash becomes non-uniform without anyone noticing. TextEncoder rather than charCodeAt so a name in any script hashes identically on Node and in a browser. Both details exist because getting them wrong produces a bug that only appears as a colour, and nobody files a bug about a colour.

03

What the wrong-patient literature actually says, and what it implies for a header

This is the part that decides whether the banner is a layout element or a control. Five findings, each with a direct design consequence.

Adelman et al., JAMIA 2013 901,776 ordering sessions · 4,028 providers
Control — banner only, no challenge reference
ID-verify — read the patient, click OK OR 0.84 · −16%
ID-reentry — type the patient's initials OR 0.60 · −40%

Shorter is better — the bar is the odds ratio for a wrong-patient order. A banner that is only read is worth a sixth of a banner that is answered.

FindingNumberWhat it means for this component
Passive display barely helps. Re-entry helps a lot.
Adelman et al., JAMIA 2013		 ID-verify alert: OR 0.84. ID-reentry: OR 0.60. The verification mode is not a nice-to-have; it is 2.5× the effect size of the thing everyone builds. §8.11.
Photographs in the banner work.
Hyman 2012; later cohort of 2.56M orders, 71,851 patients		 Displaying the patient's photograph in the EHR banner was associated with a significant reduction in wrong-patient order entry. The photo is a safety feature, not an ornament — which is exactly why "photo failed to load" must not silently render as initials. A degraded safety control has to announce that it degraded. §8.2.
Limiting open records did not fix it.
Adelman et al., JAMA 2019, randomised		 Restricting clinicians to one record open at a time showed no significant reduction versus allowing four. The error is not "too many charts open". It is "the chart I am looking at is not the chart I think I am looking at" — a display problem, squarely inside this component's scope.
Matching fails between systems.
Pew Charitable Trusts, 2018		 Up to 1 in 5 patients may be mismatched within a single facility; match rates fall to roughly 50% when records move between organisations. An identifier without its issuing system is close to meaningless. "MRN 4471" from which hospital? The component renders the system label, always, and treats an unlabelled identifier as a defect.
Two identifiers, and never the location.
Joint Commission NPSG.01.01.01		 At least two person-specific identifiers before any care action. Room and bed number are explicitly not acceptable. Encodable. A banner in an action context takes a tuple of two-or-more identifiers, enforced by the type system, and a lint rule rejects a room number in the identifier slot. §9.
The one-line version

Everyone builds the banner that reduces errors 16%. Almost nobody builds the one that reduces them 40%, because it requires the header to know what action is about to happen. That coupling is the product.

04

What a behavioural health clinician sees in this design

Behavioural health is the hardest test case for a patient banner, which makes it the right one to design against. Get it right here and general medicine is a subset.

The name in the banner is a clinical intervention

Russell et al. (Journal of Adolescent Health, 2018) followed 129 transgender and gender-nonconforming young people. Those who could use their chosen name across all four contexts studied reported 71% fewer symptoms of severe depression, 34% fewer suicidal thoughts, and 65% fewer suicide attempts than peers who could use it in none.

A banner is a context. It is the context — it is what the clinician reads aloud in the waiting room and what sits above the note for the whole session. Rendering the legal name there because name[0] was the easiest array index to reach is not a neutral technical default.

Design rule. HumanName.use resolves in the order usual → nickname → official → anonymous for display. The legal name is reachable, but only through nameContext="legal", which requires a reason — "billing", "wristband", "identity-verification", "legal-document". Making the harmful default require typing is the cheapest guardrail in the whole component.

Pronouns come from the R5 individual-pronouns extension, which the HL7 Gender Harmony work added for exactly this purpose. They sit next to the name in a lighter weight, not in the demographics line — their job is to be read before the clinician speaks, not to be found during a chart review.

"M" is four different fields, and prescribing off the wrong one is a real harm

The Gender Harmony IG separates what the reference design compresses into one letter:

FieldFHIRWhat it is forIn a banner?
Administrative genderPatient.genderCorrespondence, registries, legacy interfacesNo
Recorded sex or genderindividual-recordedSexOrGenderWhat some upstream system recorded, with its provenanceOnly labelled
Gender identityindividual-genderIdentityAffirming interaction; demographics reportingOptional
Sex parameter for clinical usepatient-sexParameterForClinicalUseInterpreting a result, sizing a dose, choosing a reference rangeYes, labelled

Only the fourth belongs anywhere near a prescribing surface, and it must carry its own label — SPCU: female-typical, not a bare "F". A prescriber who reads a lone "M" and reaches for a male reference range on a patient whose SPCU says otherwise has been misled by the user interface, not by the data.

Concrete proposal. PatientBanner refuses to render Patient.gender at all. If an application passes "gender" in fields, it gets a development-time error naming the four alternatives. That is opinionated, it will annoy someone in week one, and it is the correct call.

The banner is a disclosure surface

In the US, substance use disorder treatment records are governed by 42 CFR Part 2, which is stricter than HIPAA: the fact that a person is in such a programme is itself protected. A banner rendering Care team: MAT Clinic on a monitor angled toward a corridor has disclosed it.

HL7 already has the vocabulary. meta.security carries sensitivity codes from ActCode:

CodeMeaningBanner behaviour
PSYPsychiatry-related sensitivityProgramme and care-team names suppressed below disclosure="full"
ETHAlcohol / drug-abuse relatedAs above, plus a Part 2 marker in the reveal dialog
HIVHIV / AIDS relatedAs above
SDVSexual assault, abuse, domestic violenceAs above, plus address and contact suppressed by default

HTESTTest recordHatched, unmistakable, and never orderable-looking

The component does not decide policy and does not log. It reads the label, renders the reduced form, and fires onSensitiveReveal({ patientId, codes, at }) when a user breaks the glass. The application owns the audit trail — a component that wrote its own would be writing PHI from a browser, which ARCHITECTURE.md §9 forbids for good reason. Working demo in §8.8.

Six more things that only show up in this setting

  • The photograph is not neutral. An intake photograph taken during an involuntary admission was not meaningfully consented to, and a small square portrait on a clinical header reads to some patients as a booking photo. Photos must be a provider-level opt-in — photos: "deny" is a legitimate site configuration and the component must look complete without them, not degraded.
  • "Inactive" is a word with a body count. Here it can mean discharged, disengaged, transferred, or died. Sending an automated appointment reminder to a patient who died by suicide, because the record said "inactive" and the reminder job only checked deceasedBoolean, is a documented category of harm to families. Four states, four renderings, no shared pill.
  • Flags describe behaviour, never people. Banners are where "non-compliant" and "drug-seeking" get attached to a human permanently. CONTENT.md §8 already forbids it; the component enforces it by refusing to render a Flag without a text label, an author, and a date. If nobody will put their name to it, it does not go in the header.
  • Risk flags need an expiry. An elopement or self-harm marker still lit six months after the episode has stopped being information and started being a label. Render Flag.period; when it has ended, the flag leaves the banner and goes to history.
  • The screen faces the patient during telehealth. Screen sharing puts the banner in front of the person it describes, including any risk flag on it. A disclosure="shared-screen" level and one keyboard shortcut to reach it costs almost nothing and wins demos.
  • Continuity is therapeutic. The same patient looking identical on every screen is not a visual-polish argument here. In a service where a person is handed between six staff in a week, consistent identity rendering is part of how the team keeps hold of who they are treating.

The engine: @oxygenui-design/identity-core

Same shape as signature-core: React-free, antd-free, no DOM. Everything hard and everything clinical lives here, which is what makes it testable without a renderer and portable if the framework call ever changes.

// ── The value type ─────────────────────────────────────────────────
export interface Identity {
  key:          string;               // what the swatch hashes; never the name
  name:         ResolvedName;           // display + legal, kept apart
  pronouns?:    string;               // individual-pronouns
  birthDate?:   PreciseDate;            // value + precision, never widened
  age?:         Age;                    // { text, asOf, atDeath }
  identifiers:  ResolvedIdentifier[];   // each with its system label
  spcu?:        CodedValue;             // sex parameter for clinical use
  states:       IdentityState[];        // never one boolean
  sensitivity:  SensitivityCode[];      // PSY | ETH | HIV | SDV | R | V | HTEST
  photo:        PhotoState;             // five-valued, never undefined-as-absent
  swatch:       number;               // 0..5, decorative, aria-hidden
}

export type IdentityState =
  | { kind: "inactive"; since?: PreciseDate }        // Patient.active === false
  | { kind: "deceased"; date?: PreciseDate }         // deceased[x]
  | { kind: "merged"; into: Reference; on?: PreciseDate }// link[replaced-by]
  | { kind: "test" }                                  // meta.security HTEST
  | { kind: "restricted"; codes: SensitivityCode[] };

export type PhotoState =
  | { kind: "present"; src: string }
  | { kind: "none-on-file" }             // the record has no photo
  | { kind: "unavailable" }              // it has one; we could not fetch it
  | { kind: "withheld"; reason: string }   // policy said no
  | { kind: "loading" };

// ── Five functions. That is the entire public surface. ─────────────
export function resolveIdentity(p: Patient, policy: IdentityPolicy): Identity;
export function identitySwatch(key: string, buckets?: number): number;
export function identityInitials(n: ResolvedName, locale: string): string;
export function identityLabel(i: Identity, policy: IdentityPolicy): string;
export function disambiguate(set: Identity[]): Map<string, Escalation>;

disambiguate is the one worth staring at. It takes what is actually on screen and returns, per identity, the minimum extra fields that make that identity unique within the set:

export interface Escalation {
  reason: "same-family-name" | "same-birth-date" | "similar-name" | "same-swatch";
  add:    Field[];    // e.g. ["given-full", "dob"] — appended, never substituted
  mark:   boolean;   // render the "similar name on this list" marker
}

// The ladder, applied in order, stopping at the first step that separates them:
//   1. full given name        A. Okonkwo   → Amara Chinelo Okonkwo
//   2. date of birth          + 08 Mar 1985
//   3. primary identifier     + MRN 123 456 789
//   4. force the photograph   (overrides field-drop, never overrides policy)
//   5. explicit marker        ⚠ Similar name on this list

The similarity test is deliberately two algorithms, because they fail differently:

// identity-core/src/similarity.ts
export function looksAlike(a: string, b: string): boolean {
  const na = fold(a), nb = fold(b);        // NFD, strip marks, casefold
  if (na === nb) return true;             // Nguyen vs Nguyên
  if (jaroWinkler(na, nb) > 0.92) return true;  // Okonkwo vs Okonjo
  return doubleMetaphone(na)[0] === doubleMetaphone(nb)[0]; // Smyth vs Smith
}
// 0.92 rather than 0.90: at 0.90 "Ahmed"/"Ahmad" and "Khan"/"Khan" behave, but
// so do half the surnames on a South Asian ward, and a list where every row is
// escalated is a list where nobody reads the escalation.

Why this belongs in the library and not the application. Every hospital that has thought about it runs a "name alert" programme on paper. No component library has ever offered it, because it requires a component to know about its siblings — which is exactly the kind of thing a design system is well placed to provide and an application team will never get around to building.

07

Motion: what is allowed to move on a patient's identity

This section exists because the reference sheet is static and therefore silent, and because identity is the one component where a tasteful transition can be a clinical defect. Everything here is a rule, not a preference.

The eight rules

#RuleWhy
1Motion means "this changed." Nothing on an identity moves for any other reason.A banner that animates because a sibling panel finished loading has told the reader something changed about the patient. It hasn't.
2A patient swap animates the whole block as one unit. Never field-by-field, never staggered.Staggering lets a reader catch the old MRN beside the new name for 80 ms. That is a wrong-patient hazard created by the animation. This is the single most important line in the section.
3Photographs hard-cut. Never cross-fade.A dissolve between two faces produces, for about 100 ms, a face that is neither person. Animate the container; swap the image on a single frame.
4The skeleton shimmer is the only loop in the component.Everything else is a transition with an end. A looping animation on a clinical header becomes furniture within a day and then hides the one time it means something.
5Information animates in, never out.When disambiguation adds a DOB it slides in. When the collision clears, the field disappears on the frame — a graceful exit means it is still readable while it is leaving, and readable-but-stale is the problem this component exists to prevent.
6Error and mismatch states have zero entrance duration.A wrong-patient block must be present the instant it is true. Animating it in leaves a window in which a keystroke can still land on the form underneath.
7Nothing on a clinical header exceeds 200 ms.Above 200 ms a clinician has already begun reading. The transition then competes with comprehension rather than supporting it.
8prefers-reduced-motion removes motion; it does not soften it.Every transition becomes an instantaneous state change. Not a shorter fade — a fade at any duration is still a period during which two states are simultaneously legible.

The QA checklist a human runs

Record the patient swap at 240 fps and step through it. If any single frame contains one patient's name beside another patient's identifier, the transition is wrong regardless of how it looks at speed. That test is cheap, it is objective, and it is the only motion check in this library that is about safety rather than taste.

Six invariants the compiler holds, so a reviewer does not have to

At 24 components a reviewer catches this. At 500 they do not. Everything here is mechanical.

// 1 · Two identifiers before any action. NPSG.01.01.01 as a type.
type TwoOrMore<T> = readonly [T, T, ...T[]];

type BannerProps = { patient: Patient; fields?: Field[] } & (
  | { context: "navigation";               identifiers?: IdentifierSpec[] }
  | { context: "action" | "verification"; identifiers:  TwoOrMore<IdentifierSpec> }
);

// 2 · The legal name costs a sentence.
type NameContext =
  | { nameContext?: "display" }
  | { nameContext: "legal"; reason: "billing" | "wristband"
                                    | "identity-verification" | "legal-document" };

// 3 · Patient.gender is not renderable. Four alternatives, named in the error.
type Field =
  | "photo" | "name" | "pronouns" | "dob" | "age"
  | "spcu" | "gender-identity" | "recorded-sex-or-gender"
  | "mrn" | "identifier" | "ward";
//  "gender" is deliberately absent. @ts-expect-error is the review conversation.

// 4 · Identity is atomic — a partial resource cannot be rendered as whole.
type PatientInput =
  | { patient: Patient }
  | { loading: true }
  | { error: OperationOutcome };
//  There is no shape that carries a name without its identifiers. §8.4.

// 5 · One banner per screen, asserted at runtime in development.
// 6 · PatientGuard: an action's patient must equal the displayed patient.

Invariants 5 and 6 cannot be types, so they are context assertions that throw in development and render a blocking, non-dismissible error in production. That is deliberate: for a wrong-patient mismatch, a broken screen is the correct output. The alternative is a working screen showing the wrong human.

Three lint rules ride alongside, in the existing plugin:

  • @oxygenui/no-room-number-identifier — a location in an identifier slot. NPSG says it explicitly.
  • @oxygenui/no-truncated-identity — text-overflow or a truncate class on a name or identifier node.
  • @oxygenui/identity-requires-key — an IdentityAvatar whose swatch key is derived from a name rather than a stable id. §2.

Accessibility: one label, and a change nobody announces

The default accessible rendering of the reference design is seven fragments — "J H", the name, "Inactive", "M", "39y", a date, an identifier — that a screen-reader user has to reassemble into a person.

The avatar says nothing

aria-hidden="true", always, when it sits beside the name. It adds no information a non-sighted user can use, and alt="Photo of Amara Okonkwo" is both noise and a small PHI leak into any tooling that scrapes alt text. The swatch is decoration by definition — the tokens file says so — so it cannot be exposed as meaning.

11

Five thousand rows

A patient chip is the one component in a healthcare product that renders thousands of times on one screen — population health dashboards, panel management, claims worklists, bed boards. Worth being unusually careful about.

One node, not three

The obvious avatar is a wrapper, an inner span for initials, and an <img>. At 5,000 rows that is 15,000 elements for decoration. One element with the tint on a custom property and the photo as a background-image is 5,000. Style recalculation and memory both scale with node count, and this is the cheapest 3× anyone will find in the whole library.

The cost is that a background-image has no onError, which is exactly the "could not load" state §8.2 insists on. Resolution: the list variant is single-node and resolves photo availability in the data layer, while the banner variant — of which there is one per screen — uses a real <img> with a real error handler. Different constraints, different implementations, one API. That asymmetry should be written down rather than discovered.

Resolve once, not once per render

// A bounded LRU in the engine. Initials, swatch and label are pure functions
// of (identityKey, policy) and never change within a session.
const cache = new LruMap<string, Identity>(2000);
const cacheKey = `${identityKey}|${policyVersion}`;

The policy version in the key is what makes a disclosure-level change or a locale switch invalidate correctly, rather than leaving 2,000 patients rendered under the previous policy — which, given what disclosure level controls, would be a privacy defect and not a performance one.

What this reuses rather than rebuilds

The colour layer needs nothing — --ox-swatch-1..6 and the --ox-flag-* family already exist, already have the high-contrast collapse, and already carry the "a hue that means nothing" rationale in their $description. Nine helpers in @oxygenui-design/fhir are directly reusable. The generator, the coverage manifest, the lint plugin and size-limit are all already wired. That is Phase 0 of the architecture paying for itself.

What only you can decide

#QuestionMy recommendation
1antd or registry — for this component? The deferred call from Signature comes due here.Both, and let the engine absorb the cost. identity-core is React-free and antd-free, which is where 70% of the work is. Ship IdentityAvatar and PatientChip to the shadcn registry as copy-source with the engine vendored, and PatientBanner as an antd-wrapping npm package. The banner is the one that wants antd's Popover, Tooltip and RTL provider; the other two want three files and no dependencies. You will know within a month which channel the pull is actually coming from.
2Six swatches or eight? The reference wants eight; the tokens ship six.Six. The slider in §2 shows what the two extra hues buy: about 13 points at n=4, and nothing at all past n=8. They cost two more colours that have to prove they mean nothing, and after red, amber, emerald, blue and violet are spoken for the remaining space is genuinely thin. Collisions get handled, not avoided.
3Is the banner free or Pro?Banner free, verification Pro. The banner is what gets Oxygen into an evaluation — it is the component a health-tech CTO screenshots for their team. PatientBanner.Verify and wristband matching are what a hospital's safety committee will pay for, and they are the parts that need clinical review to stand behind, which matches the services-and-contracts model rather than a volume licence.
4Does PatientBanner really refuse Patient.gender?Yes, and I would not soften it. Someone will file an issue in week one saying their FHIR server only populates gender. The right answer is the documented escape — fields: ["recorded-sex-or-gender"], which renders it labelled as what it is — rather than a bare "M" a prescriber can mistake for a clinical fact. This is the kind of refusal a clinical-safety reviewer notices and remembers.
5"Chip", or antd's "Tag"?Keep PatientChip. antd's Tag is a label on a thing; this is a reference to a person, and calling it a Tag invites people to put it in a Tag-shaped slot where a name will get truncated. The naming rule from the loaders — name the real artifact — points the same way.
6Which regulatory frame is v1 written against? Part 2 and NPSG are US; India has DPDP and ABHA; the UK has NHS numbers and Caldicott.Build the mechanism, configure the jurisdiction. Sensitivity codes, disclosure levels and identifier systems are all data. Ship US and India configurations in v1 — that is where Zowork's buyers are — UK in v2, and never hard-code a regulation into a render path. The moment if (is42CFRPart2) appears in a component, the component is jurisdiction-specific and the next market is a fork.
7Do the motion rules go in DESIGN.md or stay component-local?DESIGN.md, and add a line to the interaction-rules checklist. Rules 2, 3 and 6 are not about identity — they are about any component where two records can be on screen during a transition, which will eventually include the medication card, the results table and the encounter switcher. Writing them down once, now, is a week of work saved three components from here.
If you only take one thing from this document

Build disambiguate(). It is about 200 lines, it needs no design approval, it is the only idea here that no other component library has, and §8.6 is demonstrable in ten seconds to anyone who has ever worked a ward — two identical rows become two distinguishable ones and the room goes quiet. Everything else in this brief is good engineering. That one is the argument for the product.

Oxygen UI is not a compliance boundary. It does not make an application HIPAA, GDPR, or DPDP compliant, and it is not a medical device or clinical decision support.
