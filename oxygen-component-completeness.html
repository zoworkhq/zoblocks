The one finding that matters

30 of the standard's 50 fields are populated on exactly zero components. Not thinly adopted — unimplemented. They fall into four groups, and each group is a whole capability the standard promises and the library cannot currently deliver:

Group · zero adoption

Domain (7 fields)

domain.industries, clinicalContext, workflows, phi, auditable, permissions, terminology.

Without industries the Clinical region cannot render on any page, and it is the field that decides whether a component gets clinical documentation at all. This is the healthcare differentiator, and it is the group with the least code behind it.

Group · zero adoption

Discovery (9 SEO fields)

No primaryKeyword, so the uniqueness constraint that prevents cannibalisation cannot be enforced. No ogImage, no searchIntent, no schema-owned canonical.

The docs site does emit a title, description and canonical today from generateMetadata — but hand-derived, not from the schema, so none of it is gateable.

Group · zero adoption

Examples & fixtures (2 fields)

No component declares a single structured example or a named fixture. The standard requires one example for Beta and three for Stable, so on this gate alone every component fails Beta.

Prose usage strings exist and are good. They are not examples: nothing renders them, nothing tests them, and they cannot seed a playground.

Group · zero adoption

Playground & graph (7 fields)

variants, controls, a11yChecks, and four relationship edges. controls is the one that hurts: the playground in §6 is generated from it, so no component can have a generated playground.

builtWith / usedIn are derivable from imports and were never wired, so the relationship graph — which the standard uses for navigation, discovery and internal linking — does not exist.

What is genuinely good, and worth protecting

Every one of the 16 has unit tests. Props are extracted from TypeScript, not hand-written — 317 of them across the catalogue. States are declared (153 in total) and accessibility notes are substantive (80). Every summary is inside the 160-character cap. That is a stronger base than most libraries have at v1, and it is why the remediation below is measured in weeks rather than quarters.

02 · Method

What was measured, and what could not be

Three sources, all generated by the repository itself: apps/docs/src/lib/generated/catalog.ts (the metadata every page reads), apps/docs/public/r/coverage.json (the existing quality gate's evidence), and the component files on disk. A field counts as present only when it is non-empty.

Two things this audit deliberately does not claim

It does not measure visual or interaction quality. Whether a component looks right, animates well, or survives a screen-reader pass is not in the metadata and is not inferable from it. Those were assessed separately in the phase-two audit and are not restated here.

Eight of the eighteen Stable gates are reported as failing for a structural reason — the field they read does not exist in the schema yet. That is honest rather than harsh: a component cannot pass a gate whose input has not been implemented. Those eight are marked in §6 as no component passes, which is a statement about the platform, not about any component's author.

Defect 01 · relationship graph

5 components declare no related component

Copilot, Switch, Patient identity, Signature, Tabs. The standard requires related to be bidirectional and validated, so these are not merely empty — they are holes that will fail the graph-integrity check the moment it is switched on. They are also the four package-distributed components, which is where a newcomer is most likely to land.

Defect 02 · story coverage

3 components have no story

Patient identity, Signature, Tabs. Stories are the VRT fixtures, so a component without one has no visual-regression baseline — and the standard seeds the VRT matrix from states, which these components do declare. Documented but unrendered.

Defect 03 · thin guidance

1 component below the useWhen floor

Helix Loader has fewer than the three useWhen entries the standard requires. Minor and quick, but it is the section AI answer engines quote, so it is worth more than its size suggests.

08 · Two defects in the standard itself

The audit found problems with the specification, not only with the components

Correction 01

fhir cannot be universally required

The standard lists fhir as required. Twelve components leave it empty and are right to: a loader, an accordion, a switch and a tab strip consume no FHIR resource, and forcing a value would produce exactly the "FHIR undefined React component" title the docs site already guards against.

Fix: make it conditionally required — mandatory only when domain.industries contains a clinical value. This audit scores it that way.

Correction 02

frameworks was mis-filed as new

§11 lists frameworks among the 32 new fields. It already ships, and is populated on the four package-distributed components (Copilot, Patient identity, Signature, Tabs).

Fix: move it to the shipping set. The real work is adoption on the other twelve, not implementation — which makes it one of the cheapest items on the plan.

09 · Remediation

Four moves, ordered by how many components each unblocks

Ordered by leverage rather than by section number. Every item below moves all 16 components at once, because every gap is a platform gap.

1
Schema · unblocks all 16 · ~2 weeks

Add the 30 missing fields and backfill

Extend defineComponentMeta() with the domain, examples, discovery, playground and relationship groups. Backfill the 16 existing components. Nothing is visible at the end of this and everything else is blocked on it.

Done when: pnpm gen --check is green with the new schema and all 16 validate.

2
Template · unblocks 9 regions · ~3 weeks

Replace the six-section page with the fifteen-region template

The current page is bespoke and renders Preview, Usage & props, Guidance, Quality, Source and Related. Generate it instead, and the nine missing regions appear for every component simultaneously.

Done when: no component has a hand-written page file.

3
Content · the per-component work · ~1 week

Close the three content defects, then examples

The quick ones first: 5 missing related edges, 3 missing stories, 1 thin useWhen. Then the real work — one example per component for Beta, three for Stable, each with a named fixture. This is the only item that does not scale by platform work.

Done when: every component clears the Beta content gates.

4
Discovery · the last 8 gates · ~2 weeks

The SEO emitters and the relationship graph

Derive builtWith from imports, invert to usedIn, validate bidirectionality. Emit sitemap, JSON-LD, OG images. Enforce primary-keyword uniqueness. These are the eight gates currently failing everywhere for want of an emitter.

Done when: a component can reach Stable.

The honest bottom line

No component is close to Stable, and none can be until the schema and the template land — the remaining failures are almost entirely platform gaps, not authoring gaps. The components themselves are in better shape than the scores suggest: tests, props, states and accessibility are all done properly. What is missing is everything that makes a component discoverable and adoptable by someone who did not write it.
