The healthcare surface area,drawn to scale.

Oxygen UI ships twenty-nine components today. This document proposes the other one hundred and thirty-nine — the full set a team needs to build a provider workspace, a behavioral-health platform, a telehealth product, or a patient app without reinventing clinical semantics on every screen.

Every component is specified against FHIR R4 resources, carries its own definition of what absence and uncertainty look like, and is sized honestly for the engineering it will actually take.

The argument

A generic component renders a value. A healthcare component renders what the value means.

Every design system solves tables, dialogs, and menus. None of them solve a result that came back preliminary, a reference range that does not exist for a two-year-old, a record the viewing clinician is not permitted to open, a medication list that disagrees with the one the patient recites, or a PHQ‑9 where item nine is non-zero and the workflow must change in the next fifteen seconds.

Those are not edge cases. In healthcare they are the normal working set, and they are where teams lose their quarters — rebuilding the same escalation logic, the same restricted-record affordance, and the same audit trail on every screen, slightly differently each time.

This library is scoped to absorb that work once. Each component below is specified to a FHIR R4 resource, so a team passes the payload it already has rather than mapping into a bespoke prop shape. Each one declares its own loading, empty, error, offline, permission-denied, and restricted states, because a blank cell and a failed fetch must never look alike.

The result is a system a product team can adopt for its semantics, not just its styling — and audit line by line, because the source is copied into their repository.

What this library does not claim

Oxygen UI is not a compliance boundary. Installing it does not make an application HIPAA, GDPR, or DPDP compliant, and it is not a medical device or clinical decision support. Access control, audit storage, data residency, and clinical validation remain the implementing team's responsibility. Every component here is designed to make those obligations easier to meet and visible when unmet — never to stand in for them.

Design principles

Seven rules every component in this proposal is held to.

Four are inherited from the shipped library. Three are added here because a catalog of this size fails in ways a catalog of nine does not.

01 · Inherited

Absence is a state

A missing value renders as explicitly missing. A blank cell is indistinguishable from a rendering failure, and in a chart or a medication list that ambiguity is dangerous. No result recorded and 0 are different facts and never share a treatment.

02 · Inherited

Never color alone

Every severity carries a color, an icon, a text label, and a structural cue such as a rule or an indent. Components stay readable in forced-colors mode, in grayscale, and on the printed chart that still drives a surprising amount of clinical work.

03 · Inherited

Don't infer clinical meaning

An interpretation stated in the payload always wins. Where none is stated, it is derived only by comparing a value to its own reference range. Nothing else is guessed, and an uninterpreted result reads Not interpreted — never Normal.

04 · Inherited

Synthetic data only

Every fixture, demo, and screenshot — including all sample data in this report — uses invented values on reserved example.org systems. No PHI enters the repository, its issues, its analytics, or its documentation.

05 · Added

Density is a contract, not a preference

The same component serves a patient reading on a phone and a nurse scanning ninety rows. Density is set by the container through data-ox-density and changes spacing and target size — never which facts are shown. Hiding a clinical fact to save a row is a defect.

06 · Added

Consequential actions are two-step and attributable

Anything that changes a clinical record, a medication, a schedule commitment, or a consent state confirms first and emits a structured audit event after. Components expose the event; persisting it is the application's job, and the component says so in its own documentation.

07 · Added

Sensitive data degrades safely

Behavioral health, substance use, reproductive care, HIV status, and minor records can each be restricted independently of the rest of the chart. The default render is the redacted one; disclosure is a deliberate, logged, reversible act with the reason captured.

How the catalog is organised

Two axes: twelve categories by subject, eight tiers by role.

Categories answer "where does this live in the product." Tiers answer "who depends on it and when do we build it." Every component carries one category and one or more tiers, and both are filterable in the index below.

Complexity scale

A blunt estimate of design and engineering effort for one component, including its states, tests, and documentation. It is not a measure of importance — several of the most important components in this catalog are the simplest.

1Presentational, few states. Days.
2Composed, interactive, standard a11y. ~1 week.
3Stateful, async, non-trivial keyboard model. 2–3 weeks.
4Virtualised, real-time, or clinically consequential. 4–6 weeks.
5Multi-surface subsystem with its own state machine and clinical review. A quarter.

Nothing in this catalog scores 1, which is deliberate: the scope excludes buttons, basic cards, and generic form fields. The distribution is 11 components at 2, 42 at 3, 77 at 4, and 38 at 5 — a median of 4, which is an honest statement about what this library costs to build.

Priority

Priority reflects what a digital-health team hits in the first month of building — the components whose absence blocks a demo — weighted by how badly the ecosystem currently serves them.

P0Blocks a credible product demo. Ship in wave one or two.
P1Needed before a real pilot with real users. Waves two and three.
P2Differentiating, not blocking. Wave three or four.
P3Commercial or specialist surface. Build on customer pull.

Interaction states

Eight states every component defines before it ships.

An unfilled state is not a formatting problem — it is an unmade decision. These are the default treatments; each component in the catalog above lists the edge cases that force it to deviate.

Loading

Layout-shaped, never value-shaped. A skeleton in the shape of a lab result invites the reader to fill in the blank. Shimmer is removed under reduced motion.

Empty
No allergy information recorded

This is not the same as no known allergies. Ask and record before prescribing.

The distinction between an absent record and a recorded negative has caused documented harm. Copy here is clinically reviewed, not written by design.

Error
Medication list could not be loaded

The pharmacy system did not respond. This section is incomplete — do not treat it as the full list.

Names what failed and what it means clinically. A partial list rendered as complete is the dangerous outcome this state exists to prevent.

Offline
Offline · showing data cached 08:41

1 note queued. It is not saved to the record yet and will sync when you reconnect.

Never implies a queued action has been recorded. Staleness carries its cache time, because "recent" is not a clinical unit.

Permission denied
Restricted under 42 CFR Part 2

Your role cannot open this section. Emergency access requires a stated reason and is reviewed.

Absent-because-hidden is a different fact from absent-because-unrecorded. Conflating them misleads the clinician in both directions.

Success
Result acknowledged

Recorded for A. Bensouda, MD at 06:46 ET with the action you selected. Entered in the audit log.

Confirms what was recorded, by whom, and that it is attributable — the properties that make an acknowledgement defensible later.

Critical
Potassium 6.8 mmol/L · critical high

Requires acknowledgement. Escalates to covering clinician in 42 seconds.

Interruption is a scarce resource. Only this tier is permitted to take it, and dismissal is recorded with an actor and a reason.

Focus & hover

Focus is never removed, never subtle, and never dependent on hue alone. Try tabbing this page — the ring is the same everywhere.

Implementation sequence

Four waves. Each one ends at a gate, not a date.

The ordering is not by category and not by priority score alone. It follows dependency: the primitives that every other component composes must be stable before anything composes them, and a change to a foundation after wave two is a change to a hundred and fifty components. Numbers here are a genuine sequence, which is why they are numbered.

Wave0134 components

Foundations, and everything that blocks a credible demo

The entire Foundations category plus the identity, results, and navigation primitives a prospective customer sees in the first ten minutes. Nothing here is impressive on its own; everything downstream is wrong without it. The already-shipped components are re-based onto these primitives in this wave rather than left on their current bespoke internals.

Wave0229 components

The behavioral-health flagship

This is the differentiating wave and it should be built before the general clinical depth in wave three. The instrument engine is the single highest-leverage component in the catalog: every behavioral-health programme uses a different set of measures, and a library that renders any Questionnaire with correct scoring is worth more than a library with nine hard-coded ones. It also answers the open question in the strategy file about whether a FHIR Questionnaire renderer is a stronger flagship than the patient card — it is.

Three recommendations that cut across the waves

Build the engine, not the instrument

Nine hard-coded assessments is a demo. One renderer that takes any Questionnaire and scores it correctly is a product. The same argument applies to the data grid, the note template engine, and the consent model — prefer the general mechanism wherever the domain varies by customer.

Ship states before you ship breadth

A component with eight correct states beats three components with only a happy path. The states are the actual differentiator against every generic library, and they are what a clinical reviewer looks at first. This is also the cheapest quality signal to demonstrate in documentation.

Let clinical review gate the release

Every component tagged Clinical & behavioral health needs a named clinical approver before release, and that name belongs in the repository. It is the credential this library will be bought on, and it cannot be retrofitted after a safety question is raised by a customer.
