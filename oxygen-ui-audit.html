01 — The verdict

A strong spine and a small body

Oxygen has a metadata generator, a contrast-gating token validator, and six domain-specific lint rules that are better than what most Series-B companies ship. Against that, it currently contains five components in one category, all beta, and the distribution and institutional layers are largely absent. The gap is not quality — it is surface area and readiness.

Genuinely excellent

  • Generator: adding a component touches one directory
  • Token validator gates on contrast and 60° hue separation
  • Components structurally cannot fetch, log, or read env
  • axe in CI, 9 pages × 2 themes, passing
  • Zero hardcoded hex in shipped source

Partly built

  • Testing: 439 tests, but one layer of eight
  • Quality gate exists and cannot be switched on
  • Cross-framework: shipped and broken under SSR
  • Release automation without release gates
  • Docs site whose props tables are wrong

Absent

  • Every governance file — contributing, security, owners
  • Storybook, visual regression, E2E, coverage gates
  • A React package installable from npm
  • i18n, despite an ADR warning about the deadline
  • Dependency scanning, SAST, SBOM

02 — Triage

Eight critical findings

Each was verified by running something, not by reading. Three would be visible to a customer today.

C1Ship blocker

The npm package crashes on import in Node

class OxLoaderElement extends HTMLElement evaluates at module scope. Any server-rendering context — Nuxt, Angular Universal, Astro, SvelteKit, a Next.js server component — throws before the loader renders. The package README explicitly promises Nuxt and Angular Universal support.

$ node -e "import('./dist/index.js')"
ReferenceError: HTMLElement is not defined
packages/loaders/src/base.ts:135 · jsdom tests passed because jsdom provides HTMLElement; there is no Node-environment test
C2Broken now

CI on main fails on the next merge

The docs deploy gate fetches a registry item that no longer exists, then pipes an empty body into JSON.parse. It also asserts a FHIR dependency that no current component has.

.github/workflows/ci.yml:265
url="https://oxygenui.design/r/vitals-panel.json?ci=${GITHUB_SHA}"
$ ls apps/docs/public/r/ | grep -c vitals → 0
C3Adoption blocker

The documentation understates every API by 95%

The props table for pulse-loader renders one prop. The component has about twenty. The extractor deliberately excludes props not declared in the component's own file — a rule written to hide 280 inherited HTML attributes, which now also hides Oxygen's own shared interface.

scripts/gen/props.ts:141
if (path.resolve(declaration.getSourceFile().fileName) !== path.resolve(ownFile)) continue;
generated catalog → prop count: 1 · extendsType: "LoaderCommonProps"
C7WCAG failure

Three contrast failures are shipping in the light palette

All three sit outside the validator's checked pair list. The focus indicator is the serious one: it governs every focusable element in every component Oxygen will ever ship, and it is well under the 3:1 floor.

focus-ring #10b995 on bg #ffffff = 2.50:1  (needs 3:1 — SC 1.4.11 / 2.4.11)
text-on-accent #ffffff on accent #059478 = 3.81:1  (needs 4.5:1 — SC 1.4.3)
border-strong #cbd5e1 on bg = 1.48:1  (needs 3:1 — backs --ox-field-border)
C8Live defect

The published tokens package predates the token pipeline

@oxygenui-design/tokens@0.1.0 on npm is nine days behind the source and still contains a bug fixed in the repository: an eight-digit zero-alpha surface-overlay that renders every dialog and popover fully transparent. No changeset is pending to correct it. The shadcn channel serves current CSS; the npm channel does not.

npm view → published 2026-08-05 · 4 files, 2 exports  (repo: 12 files, 6 exports)
tag predates pipeline commit 4bacb7e (2026-08-13)
packages/tokens/tokens/semantic/dark.json:13 documents the fix
C4Process

Releases are gated on less than merges are

The release workflow runs install → build → test → tarball → publish. No lint, no typecheck, no format, no generator drift check, no PHI scan, no accessibility audit — and no dependency on CI having passed. A commit with red CI can publish to npm.

.github/workflows/release.yml:48–78  — compare ci.yml, which runs eight gates
C5Security

One critical and five high advisories

All in build tooling — vitest, vite, esbuild, nanoid, and postcss/sharp via Next. The published runtime surface has zero dependencies and is clean. That distinction will not survive a procurement reviewer running npm audit and seeing "critical".

$ pnpm audit → {"moderate":5,"high":5,"critical":1}
C6High

The README installs a component that no longer exists

Five references to vitals-panel and ObservationPanel, including the primary install command and the quick-start example. Both 404.

README.md:27, 29, 51, 59, 163

Ownership note

C1 and C2 were introduced during the most recent work stream — the SSR crash because the element tests run in jsdom, which supplies HTMLElement, and the CI break because a deleted component was still named in a deploy gate. Both are cheap to fix. The absence of a Node-environment import test is the more important defect, and it is on the Phase 0 list.

04 — Architecture

Two implementations held together by a test

This is the central architectural finding. The React components and the custom elements are independent hand-written implementations of identical behaviour, reconciled by assertions a human wrote. That parity suite caught a mistyped bezier control point and a NaN-handling divergence within its first run — evidence both that it works, and that divergence is the normal case rather than the exception.

Current — two sources5 components · parity by hand

        ╎  test/loader-parity.test.ts — 62 assertions,

   │
   └─► packages/elements custom elements for Vue / Angular / Svelte / HTML
            └─► optional typed wrappers, added on customer demand

Why the copy-source channel stays

“The source lands in your repository where you can read every line before you trust it” is a genuinely strong argument in a healthcare procurement review. The change is not to remove it — it is to generate it from the React package so it stops being a second place where behaviour is written.

Other structural weaknesses

  • No React npm package at all — copy-source is the only React channel, so there is no versioning or upgrade path
  • loader-core exports 20 symbols and is copy-source: all of it is public API, with no extraction guard
  • The docs app doubles as the registry CDN — a docs build failure takes the install channel down
  • apps/hq is 104 MB and proprietary, inside the repository intended to be open-sourced

05 — Framework strategy

Which cross-framework approach, and why

Five viable strategies, assessed against Oxygen's buyer mix and the repository as it stands.

StrategyDeveloper experienceAccessibilityMaintenanceScales to 50+?Verdict
Separate native impls
one per framework		 Best possible, per framework Each implementation re-solves a11y — highest defect risk N× everything No — fails past ~20 Reject
Web Components only Weak in React; good elsewhere Shadow DOM complicates cross-boundary aria-*, labels, focus Lowest Yes, but React adoption suffers Reject
Core + adapters Good across the board Solved once in core Medium Yes Viable
Headless + renderers Consumers build their own UI Primitives correct; consumers can break it Medium Yes, narrower audience Reject
Hybrid
core + native React + elements		 Native in React, good elsewhere Solved once, verified per channel Medium Yes — matches the buyer mix Recommend

Recommendation

Hybrid — and make the two existing channels generated from one source rather than hand-written twins. React is the buyer reality for Netsmart, Heidi Health, and most digital-health startups; making it a second-class Web Component consumer would be strategically wrong. Web Components remain the right compatibility layer for the Angular and Vue long tail — but the SSR friction demonstrated by C1 makes them a poor primary layer.

What must be verified, and is not

There is no smoke-test application for any framework. The Vue, Angular, and Svelte support claims in the package README are unverified by any automated test — and the one verification actually run (a Node import) fails. Phase 2 adds five smoke apps to CI, each asserting render, SSR, and accessibility.

Decisions needed before Phase 1

  1. npm scope — consolidate on @oxygenui if it can be secured, or standardise on @oxygenui-design and align the registry namespace. Two similar scopes reads as a typosquat to a security reviewer. Recommend @oxygenui.
  2. React version floor — 18 or 19? Determines peer dependencies and whether custom elements are viable for React at all. Recommend ^18 || ^19.
  3. Open-source timing — before or after the first enterprise pilot? Recommend after; use pilots to harden the API.
  4. Headcount — one engineer means ~14 weeks; two means ~7. Recommend two.
  5. Phase 4 order — foundations or clinical first? Recommend foundations; the clinical components compose them.
